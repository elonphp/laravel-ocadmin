## 一、概述

### 1.1 技術選型

採用 [Spatie Laravel Permission](https://spatie.be/docs/laravel-permission) 作為權限管理基礎。

| 項目 | 說明 |
|------|------|
| 套件 | spatie/laravel-permission ^6.24 |
| Guard | 單一 Guard (`web`) |
| 角色命名 | Portal 前綴：`{portal}.{role_name}`（`super_admin`、`system` 例外） |
| 權限命名 | 四段式：`{portal}.{module}.{resource}.{action}`，portal 段由 `config/portals.php` 的 `permission_prefix` 決定 |
| 萬用權限 | Spatie Wildcard Permission（`enable_wildcard_permission => true`） |
| 多語支援 | 角色與權限的 `display_name`、`note` 透過翻譯表實現 |
| 資料表前綴 | `acl_`（透過 `config/permission.php` 設定） |

### 1.2 權限類型

| 類型 | 說明 | 實現方式 |
|------|------|----------|
| **功能權限** | 能否執行某操作 | Spatie Permission |
| **資料權限** | 能看到哪些資料 | 組織層級 + Policy |

### 1.3 現有基礎設施

- [x] `spatie/laravel-permission` 套件安裝
- [x] `config/permission.php` 設定（`acl_` 前綴、wildcard 啟用）
- [x] ACL 資料庫遷移（含翻譯表）
- [x] 自訂 Model：`App\Models\Acl\Role`、`App\Models\Acl\Permission`（含多語翻譯）
- [x] `User` Model 已掛載 `HasRoles` trait
- [x] 角色 Seeder (`AclRoleSeeder`)
- [x] `super_admin` 角色：全系統最高權限，`Gate::before` 無條件放行
- [ ] 權限 Seeder
- [ ] 路由級權限檢查

## 二、角色設計

### 2.1 命名規範

**格式：`{portal}.{role_name}`**

```
hrm.hr_manager
 │      │
 │      └── 角色名稱（snake_case）
 └── Portal 前綴
```

例外：`super_admin`、`system` 為全域角色，不帶 Portal 前綴。

> Portal 的定義與架構決策請見 [10001_Portal概述.md](10001_Portal概述.md)。

### 2.2 角色 ID 區段規劃

| ID 區段 | 用途 | 後台行為 |
|---------|------|---------|
| 1–20 | 系統保留角色 | 不可見、不可改（僅開發人員透過 DB/Seeder 調整） |
| 21–100 | 系統預設角色 | 可見、可指派給使用者、權限由 Gate::before 或 Seeder 控制 |
| 101+ | 使用者自建角色 | 完全可控（`auto_increment = 101`） |

判斷常數定義於 `Role` Model：`Role::SYSTEM_ROLES`（名稱清單，用於 `whereNotIn` 過濾）。

### 2.3 角色清單

#### 系統保留角色（id 1–20，後台不可見）

| id | name | 中文名稱 | 說明 |
|----|------|----------|------|
| 1 | `system` | 系統 | 系統操作標記角色（`users.username=service` 帳號賦予此角色） |
| 2–20 | — | — | 保留 |

#### 系統預設角色（id 21–100，後台可見）

| id | name | 中文名稱 | 說明 |
|----|------|----------|------|
| 21 | `super_admin` | 超級管理員 | 全系統最高權限，`Gate::before` 無條件放行 |
| 22–100 | — | — | 保留供各專案 Seeder 定義 |

#### Portal 角色（id 101+，後台可自建）

各專案依需求定義，例如：

**HRM Portal（hrm.*）：**

| 角色 name | 中文名稱 | 說明 |
|-----------|----------|------|
| `hrm.hr_manager` | HR 主管 | 管理所有 HR 功能，含薪資、報表 |
| `hrm.hr_operator` | HR 管理員 | 日常 HR 操作：員工資料、出勤、請假 |
| `hrm.payroll_manager` | 薪資主管 | 薪資計算、薪資單管理 |
| `hrm.dept_manager` | 部門主管 | 審核下屬請假/出勤，檢視部門資料 |
| `hrm.employee` | 一般員工 | 查看個人資料、打卡、申請請假 |

**Ocadmin Portal（admin.*）：**

| 角色 name | 中文名稱 | 說明 |
|-----------|----------|------|
| `admin.store_manager` | 門市店長 | 擁有大部分 admin.* 權限 |
| `admin.operator` | 後台操作員 | 日常後台操作 |
| `admin.viewer` | 唯讀檢視者 | 僅擁有 `*.access` 權限 |

### 2.4 system 與 super_admin 的分層

| | `system` | `super_admin` |
|---|---|---|
| **ID 區段** | 1–20（系統保留） | 21–100（系統預設） |
| **用途** | 系統操作標記 | 全系統最高權限 |
| **Gate::before** | 無 | 無條件 `return true` |
| **`can()` 快取** | 走角色組合快取 | 跳過（直接 `return true`） |
| **後台 UI 可見** | 不可見 | 可見 |
| **權限指派** | 無需權限 | 不需要（Gate 層放行） |
| **角色指派方式** | 僅 DB/Seeder | 後台可指派 |

**設計目的：** `super_admin` 為全系統最高權限，`Gate::before` 無條件放行。`system` 為系統操作標記角色，供系統自動執行的操作使用（如 `users.username=service` 帳號）。

### 2.5 跨角色指派

同一帳號可擁有多個角色：

```php
// HR 主管：管理功能 + 自己也是員工
$user->roles: ['hrm.hr_manager', 'hrm.employee']

// 部門主管：ESS + 部門管理
$user->roles: ['hrm.dept_manager', 'hrm.employee']

// 超級管理員：僅限 Ocadmin
$user->roles: ['super_admin']
```

## 三、權限設計

### 3.1 命名規範

**格式：`{portal}.{module}.{resource}.{action}`**

- **原則上 4 段**，使用點分隔，全小寫，snake_case
- resource 一律使用**單數**（如 `product`、`order`、`payment`，不用 `products`）
- module 多層用底線連接

| 段落 | 說明 | 範例 |
|------|------|------|
| `portal` | 系統入口（由 `config/portals.php` 的 `permission_prefix` 決定） | `hrm`, `admin` |
| `module` | 功能模組 | `ess`（自助）, `mss`（管理）, `team`（部門主管）, `catalog`, `order` |
| `resource` | 資源名稱 | `profile`, `employee`, `product`, `order`, `role` |
| `action` | 操作動作 | `access`, `modify`, `delete`, `approve`, `export` |

**非四段的例外情況：**

功能權限（CRUD 操作）固定 4 段，但用於**選單群組可見性控制**時，可使用較短的格式：

| 段數 | 格式 | 用途 | 範例 |
|------|------|------|------|
| 4 段 | `{portal}.{module}.{resource}.{action}` | 功能權限（原則） | `admin.master.supplier.access` |
| 2 段 | `{portal}.{module}` | 模組入口可見性 | `admin.master` |
| 3 段 | `{portal}.{module}.{resource}` | 資源入口可見性 | `admin.master.supplier` |

例如「主檔管理」選單群組設定 `permission: admin.master.access`，沒有此權限的角色整個主檔管理選單不可見，即使擁有其下子項的功能權限（見 [10011_選單機制.md](10011_選單機制.md)）。

### 3.2 萬用權限（Wildcard）

啟用 Spatie 原生 wildcard permission（`config/permission.php` 中 `enable_wildcard_permission => true`）。

使用 `*` 作為萬用字元：

```
# 單一資源的所有動作
hrm.mss.employee.*        → 符合 hrm.mss.employee.access、.modify、.delete、.export

# 整個模組的所有權限
hrm.mss.*.*               → 符合 hrm.mss.employee.*、hrm.mss.leave.*、hrm.mss.holiday.*

# 整個 Portal 的所有權限
hrm.*.*.*                  → 符合所有 hrm 權限

# 明確指定單一動作
hrm.ess.leave.modify       → 僅符合「請假申請」
```

> **注意**：不要建立 `*.all` 權限，使用 Spatie 原生 wildcard `*` 即可達成相同效果，無需額外的 Gate 邏輯。

```
admin.sale.return.modify            退貨處理

# Admin Portal — 系統管理

# 欄位級權限（action 後加 :column）
```

### 3.4 常用 Action

| Action | 說明 | 涵蓋範圍 |
|--------|------|----------|
| `menu` | 選單可見 | 純 UI 層，控制 sidebar 是否顯示該項目（見 [10011](10011_選單機制.md)） |
| `access` | 檢視 | 列表 + 單筆檢視（原 list + read），資料權限基礎 |
| `modify` | 修改 | 新增 + 修改（原 create + update） |
| `delete` | 刪除 | |
| `export` | 匯出 | |
| `approve` | 審核 | 適用於請假、出勤、退款等需審核流程 |

> **簡化原則**：能看就能列表（access），能改就能建（modify），刪除與審核獨立控管。

> **`menu` 與 `access` 拆開**：`menu` 只負責「選單是否顯示」，`access` 負責「能否進入該作業頁面 + 看資料」，兩者語意獨立、各自勾選。MenuComposer 用 `*.menu` 過濾，Controller `authorize()` 用 `*.access`。詳見 [10011_選單機制.md §1.1](10011_選單機制.md)。

> **`access` 是資料權限的基礎**：`modify`、`delete` 等權限建立在 `access` 之上——沒有 `access` 就進不了頁面、看不到資料，其他權限無從行使。因此指派權限時，給 `modify` 或 `delete` 必須同時給 `access`。

### 3.6 角色權限指派範例（Wildcard）

```php
// hrm.hr_manager — 使用萬用權限涵蓋所有動作
$hrManager->givePermissionTo([
    'hrm.mss.*.*',              // MSS 管理模組全部
    'hrm.team.*.*',             // 部門主管模組全部
    'hrm.ess.*.*',              // ESS 自助模組全部
]);

// hrm.hr_operator — 部分模組全開，部分限定
$hrOperator->givePermissionTo([
    'hrm.mss.employee.*',       // 員工管理全部動作
    'hrm.mss.department.access',
    'hrm.mss.designation.access',
    'hrm.mss.attendance.*',
    'hrm.mss.leave.*',
    'hrm.ess.*.*',              // ESS 自助全部
]);

// hrm.employee — 僅 ESS 個人權限
$employee->givePermissionTo([
    'hrm.ess.profile.access',
    'hrm.ess.profile.modify',
    'hrm.ess.attendance.modify',
    'hrm.ess.leave.access',
    'hrm.ess.leave.modify',
    'hrm.ess.payslip.access',
]);

// hrm.dept_manager — ESS + 部門管理
$deptManager->givePermissionTo([
    'hrm.team.employee.access',
    'hrm.team.attendance.access',

]);
```

## 四、資料表結構

### 4.1 Spatie Permission 資料表

使用 `acl_` 前綴（透過 `config/permission.php` 設定）：

| 資料表 | 說明 |
|--------|------|
| `acl_permissions` | 權限 |
| `acl_roles` | 角色 |
| `acl_role_has_permissions` | 角色-權限關聯 |
| `acl_model_has_permissions` | 使用者-權限關聯（直接指派） |
| `acl_model_has_roles` | 使用者-角色關聯 |

### 4.2 翻譯表

| 資料表 | 說明 |
|--------|------|
| `acl_role_translations` | 角色多語翻譯（display_name, note） |
| `acl_permission_translations` | 權限多語翻譯（display_name, note） |

### 4.3 擴展欄位

`acl_permissions`：**不需要任何擴展欄位**，僅用 spatie 標準欄位。

> 設計理由：
> - 權限沒交易語意（不像訂單有狀態）。用不到的權限直接 `DELETE` 即可，spatie pivot（`acl_role_has_permissions` / `acl_model_has_permissions`）皆 cascadeOnDelete，無孤兒問題；不需要軟標 zombie record。
> - 選單可見性透過獨立的 `*.menu` action 處理（見 [10011_選單機制.md §1.1](10011_選單機制.md)），不需在 `acl_permissions` 上加 `type` 欄位。
> - 權限分組顯示靠權限 name 的四段式結構解析（`{portal}.{module}` 前兩段）即可，不需 `parent_id` 樹狀結構。

`acl_roles` 額外欄位：

| 欄位 | 類型 | 說明 |
|------|------|------|
| `is_active` | boolean, default true | 是否啟用 |

## 五、設定與安裝

### 5.1 config/permission.php（重點摘要）

```php
return [
    'models' => [
        'permission' => App\Models\Acl\Permission::class,  // 自訂 Model
        'role' => App\Models\Acl\Role::class,              // 自訂 Model
    ],

    'table_names' => [
        'roles' => 'acl_roles',
        'permissions' => 'acl_permissions',
        'model_has_permissions' => 'acl_model_has_permissions',
        'model_has_roles' => 'acl_model_has_roles',
        'role_has_permissions' => 'acl_role_has_permissions',
    ],

    'teams' => false,  // 不使用 teams 功能

    'enable_wildcard_permission' => true,  // 啟用萬用權限

    'cache' => [
        'expiration_time' => \DateInterval::createFromDateString('24 hours'),
        'key' => 'spatie.permission.cache',
        'store' => 'default',
    ],
];
```

### 5.2 config/portals.php

每個 Portal 定義 `role_prefix` 和 `permission_prefix`，分別用於角色與權限命名的第一段；ocadmin 段透過 `env()` 讀取，衍生專案以 `.env` 覆寫即可換掉整套 prefix：

```php
return [
    'ocadmin' => [
        'url_slug'          => 'admin',
        'role_prefix'       => env('OCADMIN_ROLE_PREFIX', 'admin'),       // 角色命名：{role_prefix}.{role_name}
        'permission_prefix' => env('OCADMIN_PERMISSION_PREFIX', 'admin'), // 權限命名：{permission_prefix}.{module}.{resource}.{action}
        'dir'               => 'Ocadmin',
    ],
    'webv1' => [
        'url_slug'          => '',
        'role_prefix'       => 'webv1',
        'permission_prefix' => 'webv1',
        'dir'               => 'WebV1',
    ],
];
```

- **`role_prefix`**：角色名稱的前綴段，如 `admin.order_operator`
- **`permission_prefix`**：權限名稱的前綴段，如 `admin.catalog.option.access`
- 兩者通常相同，但保持分開定義以便未來彈性調整
- 字串拼接統一走 `permName()` / `roleName()` helper，**code / seeder 全程不 hardcode prefix**，見 [§5.5 Prefix 注入機制](#55-prefix-注入機制)

### 5.3 自訂 Model

角色和權限 Model 繼承自 Spatie 基礎類別，加上 `HasTranslation` trait 實現多語支援：

```php
// app/Models/Acl/Role.php
class Role extends SpatieRole

    use HasTranslation;

    protected array $translatedAttributes = ['display_name', 'note'];
    protected string $translationModel = RoleTranslation::class;
}

// app/Models/Acl/Permission.php
class Permission extends SpatiePermission
{
    use HasTranslation;

    protected $fillable = ['name', 'guard_name'];

    protected array $translatedAttributes = ['display_name', 'note'];

```

### 5.4 User Model

```php
// app/Models/User.php
use Spatie\Permission\Traits\HasRoles;

class User extends Authenticatable
{
    use HasRoles;

    /**
     * 檢查使用者是否擁有指定 Portal 的角色
     * super_admin 視為擁有所有 Portal 存取權
     */
    public function hasPortalRole(string $portal): bool
    {
        return $this->roles->contains(
            fn ($role) => $role->name === 'super_admin'
                || str_starts_with($role->name, $portal . '.')
        );
    }
}
```

### 5.5 Prefix 注入機制

`permission_prefix` / `role_prefix` 透過兩個 helper（`app/Helpers/helpers.php`）拼接，**code / seeder 全程不 hardcode prefix 字串**。衍生專案改 `.env` 即可換掉整套權限與角色名稱。

#### 5.5.1 Helper 函式

```php
// app/Helpers/helpers.php

function permName(string $suffix): string
{
    $prefix = config('portals.ocadmin.permission_prefix', 'admin');
    return "{$prefix}.{$suffix}";
}

function roleName(string $name, bool $isException = false): string
{
    if ($isException) {
        return $name;
    }
    $prefix = config('portals.ocadmin.role_prefix', 'admin');
    return "{$prefix}.{$name}";
}
```

- `permName('catalog.product.access')` → `admin.catalog.product.access`
- `roleName('order_operator')` → `admin.order_operator`
- `roleName('super_admin', true)` → `super_admin`（例外不加 prefix）

#### 5.5.2 例外角色清單

跨 portal 通用、不參與 prefix 拼接：

| name | 用途 |
|------|------|
| `system` | 系統操作標記角色（`users.username=service` 帳號） |
| `super_admin` | 全系統最高權限，`Gate::before` 無條件放行 |

呼叫時以 `roleName($name, true)` 標記例外。未來新增類似 framework-level 角色加入此清單；其他業務角色一律走 prefix。

#### 5.5.3 Seeder 寫作慣例

Seeder 內 array key **只寫後三段業務 token**（不含 prefix），runtime 由 helper 拼接：

```php
// AclPermissionSeeder
$permissions = [
    'catalog.product.access' => ['en' => 'Product Access', 'zh_Hant' => '商品 檢視'],
    'catalog.product.modify' => ['en' => 'Product Modify', 'zh_Hant' => '商品 修改'],
    // ...
];

foreach ($permissions as $suffix => $translations) {
    Permission::updateOrCreate(
        ['name' => permName($suffix), 'guard_name' => 'web'],
    );
    // ...
}

// AclRoleSeeder
[
    'id' => 21,
    'name' => roleName('super_admin', true),   // 例外，不加 prefix
],
[
    'id' => 101,
    'name' => roleName('order_operator'),      // → admin.order_operator
    'permissions' => [
        permName('catalog.product.access'),     // → admin.catalog.product.access
        permName('order.order.modify'),
    ],
],
```

實際檔案見 `database/seeders/AclPermissionSeeder.php` 與 `AclRoleSeeder.php`。`MenuSeeder` 內 `permission_name` 欄位、`UserSeeder` 內測試帳號的 `roles` 欄位同此寫法。

#### 5.5.4 其他「讀 prefix 字串」的位置

| 位置 | 寫法 |
|---|---|
| Route middleware | `'permission:' . permName('catalog.product.access')` |
| `requirePortalRole` middleware | `'requirePortalRole:' . config('portals.ocadmin.role_prefix')` |
| Blade `@can` | `@can(permName('catalog.product.access'))` |
| Policy / Gate | `$user->can(permName('...'))` |
| MenuComposer code-driven 備援選單 | `permission => permName('...')` |
| LIKE 查詢 portal 角色 | `where('name', 'like', config('portals.ocadmin.role_prefix') . '.%')` |
| `hasRole('super_admin')` | 直接寫字串，例外角色不需 prefix |

#### 5.5.5 為何抽 prefix runtime 拼接（而非 seeder 字串內帶 prefix）

- Seeder 字串若用 `{$prefix}.catalog.product.access` 仍混雜 prefix 與業務 token，跨專案不能直接重用
- 抽掉 prefix 後 seeder 字串純粹是「業務 token」，ocadmin 與衍生專案的 seeder **業務 token 清單可完全相同**，只差 runtime prefix
- 未來如要把 seeder 邏輯做成共用基底（`Core/Seeders/BasePermissionSeeder`），此為必要前提

### 6.1 Controller 中

### 6.2 Middleware

```php
// 或

    ->middleware('can:hrm.mss.employee.access');
```

### 6.3 Blade 中

```blade
{{-- 顯示控制 --}}
@can('hrm.mss.employee.modify')
    <button>新增員工</button>
@endcan

{{-- 或在 Controller 已決定後直接以變數控制 --}}

    <button>新增員工</button>

```

本範本前後端不分離，按鈕可見性由 server-side Blade 直接決定，**不需把 permission 集合送到 client**（前端拿不到、也偽造不出）。以下 §6.3.1～§6.3.4 記錄「**若改走前後端分離**（Inertia / Vue / React SPA）」時權限如何送到前端——本範本雖未採用，仍先釘好設計，衍生專案導入 SPA 時照做即可。

#### 6.3.1 前後端分離時：權限怎麼送到前端（兩種資料、兩個時機）

前後端分離後，「權限」在前端要用到兩件事，**時機與次數完全不同，先分清**：

| | 是什麼 | 何時給 | 給幾次 | 由誰算 |
|---|---|---|---|---|
| **權限集合**（權限名稱字串陣列） | 這個 user 能幹嘛的**全集** | **登入 / SPA 開機那一次** | **一次，給整包** | 前端拿去濾選單、濾按鈕 |
| **每個動作的把關** | 這次 POST/PUT 准不准 | **每次打 API 時** | **每個動作各自** | **後端** route `can:` middleware（真牆） |

**(1) 登入時給「全部」，不是進頁才給。** 前端登入後打一次 `GET /api/me`，後端回這個 user 的權限全集（外加身分、super_admin 旗標）：

```php
// 後端 /api/me（auth:sanctum）
Route::middleware('auth:sanctum')->get('/api/me', function (Request $request) {
    $u = $request->user();
    return [
        'user'           => $u->only('id', 'name'),
        'roles'          => $u->getRoleNames(),          // ['hrm.hr_manager', ...]
        'permissions'    => $u->getAllPermissions()->pluck('name'),  // 見 §6.3.2
        'is_super_admin' => $u->hasRole('super_admin'),  // 見 §6.3.3（必帶）
    ];
});
```

- 這包很小（一堆字串）、**很少變** → **一次給整包最划算**，不要每進一頁再跟後端要。
- **選單**就從這包濾：選單項掛 `hrm.mss.employee.menu`，包裡有 → 顯示，沒有 → 不顯示。**登入當下整棵選單即定。**

**(2) 進功能頁不用「再給權限」，但後端每個動作照樣擋。** UI 該顯示什麼，用登入那包就夠；但後端不因此放手——進頁 GET 檢查 `.access`、按儲存 POST/PUT 檢查 `.modify`，沒有一律 403。

> **鐵律**：登入那包只是「畫 UI 用的提示」，**真門鎖永遠在後端、每個動作各自鎖**（見 §6.5 route middleware）。改 JS 變數、繞 UI 直打 API 都被 `can:` 擋。前端 `can()` **永遠不是授權邊界**。

#### 6.3.2 `permissions` 陣列裡放什麼

`getAllPermissions()->pluck('name')` 回傳的是**該 user 透過角色（+直接指派）取得的權限名稱字串陣列**：

```json
["hrm.mss.employee.menu", "hrm.mss.employee.access", "hrm.mss.employee.modify",
 "hrm.mss.leave.access",  "hrm.mss.leave.approve"]
```

**Wildcard 注意**（呼應 §3.2）：若角色被指派的是 wildcard（如 `hrm.mss.*.*`），陣列裡會**原樣**是 `"hrm.mss.*.*"`，**不會**自動展開成一條條具體權限。前端若只用 `includes(name)` 精確比對就會漏判。兩個解法擇一：

- **前端 `can()` 自己比對 wildcard**（推薦，見 §6.3.3 的 helper）；或
- **後端傳前先展開**成具體權限清單再送（前端就能純 `includes`）。

#### 6.3.3 `super_admin` 的空陣列坑（必處理）

`super_admin` 靠 `Gate::before` 無條件放行、**本身沒有被指派任何具體權限**（見 §10.5），所以 `getAllPermissions()` 對 super_admin **回空陣列 `[]`**。

若 `/api/me` 天真地把空陣列丟前端 → 前端 `can()` 全 `false` → **super_admin 登入卻看到空選單、零按鈕**。此坑**只在拿 super_admin 帳號測時才爆**，最易漏。

**解法**：`/api/me` 一定帶 `is_super_admin` 旗標（`developer` 同理），前端 `can()` 開頭先判：

```js
// 前端權限 helper（含 super_admin 旗標 + wildcard 比對）
function can(name) {
  if (auth.is_super_admin) return true                    // ← 漏這行 super_admin 就瞎
  return auth.permissions.some(p =>
    p === name ||                                          // 精確
    (p.endsWith('.*') && name.startsWith(p.slice(0, -2) + '.'))  // wildcard 尾段
  )
}
```

#### 6.3.4 無權限時的 UI：隱藏 vs 變灰

有 `.access` 沒 `.modify`（能看不能存）時，UI 要有分別。兩種做法：

| 做法 | 何時用 | 缺點 |
|---|---|---|
| **隱藏**（不 render 按鈕） | **預設首選**：這角色本就不該做（如檢視者看不到「刪除」） | 使用者不知「有此功能但我沒權」 |
| **變灰 / disabled** | 想讓人知道「有此功能、你這身分不能用，需申請」 | 一堆灰鈕無說明會被當成故障 |

**建議：**

1. **破壞性 / 敏感動作（`delete`、`approve`、作廢、退款等）→ 直接隱藏。**
2. **表單「儲存」鈕**：沒 `.modify` 就**整頁進唯讀**（欄位 disabled + 不顯示儲存），而非只灰儲存鈕、卻讓人填半天才發現存不了。
3. **要變灰就配一句說明**（「此操作需 XX 權限」），否則灰鈕形同騙人。
4. 判斷原則：**「這角色永遠不會有」→ 隱藏；「同頁有人有、有人沒，想讓人知道差異」→ 變灰＋說明。**

> 這與 Blade 版一致：Blade 用 `@can` 決定「印不印按鈕」（隱藏）或「印出 disabled 屬性」（變灰），只是判斷從 server-side `@can` 換成前端 `can()`。**授權邊界兩者都在後端，UI 只是提示。**

### 6.4 欄位級權限

```php
// Controller
public function show(Employee $employee)
{
    $data = $employee->toArray();

    // 隱藏無權限的敏感欄位
    if (!auth()->user()->can(permName('mss.payroll.access:salary'))) {
        unset($data['salary']);
    }
    if (!auth()->user()->can(permName('mss.payroll.access:bonus'))) {
        unset($data['bonus']);
    }

    return view('admin.hrm.employee.show', ['employee' => $data]);
}
```

### 6.5 Route middleware 強制檢查（推薦樣板）

**Enforcement 一律落在 route middleware**：集中於 routes 一處掃描，不污染 controller，`route:list` 看得到，漏鎖容易被 review 出來。Controller / FormRequest 的 `authorize()` 屬備援、欄位級才用。

#### 6.5.1 標準 CRUD 8 routes 對應表

每個 CRUD resource 的 8 條標準 routes 對應 3 個 action permission：

| Route | Method | Permission action |
|---|---|---|
| `/` (index) | GET | `.access` |
| `/list` (list) | GET | `.access` |
| `/{binding}/edit` (edit form) | GET | `.access` |
| `/create` (create form) | GET | `.modify` |
| `/` (store) | POST | `.modify` |
| `/{binding}` (update) | PUT | `.modify` |
| `/{binding}` (destroy) | DELETE | `.delete` |
| `/batch-delete` (batchDelete) | POST | `.delete` |

> **為何 `edit` 表單是 `.access` 但 `create` 表單是 `.modify`？**
> `edit` 顯示既有資料 → 只要能「看」就允許看表單，能不能存（PUT update）由 `.modify` 另擋；`create` 顯示空白表單 → 沒有資料可看，存在意義就是「打算新增」，所以早一步用 `.modify` gatekeep，避免使用者填完才 403。

#### 6.5.2 `CrudRoutesHelper::register()` helper

`app/Helpers/Classes/CrudRoutesHelper.php` 提供 `CrudRoutesHelper::register()` 一行展開上述 8 條 + 對應 middleware：

```php
// app/Portals/Ocadmin/routes/ocadmin.php

use App\Helpers\Classes\CrudRoutesHelper;

Route::prefix('catalog')->name('catalog.')->group(function () {
    CrudRoutesHelper::register('products', ProductController::class, 'catalog.product', 'product');

    CrudRoutesHelper::register('options',  OptionController::class,  'catalog.option',  'option');
});
```

參數順序：URL 路徑段 / Controller class / permission 中段（不含 prefix 與 action）/ route binding 變數名。

Ad-hoc action 透過第 5 個參數陣列傳入，每筆 `[method, url, controllerMethod, routeName, permAction]`：

```php
CrudRoutesHelper::register('departments', DepartmentController::class, 'org.department', 'department', [
    ['get', '/by-company', 'byCompany', 'by-company', 'access'],
]);

CrudRoutesHelper::register('settings', SettingController::class, 'system.setting', 'setting', [
    ['post', '/parse-serialize', 'parseSerialize', 'parse-serialize', 'modify'],
    ['post', '/to-serialize',    'toSerialize',    'to-serialize',    'modify'],
]);
```

#### 6.5.3 Ad-hoc action 對應規則

非 CRUD 7 標準動詞按業務語義歸三類：

| 類型 | 對應 | 涵蓋 |
|---|---|---|
| 唯讀 / 列表 / 表單頁 / 篩選 / 搜尋 | `.access` | `byCompany`、`byTaxonomy`、`searchUsers`、`search`、`links`、`form`、`preview`、`children` |
| 寫入動作 | `.modify` | `save`、`saveLinks`、`reorder`、`parseSerialize`、`toSerialize`、`upload`、`folder` |
| 刪除 / 撤銷 / 強制踢登 | `.delete` | `revoke`、`forceRevoke`、`delete`（ImageManager 的） |

`revoke` / `forceRevoke` 屬「刪除 record」性質 → `.delete`。**不另開 `.revoke` action**：簡單三段（access/modify/delete）涵蓋所有 ACL 與系統管理場景。當業務 module 出現真正的「上級主管」概念（如訂單 void / unvoid、請假 approve）時，個別開新 action（`.approve`、`.unvoid`），不在範本層的標準動詞之上預先設計。

#### 6.5.4 豁免清單

下列 route 不掛 `can:` middleware，但仍受 `auth` + `requirePortalRole:` 兩層保護：

| Route 範圍 | 理由 |
|---|---|
| `LoginController` (login form / login / logout) | 認證前 |
| Dashboard 首頁與 widget API | 任何 admin role 皆可進首頁 |
| `Core/Account/ProfileController` / `Modules/Account/UserDeviceController` | self-service，登入即可動自己的資料 |
| `Core/Controllers/System/SchemaController` | Controller 內已 `hasRole('super_admin')` 硬鎖（dev tool） |
| `OcadminController` base | base class，無 action |

#### 6.5.5 ImageManager 雙模處置

`ImageManagerController` 是跨 module 的圖片管理 utility。處置依 [10001 §八 雙模架構](10001_Portal概述.md)：

| 模式 | 處置 |
|---|---|
| **Mode A（前後台分離）** | 鎖 `admin.common.image_manager.{access,modify,delete}`，預設給編輯類角色（如 `admin.catalog_editor`）。範本層 `routes/ocadmin.php` 即此實作 |
| **Mode B（ocadmin 兼任前台 / 單應用）** | **建議衍生專案在 ServiceProvider boot 階段檢查 `web_enabled === true` 時不註冊 image-manager 路由**。理由：單一應用所有登入者都能存取整個系統圖庫（誤刪、隱私、亂上傳風險）— 即使有 permission 機制也不該開放這條路徑。Mode B 場景需要圖片時走業務專屬 controller 個別處理（例如員工大頭照 upload 限定 HR 角色） |

範本層只實作 Mode A 鎖；Mode B 處置以衍生專案各自負責。

#### 6.5.6 注意：`User::can()` 與 `Gate::check()` 兩條路徑差異

本範本的 `User::can()` 覆寫了 Eloquent 預設行為，改走角色組合快取（見 [§十 使用者權限快取](#十使用者權限快取)）。實際路徑：

- **`Gate::check($ability)` / route `can:` middleware / Blade `@can(...)` / `$this->authorize(...)`** → 走 Gate 流程，先跑 `Gate::before` callback（super_admin 在這層無條件放行），未命中才比對角色權限。**推薦樣板用這條路徑**
- **`$user->can($ability)` 直呼** → 走 User Model 覆寫，**bypass `Gate::before`**，只比對角色組合快取的權限清單。super_admin 因預設 `permissions => []`（依賴 `Gate::before` 放行），這條路徑會回 `false`

實務上幾乎所有 Laravel 慣用法（middleware / Blade / Policy）都走 Gate 路徑，不受影響。**僅當 PHP code 內寫 `$user->can(...)` 且需要 super_admin 也通過時**，改用 `Gate::forUser($user)->check($ability)` 才會等同 middleware 行為。

`MenuComposer::filterByPermission` 就是因此明確採 `Gate::check()` 走 before 流程，確保 super_admin 選單可見性正確。

## 七、資料權限

資料範圍由權限的 module 前綴隱含：

| 權限前綴 | 資料範圍 | 對應角色 |
|----------|---------|---------|
| `hrm.mss.*` | 全公司 | HR 管理角色 |
| `hrm.team.*` | 同部門 | 部門主管 |
| `hrm.ess.*` | 僅自己 | 一般員工 |

### 7.1 Policy

```php
// app/Policies/EmployeePolicy.php

class EmployeePolicy
{
    public function viewAny(User $user): bool
    {
        return $user->can('hrm.mss.employee.access')
            || $user->can('hrm.team.employee.access');
    }

    public function view(User $user, Employee $employee): bool
    {
        // HR 有權限可查看所有
        if ($user->can('hrm.mss.employee.access')) {
            return true;
        }

        // 查看自己
        if ($employee->user_id === $user->id) {
            return true;
        }

        // 部門主管查看下屬
        if ($user->can('hrm.team.employee.access')) {
            return $employee->department_id === $user->employee?->department_id;
        }

        return false;
    }
}
```

### 7.2 請假審核

```php
// app/Policies/LeavePolicy.php

class LeavePolicy
{
    public function approve(User $user, Leave $leave): bool
    {
        // HR 可審核所有
        if ($user->can('hrm.mss.leave.approve')) {
            return true;
        }

        // 部門主管只能審核自己部門的
        if ($user->can('hrm.team.leave.approve')) {
            return $leave->employee->department_id === $user->employee?->department_id;
        }

        return false;
    }
}
```

## 八、Seeder

### 8.1 角色 Seeder

角色由 `AclRoleSeeder` 管理，定義於 `database/seeders/AclRoleSeeder.php`。Portal 角色用 `roleName($name)`；`system` / `super_admin` 例外角色用 `roleName($name, true)` 標記不加 prefix（見 [§5.5 Prefix 注入機制](#55-prefix-注入機制)）。

### 8.2 權限 Seeder（範例）

Array key **只寫後三段業務 token**（不含 prefix），`permName($suffix)` 在 runtime 拼接 `config('portals.ocadmin.permission_prefix')`。衍生專案改 `.env` 即可換掉整套權限名稱。

```php
// database/seeders/AclPermissionSeeder.php

use App\Models\Acl\Permission;
use App\Models\Acl\PermissionTranslation;
use Illuminate\Database\Seeder;
use Spatie\Permission\PermissionRegistrar;

class AclPermissionSeeder extends Seeder
{
    public function run(): void
    {
        app()[PermissionRegistrar::class]->forgetCachedPermissions();

        $permissions = [
            'mss.dashboard.access'   => ['en' => 'Dashboard',        'zh_Hant' => '儀表板'],
            'mss.employee.access'    => ['en' => 'Access Employee',  'zh_Hant' => '員工檢視'],
            'mss.employee.modify'    => ['en' => 'Modify Employee',  'zh_Hant' => '員工修改'],
            'mss.employee.delete'    => ['en' => 'Delete Employee',  'zh_Hant' => '員工刪除'],
            'ess.profile.access'     => ['en' => 'Access Profile',   'zh_Hant' => '個人資料檢視'],
            'ess.profile.modify'     => ['en' => 'Modify Profile',   'zh_Hant' => '個人資料修改'],
            // ... 其餘權限依 §3.5 權限清單定義
        ];

        foreach ($permissions as $suffix => $translations) {
            $perm = Permission::updateOrCreate(
                ['name' => permName($suffix), 'guard_name' => 'web'],
            );
            foreach ($translations as $locale => $displayName) {
                PermissionTranslation::updateOrCreate(
                    ['permission_id' => $perm->id, 'locale' => $locale],
                    ['display_name' => $displayName],
                );
            }
        }
    }
}
```

實際 ocadmin 範本檔見 `database/seeders/AclPermissionSeeder.php`（含 catalog / member / order / system 等業務 token 清單）。`MenuSeeder` 的 `permission_name` 欄位、`UserSeeder` 測試帳號的 `roles` 欄位也走 helper，寫法同此。

## 九、多語支援

本系統的角色與權限支援多語翻譯，透過自訂 Model 上的 `HasTranslation` trait 實現。

### 9.1 取得翻譯後的名稱

```php
// 取得當前語系的 display_name
$role->display_name;  // 自動依 app()->getLocale() 回傳

// 指定語系
$role->translate('zh_Hant')->display_name;  // "HR 主管"
$role->translate('en')->display_name;        // "HR Manager"
```

### 9.2 View 顯示

Controller 傳遞角色/權限資訊到 view 時，模型的 `display_name` 自動帶入當前語系的翻譯：

```php
// Controller
return view('ocadmin::system.acl.role.index', [
    'roles' => Role::with('translation')
        ->orderBy('sort_order')
        ->where('is_active', true)
        ->get(),
]);
```

Blade 內直接讀 `$role->display_name`，會依當前 `app()->getLocale()` 自動回傳對應語系。

## 十、使用者權限快取

### 10.1 問題

Spatie 內建快取僅快取**全域權限定義表**（所有 permission 與 role 的對應關係），不快取個別使用者的權限。每個 request 仍需：

1. 載入使用者的 roles（1 次 DB query）
2. 載入使用者的 direct permissions（1 次 DB query）
3. In-memory 比對

系統規模擴大（使用者多、權限多）時，每個 request 固定 2 次 DB query 可優化。

### 10.2 方案：角色組合快取 + 全域版本號

**核心概念：** 將使用者的 role ids 排序後組成 cache key，快取該角色組合的所有權限名稱。相同角色組合的使用者共用同一份快取。

**Cache 結構：**

```
┌─────────────────────────┐     ┌──────────────────────────────────┐
│ key: role_perm_ver      │     │ key: role:1-3-11:v42             │
│ val: 42                 │     │ val: ['admin.catalog.product.ac… │
│ TTL: forever            │     │       'admin.master.supplier.ac… │
│                         │     │       ...]                       │
│ （全域版本號，所有角色   │     │ TTL: 7 days                      │
│   組合共用一個）         │     │                                  │
└─────────────────────────┘     │ （角色 1+3+11 的所有權限）        │
                                └──────────────────────────────────┘
```

### 10.3 查詢流程

```
使用者發 request
    │
    ├─ 1. 取 user 的 role_ids → [1, 3, 11]（從 DB 或 session）
    │
    ├─ 2. 取全域版本號 → Cache::get('role_perm_ver') → 42
    │
    ├─ 3. 組 cache key → "role:1-3-11:v42"
    │
    ├─ 4. Cache::get("role:1-3-11:v42")
    │     ├─ hit  → 拿到權限陣列（0 DB query）
    │     └─ miss → 查 DB 建立權限陣列，寫入 cache（TTL 7 天）
    │
    └─ 5. $user->can() 在 in-memory 比對
```

**每 request 成本：** 2 次 cache get（版本號 + 權限），cache hit 時 0 次 DB query。

### 10.4 快取失效：全域版本號

角色的權限被修改時，**只遞增版本號，不主動重建快取**：

```php
// 角色權限變更時（如 RoleController 儲存權限後）
Cache::increment('role_perm_ver');
```

- 版本號從 42 → 43
- 所有 request 組出的 key 自動從 `v42` 變 `v43`
- 全部 cache miss，各自在下一次 request 時從 DB 重建
- 舊版 `v42` 的 key 無人再讀，靠 TTL（7 天）自然回收

**不在變更當下重建的原因：** 管理員設定權限時可能連續修改多次，若每次都重建會造成不必要的 IO。Lazy rebuild（等 request 進來時才建）更合理。

### 10.5 實作要點

**User Model 覆寫 `can()`：**

```php
// app/Models/User.php

public function can($ability, $arguments = [])
{
    // Policy 檢查（有 arguments 時走原生 Gate 邏輯）
    if (!empty($arguments)) {
        return parent::can($ability, $arguments);
    }

    // super_admin 跳過快取（Gate::before 也會放行，這裡提前 return 省掉 cache lookup）
    if ($this->hasRole('super_admin')) {
        return true;
    }

    $permissions = $this->getCachedPermissions();

    return in_array($ability, $permissions);
}

protected function getCachedPermissions(): array
{
    $roleIds = $this->roles->pluck('id')->sort()->implode('-');
    $ver = Cache::get('role_perm_ver', 1);
    $key = "role:{$roleIds}:v{$ver}";

    return Cache::remember($key, now()->addDays(7), function () {
        return $this->getPermissionsViaRoles()
            ->pluck('name')
            ->toArray();
    });
}
```

**角色權限變更時遞增版本號：**

```php
// 角色權限 sync 後
$role->syncPermissions($permissions);
Cache::increment('role_perm_ver');
```

**版本號初始化與 Gate::before（AppServiceProvider boot）：**

```php
// Cache::add 僅在 key 不存在時寫入，每次 boot 呼叫無副作用
Cache::add('role_perm_ver', 1);

// super_admin 為全系統最高權限，Gate::before 無條件放行
Gate::before(fn ($user, $ability) => $user->hasRole('super_admin') ? true : null);
```

### 10.6 TTL 設計

| Cache entry | TTL | 原因 |
|-------------|-----|------|
| `role_perm_ver`（版本號） | forever | 關鍵資料，不可意外過期 |
| `role:{ids}:v{ver}`（權限集合） | 7 天 | 當前版本實質 forever（持續命中）；舊版靠 TTL 自動回收 |

### 10.7 注意事項

- **直接指派權限（`model_has_permissions`）：** 此快取僅涵蓋透過角色取得的權限。若有使用直接指派，需在 cache key 中加入 user id 或另行處理
- **角色變更 vs 權限變更：** 使用者的角色被更換時，其 role_ids 組合改變，自然組出不同 cache key，不需要額外處理版本號
- **Cache driver：** 此方案不依賴 Cache Tags，任何 driver（file、database、Redis、Memcached）皆可使用
- **停用帳號：** 緊急封鎖惡意使用者應透過停用帳號（`is_active = false`，auth middleware 攔截），不應依賴權限快取失效

### 10.8 與 Spatie 內建快取的比較

| | Spatie 內建 | 角色組合快取 |
|---|---|---|
| **快取內容** | 全域權限定義表 | 角色組合 → 權限名稱集合 |
| **每 request DB query** | 2 次（user→roles, user→permissions） | 0 次（cache hit 時） |
| **快取命中率** | 100%（全域一份） | 高（同角色組合共用，實務上組合有限） |
| **失效機制** | 權限/角色定義異動時自動清 | 全域版本號遞增 |
| **Cache driver 限制** | 無 | 無 |

## 十二、單控制器多選單入口

### 12.1 情境

同一筆資料（如供應商）需要從不同選單入口操作：

- **主檔管理 > 供應商**：`/admin/master/suppliers`
- **庫存管理 > 供應商**：`/admin/inventory/suppliers`

兩個入口使用**同一個 Controller**（`SupplierController`），但使用者從哪個入口進來，返回按鈕、列表連結、分頁連結就要指回對應的路徑。

### 12.2 路由：相同 Controller 掛在不同前綴

```php
// 主檔管理 > 供應商
Route::prefix('master')->name('master.')->group(function () {
    Route::prefix('suppliers')->name('supplier.')->group(function () {
        Route::get('/', [SupplierController::class, 'index'])->name('index');
        Route::get('/list', [SupplierController::class, 'list'])->name('list');
        Route::get('/create', [SupplierController::class, 'create'])->name('create');
        // ...
    });
});

// 庫存管理 > 供應商（共用同一個 Controller）
Route::prefix('inventory')->name('inventory.')->group(function () {
    Route::prefix('suppliers')->name('supplier.')->group(function () {
        Route::get('/', [SupplierController::class, 'index'])->name('index');
        Route::get('/list', [SupplierController::class, 'list'])->name('list');
        Route::get('/create', [SupplierController::class, 'create'])->name('create');
        // ...
    });
});
```

產生兩組 route name：

| 入口 | route name 前綴 |
|------|----------------|
| 主檔管理 | `lang.ocadmin.master.supplier` |
| 庫存管理 | `lang.ocadmin.inventory.supplier` |

### 12.3 Controller：用 `routePrefix()` 動態推算

Controller 不寫死路由名稱，而是從當前 request 的 route name 反推前綴：

```php
/**
 * 從當前 route name 反推前綴
 * e.g. 'lang.ocadmin.master.supplier.index' → 'lang.ocadmin.master.supplier'
 *      'lang.ocadmin.inventory.supplier.edit' → 'lang.ocadmin.inventory.supplier'
 */
protected function routePrefix(): string
{
    return preg_replace('/\.[^.]+$/', '', request()->route()->getName());
}
```

所有 URL 都透過前綴動態產生：

```php
public function index(Request $request): View
{
    $prefix = $this->routePrefix();

    $data['list_url']  = route("{$prefix}.list");
    $data['index_url'] = route("{$prefix}.index");
    $data['add_url']   = route("{$prefix}.create");
    // ...
}

public function create(): View
{
    $prefix = $this->routePrefix();

    $data['save_url'] = route("{$prefix}.store");
    $data['back_url'] = route("{$prefix}.index");  // 返回按鈕回到來源列表
    // ...
}
```

### 12.4 View：不需任何修改

View 只使用 Controller 傳入的 `$back_url`、`$list_url` 等變數，不關心具體路徑。

### 12.5 效果

| 使用者操作 | 產生的 URL |
|-----------|-----------|
| 從主檔管理進入，點新增 | `/admin/master/suppliers/create` |
| 按返回 | `/admin/master/suppliers` |
| 從庫存管理進入，點新增 | `/admin/inventory/suppliers/create` |
| 按返回 | `/admin/inventory/suppliers` |

### 12.6 注意事項

- 兩組路由的 action name（`index`、`create`、`store`、`edit`、`update`、`destroy`）必須一致
- Route Model Binding 的參數名也要一致（如 `{organization}`）
- 權限控制在 Controller constructor 中處理，兩個入口可共用或分別設定權限
- **權限層面：功能權限綁資源、選單可見綁放置點**——`.access` / `.modify` / `.delete` 是資源層（兩入口**共用同一組**，不因入口而異）；`.menu` 是放置點層（兩入口可**各自**控制顯隱，或共用一個）。這正是 `.menu` 與 `.access` 分開的價值之一，詳見 [10011 §1.1](10011_選單機制.md#11-選單權限慣例menu-action)

## 十三、設計決策說明（為何選單數）

§3.1 規定 resource 段一律用單數（`product`、`order`、`user`，不用複數）。
這個決策有時會被質疑——畢竟 RESTful 路由用複數（`/products`、`/users`），
業界 IAM 命名也常見複數（GCP IAM `compute.instances.get`、Spatie 文件範例
`edit articles`）。本節說明為何本規範刻意選**單數**：

### 13.1 跟 Eloquent Model 命名對齊

Laravel Model 用單數（`User`、`Product`、`Order`），permission 跟著單數，
跨 layer 一致：

```
Model:      App\Models\Product
Policy:     App\Policies\ProductPolicy
Permission: admin.catalog.product.access     ← 看到 permission name 立刻知道對應 Model
Route URL:  /admin/catalog/products          ← URL 走 RESTful 複數慣例（不衝突）
```

URL 跟 permission 各走各的慣例，不互相牽動。維護者習慣這個分工後，看 permission
就知道對應哪個 class。

### 13.2 英文複數變化複雜，單數最簡單

部分名詞複數變化規則特殊：

| 單數 | 複數 |
|---|---|
| `category` | `categories` |
| `taxonomy` | `taxonomies` |
| `status` | `statuses` |
| `child` | `children` |
| `phenomenon` | `phenomena` |
| `analysis` | `analyses` |

選單數 = 永遠不用想複數規則，跨整個系統 token 一致。

### 13.3 Wildcard 語意更直覺

```
admin.catalog.product.*    讀作「對 product 資源的所有動作」     ← 直覺
admin.catalog.products.*   讀作「對 products 集合的所有動作」？  ← 含混：是集合操作還是逐筆？
```

單數版用 wildcard 時，語意自然指向「對該資源類型的所有動作」，不會有「集合 vs 個體」
的歧義。

### 13.4 避免 list/show 的二元區分

複數版命名容易引導出「集合操作 vs 個體操作」二元化：

```
products.list   看清單
products.show   看單筆
```

但 spatie / Laravel ACL 沒這層區分，看清單跟看單筆通常用同一個 `access` 權限。
單數版自然不會落入這個陷阱：

```
product.access   一個權限管「能否進該資源的存取頁面」（含清單與單筆）
```

### 13.5 Action 段（第 4 段）天生單數

`access`、`modify`、`delete`、`approve`、`export`、`pay` 都是動詞，動詞沒複數
變化問題。第 4 段一律單數沒爭議；既然第 4 段單數，第 3 段也跟著單數，整個 token
讀起來最一致。

### 13.6 業界並非壓倒性偏向某一方

實際上業界混用，並無公認標準：

| 系統 | 慣例 |
|---|---|
| AWS IAM | 混用（`s3:GetObject` 單數、`ec2:DescribeInstances` 複數） |
| GCP IAM | 偏複數（`compute.instances.get`） |
| Spatie 官方文件 | 偏複數（範例 `edit articles`） |
| Laravel Gate / Policy | 無強制慣例 |

本規範選擇單數是**內部一致性決定**（與 Model / Policy 對齊、與英文不規則複數
脫鉤），不是因為「業界都這麼做」。
