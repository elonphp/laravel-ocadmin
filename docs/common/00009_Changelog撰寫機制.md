# Changelog 撰寫機制

每季產出一份「業務導向」的系統更新摘要，給管理層、跨部門查閱。詳細技術改動看 `git log`；本機制目的是把「對營運有意義的變更」整理成非工程同仁也能讀的形式。

> 本文件為跨 branch 共用約定。各專案的具體受眾、撰寫節奏可在自家 `docs/changelog/README.md` 微調。

## 位置與命名

- 目錄：`docs/changelog/`
- 檔名：`YYYYQN.md`（例：`2026Q2.md` = 2026 年第二季）
- 自家 README：`docs/changelog/README.md` — 放自家受眾、範本與微調說明（內容可參照本文件）

## 撰寫節奏

| 季度 | 月份 | 撰寫時間 |
|---|---|---|
| Q1 | 1-3 月 | 4 月初 |
| Q2 | 4-6 月 | 7 月初 |
| Q3 | 7-9 月 | 10 月初 |
| Q4 | 10-12 月 | 隔年 1 月初 |

## 寫法重點

1. 寫**業務影響**而非技術細節（給非工程背景的讀者看）
2. 量化效益盡量量化（節省幾小時、影響幾人、降低多少錯誤率）
3. 分四段落：
   - **新功能上線**：使用者直接感受到的新能力
   - **系統改善**：後台優化、技術升級，使用者可能無感但有長期價值
   - **修正問題**：bug 修正，盡量註明影響範圍
   - **進行中項目**：預告下一季交付內容

## 季中草稿機制（重要）

**季中草稿不進 git，季末完稿才提交。**

理由：
- changelog 的本質是「已成為事實的事」，季中還會反覆改的內容不是 changelog，是 working notes
- 每週一條 `docs: update Q? draft` 會稀釋 git log 的訊號

工作流程：

1. 季初開草稿在 `docs/todo/changelog_YYYYQN_draft.md`
2. 季中持續累積（純本地檔案，不被 git 追蹤）
3. 季末整理完稿 → `git mv` 到 `docs/changelog/YYYYQN.md` → 一次性 commit

`.gitignore` 必備規則：

```gitignore
# Changelog 季中草稿（季結束後改名移到 docs/changelog/ 才提交）
docs/todo/changelog_*_draft.md
```

> 注意：這條規則跟 `docs/todo/` 整目錄是否進 git 無關。`docs/todo/` 一般情況**仍進 git**（設計筆記、跨機器同步、進度追蹤都需要），只是 `changelog_*_draft.md` 這個 pattern 例外。

## 範本

新建檔案後複製填寫：

```markdown
# YYYY QN 開發成果

> **本季定位：（一句話概括）**

## 摘要
- **時間**：YYYY-MM-DD ～ YYYY-MM-DD
- **里程碑**：（本季最重要的 1-2 件事）

## 新功能上線
- **功能 A**：業務影響（量化）
- **功能 B**：⋯⋯

## 系統改善
- ⋯⋯

## 修正問題
- ⋯⋯

## 進行中項目
- 項目 X（預計 Q? 上線）
```

## 跟其他文件的關係

| | 用途 |
|---|---|
| `docs/changelog/` | 商業／管理視角，每季一份 |
| `git log` | 完整技術 commit 紀錄，工程師查 bug／追蹤改動用 |
| `docs/md/` | 系統設計、規格、操作手冊等技術文件 |
| `docs/todo/` | 待辦事項與進行中工程細節 |
