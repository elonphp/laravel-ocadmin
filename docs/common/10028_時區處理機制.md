# 時區處理機制

> 建立日期：2026-07

全站時間欄位的**儲存**與**顯示**慣例。核心原則：**選定一個儲存基準時區、一律以它儲存；顯示時才依使用者時區換算。**

本範本（ocadmin）及衍生專案（多為台灣接案）**建議儲存基準採台北時間**，理由見 §二。

## 一、一句話規範（快速參考）

> **存台北、台灣直接顯示、跨國才換算。** `app.timezone` 設成儲存基準（台灣專案建議 `Asia/Taipei`）；時間欄型別沿用 Laravel 慣例——`xxx_at` 事件欄用 **`timestamp`**（靠**連線固定 +08:00** 保跨環境一致·§四），可能 <1970 或 >2106 的日期（生日等）用 **`date`/`datetime`**；顯示時只有**跨國使用者**才依 `users.timezone` 換算。

| 層 | 設定（檔案） | 效果 |
|---|---|---|
| `app.timezone`（`config/app.php`） | `Asia/Taipei`（＝UTC+8） | Eloquent 讀寫 DB、`now()` 皆以台北 |
| 時間欄型別 | `_at` 用 `timestamp`；寬範圍日期用 `date`/`datetime` | 見 §五 |
| 連線時區（`config/database.php`） | `timestamp` 欄靠連線固定 `+08:00` | 跨環境一致（§四） |
| 顯示 | 台灣直接用 stored 值；跨國依 `users.timezone` | 只在跨國情境換算 |

（三個設定檔各自的角色見 §三。）

## 二、建議設定與理由（台灣為主）

**建議（因開發人員與主要使用者都在台灣）：`app.timezone` 設成 `Asia/Taipei`（＝ +8）。**

- **這樣時間欄存進 DB 的就是台北時區（+8）的時間**；台灣使用者的顯示＝直接用 stored 值、**免換算**（99% 情境）。
- **顯示時可再依 `users.timezone` 做變化**：跨國使用者在顯示層把「台北 → 該用戶時區」換算即可，儲存不動。

**為什麼可以存本地時間、不強制 UTC**：教科書「一律存 UTC」主要是為了 **DST（日光節約時間）安全**與全球規模。**台灣自 1979 起無 DST** → 存本地時間**沒有「牆鐘時間重複/跳過」的經典風險**，那個最強反對理由在台灣不成立。對「開發者＋主要使用者都在台灣」的專案，存台北**最省事、最不過度設計**。

> **代價（誠實記錄）**：放棄「儲存＝宇宙絕對瞬間」。stored 值的意義＝台北時間（如同 UTC 也靠約定，只是基準改台北）。與外部 API/金流（常用 UTC）的邊界、深度跨國整合時，需記得「基準是台北」再換算。
>
> **例外**：若某衍生專案的**主要使用者非台灣 / 需真正全球化**，可改採「存 UTC」（`app.timezone=UTC`）——原則完全相同（存基準、顯示換算），只是基準時區換成 UTC。本文機制（連線固定、欄型原則、三環境對照）兩種基準都適用。

## 三、三個設定檔的作用（先搞懂旋鈕）

時區牽涉**三個檔**，各管不同層。**先分清楚它們，後面才不會亂**：

| 檔 | 進版控？ | 角色 | 時區相關設定 |
|---|---|---|---|
| **`.env`** | ❌ 否（gitignore·每環境各一份） | 放**環境變數**；config 檔透過 `env('KEY', 預設)` 讀它 | `APP_TIMEZONE=Asia/Taipei`（給 app.php 讀·可覆寫） |
| **`config/app.php`** | ✅ 是 | **Laravel/PHP 的時區**（＝`app.timezone`）：決定 `now()` 回什麼、Eloquent 把時間欄當成哪個時區。**這是「儲存基準」** | `'timezone' => env('APP_TIMEZONE', 'Asia/Taipei')` |
| **`config/database.php`** | ✅ 是 | **資料庫連線的 session 時區**：連線時送給 MySQL 的 `SET time_zone`。**這是「連線固定 +08:00」**，讓 `timestamp` 欄跨環境一致 | mysql `'timezone' => '+08:00'` |

### 關係流向

```
.env  APP_TIMEZONE=Asia/Taipei
   │ 被讀取
   ▼
config/app.php  'timezone' => env('APP_TIMEZONE', 'Asia/Taipei')
   │ 成為
   ▼
config('app.timezone') = Asia/Taipei   ← PHP/Laravel/Eloquent 的時區（now()、時間欄解讀）

config/database.php  mysql 'timezone' => '+08:00'
   │ 連線時送出
   ▼
MySQL 連線 SET time_zone='+08:00'       ← 只影響 timestamp 欄的換算
```

### 為什麼有**兩個** timezone 設定（最容易混淆處）

`app.php` 和 `database.php` 各有一個 `timezone`，**方向都是 +8，但作用在不同層、管不同東西、連值的格式都不同**：

| | `config/app.php` 的 timezone | `config/database.php` 的 timezone |
|---|---|---|
| 管誰 | **PHP/Laravel 端**（`now()`、Eloquent、時間欄解讀） | **MySQL 連線端**（`timestamp` 欄的換算） |
| 影響哪種欄 | 影響**所有**時間欄「怎麼被 Laravel 認定」 | **只**影響 `timestamp` 型欄（`date`/`datetime` 免疫、不受它管） |
| 值的格式 | **`Asia/Taipei`**（PHP 時區**名**·**不能**填 `+08:00`） | **`+08:00`**（MySQL 數字偏移·不用具名·免依賴時區表） |
| 為何需要 | 定「我們的時間是台北」 | 讓 `timestamp` 欄在不同伺服器時區上**一致**（§四） |

> ⚠️ **`app.timezone` 需填合法 PHP 時區名（`Asia/Taipei`）**，不可填 `+08:00`（那不是合法 PHP 時區識別字）；數字偏移 `+08:00` 只用於 DB 連線設定。兩者格式不同、別填反。

## 四、⚠️ 連線時區固定 `+08:00` 是故意的·勿刪

> ### 🚨 給未來維護者：不要以為這是設定錯誤而刪掉它
>
> `config/database.php` 的 mysql 連線會有：
> ```php
> 'timezone' => '+08:00',   // 見 docs/common/10028 §四·請勿刪除
> ```
> 意思是**把資料庫連線的 session 時區固定成 +08:00**（不論伺服器本身是什麼時區都強制蓋成 +8）。**不是筆誤、不是多餘，是刻意為之。**
>
> **⚠️ 本站所有 `xxx_at` 欄都是 `timestamp`（見 §五），它們的正確性「全押在這行」**——所以這行比什麼都重要。
>
> **常見誤解**：「`timestamp` 不是與時區無關嗎？何必固定？刪掉吧。」
> **➡ 錯。** MySQL/MariaDB 的 **`timestamp` 欄會依「連線 session 時區」換算**（寫入時 tz→UTC、讀出時 UTC→tz），**不是**與環境無關的。
>
> **為何要固定**：本站**刻意以台北時間儲存**（`app.timezone=Asia/Taipei`）。而伺服器 session 時區**各環境可能不同**（例：本地機器 `Asia/Taipei`、遠端 Ubuntu OS 為 `UTC`）。若不固定，session=UTC 的環境會把 Laravel 寫入的台北字串**當成 UTC 解讀** → 所有 `timestamp` 欄（`created_at`/`updated_at`…）**偏移 8 小時**、且**與其他環境不一致**（dump/搬遷、跨環境比對出錯）。
>
> **固定為 `+08:00` 的作用**：強制 Laravel 連線 session 一律 +08:00（覆蓋伺服器設定），讓 `timestamp` 欄的解讀與 `app.timezone` **對齊、且所有環境一致**。
>
> **結論**：**刪掉這行 → session 非 +8 的環境其所有 `_at` 欄會錯 8 小時。這行是正確性保證，不是可有可無。**

（`date`/`datetime` 欄**不受此影響**——它們不換算；連線固定純粹是為了 `timestamp` 型別的欄位。用數字 `+08:00` 而非具名，免依賴 MySQL 時區表；台灣無 DST，永遠 +8。）

## 五、欄位型別原則：`_at` 用 `timestamp`、寬範圍日期用 `date`/`datetime`

**以 `timestamp` 為時間欄預設**（沿用 Laravel 慣例、風格一致）；只有存不進 timestamp 範圍的日期才改 `date`/`datetime`。

| 欄位性質 | 型別 | 理由 |
|---|---|---|
| **`xxx_at` 事件欄**（`created_at`/`updated_at`/`published_at`/`deleted_at`/`email_verified_at`…） | **`timestamp`** | Laravel 慣例、風格一致；是「近期發生的事件」，**永遠 ≥1970、≪2106**，落在 timestamp 範圍內。**靠連線固定 +08:00（§四）＋app.tz 保正確、跨環境一致。** |
| **任意/寬範圍日期**（生日、歷史日期、遠期排程） | **`date`（純日期）或 `datetime`** | 可能 **<1970 或 >2106**，`timestamp` 存不下（如生日 1950 年）→ 只能用 date/datetime；且它們天生免疫伺服器時區 |

**為何 `timestamp` 對 `_at` 夠用：**
1. **連線固定已補上**：`timestamp` 唯一的坑是「不同伺服器時區不一致」，由 §四 的 `+08:00` 固定解掉（PHP `now()`＝MySQL `NOW()`·無 skew）。
2. **MariaDB 到 2106**（見 §八），遠超規劃視野。
3. **`_at` 是近期事件**：永遠落在 1970–2106，碰不到邊界。

**`timestamp` vs `date`/`datetime` 對照：**

| | `timestamp` | `date` / `datetime` |
|---|---|---|
| MySQL 時區換算 | **會**（依 session 時區·故需 §四 連線固定） | **不換算**（存什麼讀什麼·免疫伺服器時區） |
| 年份範圍 | 1970–2038（MySQL）／1970–**2106**（MariaDB） | date/datetime：1000–9999 |
| 容量 | 4 bytes | date 3B / datetime 5B |
| 適用 | 近期事件 `_at` | 生日、歷史、遠期、需跨工具字面一致者 |

> **取捨誠實記錄**：全站 `_at` 用 timestamp ＝ 正確性**全押在連線固定（§四）**；若那行被刪，所有 `_at` 在非 +8 環境會錯（date/datetime 版才自帶免疫）。已用**大聲的「勿刪」警告**擋這風險。另：遠端 DB 工具直接查 `timestamp` 欄會顯示伺服器時區（純 ops 顯示、Laravel 一律正確，見 §七）。

## 六、時間值怎麼流動

以 `_at` 欄（`timestamp`·基準台北）為例（有連線固定＋app.tz=台北）。

**台灣使用者（無 `users.timezone`）——全程零換算**
```
輸入 16:14(台北) ──存──▶ DB timestamp 欄（內部存 UTC 08:14·session+8 換算）
                              │ 讀出(session+8→台北, app.tz=Asia/Taipei)
                              ▼
                         顯示 16:14(台北)   ← 免換算
```
> `timestamp` 內部是 UTC 08:14（MySQL 依 session 換算），但寫入/讀出都經 +8 抵消 → Laravel 端一律看到台北 16:14。這正是為何**連線固定不可少**（§四）。

**跨國使用者（`users.timezone` 有值·例東京 +9）**
- 顯示：`$dt->setTimezone($user->timezone)` → 台北 16:14 → 東京 17:14。
- 輸入：以該用戶時區解讀 → 轉基準再存（`Carbon::parse($input, $user->timezone)->setTimezone('Asia/Taipei')`）。

→ 換算只在「跨國使用者的輸入/顯示」兩邊界發生；台灣情境完全免換算。

## 七、三種環境組合對照（含 pin 後殘留效應）

前提：`app.timezone=Asia/Taipei`、`_at` 欄用 `timestamp`。差異只在**伺服器 `default-time-zone`**（`date`/`datetime` 欄不換算、三情況都一致，不在此列）。

### 7-1　**不設**連線固定時（為何需要固定·動機）

| 情況（本地／遠端 `default-time-zone`） | `timestamp` 欄（所有 `_at`·**不設**固定時） | 連線固定 |
|---|---|---|
| **1. 本地 +8 / 遠端 +0** | 本地正確、**遠端 −8 偏移** → **兩環境不一致** ❌·dump 會漂 | **必須** |
| **2. 本地 +8 / 遠端 +8** | 兩環境都正確一致 ✅（伺服器本就＝app.tz） | 非必須·**建議防禦性設** |
| **3. 本地 +0 / 遠端 +0** | 兩環境**彼此一致**，但內部有「台北被當 UTC」的 **+8 skew**（Laravel 顯示仍對·但真 UTC 值錯、與外部 UTC/工具對不上、日後改 session 會漂） | **建議**（去 skew） |

→ 說明**為何一律固定**：情況 1 不固定就壞、情況 3 埋隱患、情況 2 僥倖沒事。

### 7-2　**設**連線固定 `+08:00` 之後（＝建議做法·殘留效應）

**一旦連線固定 +08:00，伺服器 `default-time-zone` 就再也影響不到 Laravel。** 它只剩一個殘留作用——「用 DB 工具直接查 `timestamp` 欄時，看到什麼時區」。

| 情況（本地／遠端 `default-time-zone`） | Laravel 行為（所有 `_at`） | DB 工具查 `timestamp` 欄 |
|---|---|---|
| **1. 本地 +8 / 遠端 +0** | **完全一致·正確** ✅ | 本地→台北、遠端→UTC |
| **2. 本地 +8 / 遠端 +8** | **完全一致·正確** ✅ | 兩邊→台北 |
| **3. 本地 +0 / 遠端 +0** | **完全一致·正確** ✅ | 兩邊→UTC |

**三句結論：**
1. **Laravel 端**：三情況**完全相同**（固定蓋掉 default-time-zone）。程式行為與 default-time-zone **無關**。
2. **唯一殘留差異**：DB 工具**直接查 `timestamp` 欄**的顯示時區，跟著各機器 `default-time-zone`。**純顯示、只在用工具直查時**——**不影響任何程式正確性**。
3. **所以固定之後，你基本可以無視 `default-time-zone`**：它剩下的唯一影響是「工具直查 `_at` 看到台北 vs UTC」。

**結論：一律設連線固定 `+08:00` ＝ 一勞永逸**，三情況行為一致、不必分類討論。

## 八、2038 vs 2106（為何 timestamp 夠用）

`timestamp` 的年份上限**在 MariaDB 已解、MySQL 未解**（2026 查證）：

- **MariaDB 11.5+（MDEV-32188）**：TIMESTAMP 上限 `2038-01-19` → **`2106-02-07 06:28:15 UTC`**（無號 32-bit·格式不變仍 4 bytes·限 64-bit 平台）。→ MariaDB 下 `_at` 欄安全到 2106。
- **MySQL（Oracle）**：截至 2026 **仍卡 2038**。**若專案用 MySQL**，`_at` 上限退回 2038，屆時再評估改 datetime；MariaDB 下無此問題。
- **寬範圍日期**（生日等）本就用 `date`/`datetime`（§五），到 9999 年、且能存 <1970，不受此限。

> 參考：MariaDB MDEV-32188、11.5 release notes；MySQL Bug #119944（未實作）。

## 九、實作鐵律

1. **一律以基準時區儲存**（台灣專案＝台北）。取「現在」用 PHP `now()`（依 `app.timezone`）；不用 MySQL `NOW()`。
2. **時間欄型別**：`xxx_at` 事件欄用 **`timestamp`**（Laravel 慣例）；可能 <1970 或 >2106 的日期用 **`date`/`datetime`**。
3. **務必保留 `config/database.php` 連線固定 `+08:00`**（§四）——所有 `_at` 的正確性靠它；該行加註解指向本文件。
4. **顯示**：台灣直接用 stored 值；跨國才 `$dt->setTimezone($user->timezone)`。跨國輸入則「該用戶時區 → 轉基準 → 存」。
5. **連線固定用數字 `+08:00`**，不用具名（免依賴 MySQL 時區表）。`app.timezone` 則填 PHP 時區名 `Asia/Taipei`（別填反）。
6. **共用 DB 一致性**：若多專案共用同一 MySQL 實例（如共用 sysdata），**全體須採同一基準時區**，避免共用表時間值混雜。
