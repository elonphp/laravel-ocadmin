# 開發協作流程

涵蓋分支策略、commit 訊息、push 規則、解衝突、CI 機制等日常工程實務約定。本文件為 Ocadmin 系列（範本與各衍生版本）共用約定，各衍生專案在自家 `docs/md/` 補充環境特有設定即可。

> 本文件**不**規範架構設計、API 設計、Code Review 細節（那是另一個層級），純粹聚焦在「日常 Git 與 CI 操作」。

## 分支策略

### 目前階段：直接推 main + feature branch

- **main**：受保護的主分支，禁 force push（見下方〈Push 規則〉）
- **feature/*** / **hotfix/***：個人開發分支，可 force push 隨意（其他前綴見下方〈分支命名慣例〉）
- 共用分支（main、release/*）一律不允許 force push

> **本文件的適用情境**：Ocadmin 系列各衍生專案的實際開發規模差異很大 —— 有的是一個工程師獨自負責一整個專案，有的是兩人以上共用同一份 codebase。本文件因此**同時涵蓋兩種情境**：通用規則先寫一次，差異處用 **[單人]** / **[協作]** 標註。讀的時候對照自己當下的情境取用，不要把不適用的那條當成不存在。
>
> 即使是單人作業也建議遵守協作向的最低限規範（例如 main 鎖 force push、commit 訊息規範），原因有二：(a) 哪天有人加入時不需要重學；(b) 未來自己維護時，過去的歷史對「未來的自己」就是別人。
>
> **範本/文件型專案的豁免**：純文件或純範本性質的專案，無業務 code、無部署目標時，可豁免 CI、staging 分支等與「驗證業務正確性 / 區分發布狀態」相關的規範。Branch Protection、commit / branch 命名等與 git 歷史品質相關的規範**不**豁免。
>
> **ocadmin 即為此例**：本範本專案不啟用 GitHub Actions CI、不使用 staging 分支，但 main 仍鎖 force push、commit / branch 命名照本文件規範。衍生專案有實際業務 code 與部署目標時，依本文件全套執行，**不**享豁免。

### 分支命名慣例

| 前綴 | 用途 | 目前使用 | 範例 |
|---|---|---|---|
| `feature/` | 新功能 | ✅ | `feature/leave-approval`、`feature/payroll-export` |
| `hotfix/` | 急修（含發現的舊 bug 需要插隊處理） | ✅ | `hotfix/login-loop` |
| `fix/` | 一般 bug 修正 | ⏸ 暫不使用 | `fix/annual-leave-calculation` |
| `upgrade/` | 版本升級 | ⏸ 暫不使用 | `upgrade/laravel-13`、`upgrade/php-85` |
| `refactor/` | 重構（不改行為） | ⏸ 暫不使用 | `refactor/extract-leave-service` |

**建議實務**：

- **[單人]** 只用 `feature/` + `hotfix/` 兩種就夠
  - `feature/` 涵蓋所有「新做的東西」，包含一般 bug fix、小重構
  - `hotfix/` 留給「需要插隊、不能等目前手上 feature 做完」的情境
  - 自己一個人時，多開分支類別只是裝飾，徒增記憶負擔
- **[協作]** 可額外啟用 `fix/` 區分「修 bug」與「做新功能」
  - 兩人以上時，一眼從 `git branch -r` 看出對方在修 bug 還是做新功能，對 review 順序、避免衝突有實質幫助
  - `upgrade/` `refactor/` 仍是「等真的有需要再啟用」的預留前綴 —— 例如 CI 想對 `upgrade/*` 跑額外的相容性測試

**不論用哪個前綴，急修流程都一樣**：從 main 開新分支（**不要**在現有 feature branch 裡順手修，會卡住急修上線）→ 修完 merge 回 main → 切回原 feature branch 繼續。

分支用完（merge 進 main 後）就刪掉，避免 stale branches 累積。本地 `git branch -d <name>`、遠端 `git push origin --delete <name>`。

### 未來：PR-based 流程 [協作]

當團隊規模 / 系統重要性升高，切換到：
- 任何改動進 main 必須透過 PR
- PR 需 CI 通過才能 merge
- 至少一位 reviewer approve
- merge 完自動刪除 source branch（GitHub repo settings 可設）

**[單人]** 情境通常不需要走 PR-based —— 自己 review 自己的 PR 多半流於形式。但若想練習為未來協作鋪路，或想用 PR 介面看 diff 較直觀，自願採用也沒壞處。

### 變體：個人分支 + staging + main 部署模型 [協作]

當衍生專案的 **main 與 production 直接綁定**（push 即觸發部署，例如 Plesk webhook），且採兩位以上開發者 per-developer WIP 分支模式，用本變體**取代**上面的 `feature/* → main` 流程。

> 本變體只是個樣板，衍生專案可以照搬，也可以挑部分採用（例如只用 staging 整合層、不用 `git-main.bat` 自動化）。後段的腳本與 rollback 機制是參考實作，命名 / remote name / 部署目標細節依各衍生專案實際情況調整。

#### 分支用途

三層分支結構（以兩位開發者 `john`、`peter` 為例 —— 各自建同名分支做本地開發）：

| 分支 | 角色 | force push | 誰能動 |
|---|---|---|---|
| `main` | **production 部署目標**（webhook 監聽，一變就部署） | 禁（`git-main.bat` / rollback 例外） | `git-main.bat` 唯一 |
| `staging` | **整合線** — 雙方 ready 的 commit merge 進來，部署來源 | 允許（建議 `--force-with-lease`） | 雙方 merge / amend |
| `john` | **John 個人 WIP** | 自由 | 只有 John |
| `peter` | **Peter 個人 WIP** | 自由 | 只有 Peter |
| `old-main` | `git-main.bat` 自動建立的 main 遞增備份（每次 deploy 多一個 merge 節點，永不丟資料；單步 + 多步 rollback 用） | 自動 | `git-main.bat` |
| `feature/xxx` | （可選）超大功能再開額外的 sub-branch | 自由 | 開的人 |

> **為什麼用 per-dev 分支？** 兩位開發者各自隨意 commit / rebase / amend / force push 都不會打擾對方，等 ready 才整合到 staging。
>
> **Branch 名 = GitHub username** — 一眼就知道是誰的 WIP，不用問。

#### 為什麼「amend 已 push 的個人分支」是安全的（hash 推理）

一般鐵律「已 push 的 commit 不要 amend」是為**共享分支**設的（別人可能已基於舊 commit 接東西）。**個人 WIP 分支不受此限**——只要該分支真的只有你在動、且無他人推送，**已 push 也可自由 amend / rebase + force**。原理：

- commit hash 是**內容定址**的 SHA：由 tree（檔案快照）＋parent(s)＋author/committer/message/timestamp 一起算出。因此 **同 hash ⟺ 同一顆 commit＝同內容、同歷史**；反之 amend 一定換 hash（就算 `--no-edit`、檔案沒動，committer timestamp 也變）。
- 個人分支只有你動：**遠端 branch tip 的 hash 若＝你上次推的那顆**（沒有他人 commit 疊上去），代表遠端就是你推的、沒被動過 → amend 後覆寫是安全的。
- `--force-with-lease` 把這件事**機器化驗證**：push 前先 fetch，若遠端 tip ≠ 你的 remote-tracking ref（有人動過）就**拒推**，相等才推。故 `git-staging.bat` 一律用 `--force-with-lease`（非裸 `--force`）。
- **前提：該分支真的只有你**。共享分支即使當下 hash 相符，隊友仍可能已 `pull` 過、在他本地接了你看不到的東西 → 這條豁免**不適用**，回到「不 amend 已 push」鐵律。

> 反過來說：`--force-with-lease` 失敗（拒推）就是在告訴你「遠端 tip 已不是你以為的那顆」——通常代表有他人推送或你在別台機器動過，這時**先 fetch 檢視**再決定，別直接改用裸 `--force` 硬蓋。

#### 環境對應

| 分支 | 環境 | 部署方式 |
|---|---|---|
| `main` | **production**（正式區網域） | `git-main.bat` → webhook 自動拉取 |
| `staging` | **測試區**（測試區網域） | **手動**部署（衍生專案在自家 `docs/md/` 補上細節） |
| `john` / `peter` | 本機 | `php artisan serve` |

#### ⚠ 不要直接 push 到 main

`main` 由 `git-main.bat` **唯一**控制 — 跑一次就把當下的 staging force-push 過去。**直接 push 到 main 的 commit 會被下次 deploy 蓋掉**（雖然有 `old-main` 備份，但這是設計外的操作）。

#### 日常流程

**檔案摘要**
git-staging.example.bat, git-main.example.bat 這兩個檔案要提交。
git-staging.bat, git-main.bat 這兩個檔案不提交，可指定分支名稱。

**情境 1：日常開發**

```bash
git switch john                   # 切到自己的 WIP branch
git pull                          # 同步遠端（如果你在另一台機器也用這個 branch）
# 改 code、commit、可以盡情 amend / rebase / squash
git push origin john              # 必要時加 --force-with-lease
```

**情境 2：WIP 完成、要同步到 staging（一天多次都可，跟 deploy 分開）**

頻繁的同步流程封裝成 `git-staging.bat` / `git-staging.sh`，一鍵搞定 fetch + merge + push。

*首次設定（per-developer）：*

`git-staging.bat` / `.sh` / `git-main.bat` / `.sh` 採「example 模板 + 個人副本」模式 —— **模板入 git，個人副本 gitignored**：

```cmd
copy git-staging.example.bat git-staging.bat   :: Windows
cp git-staging.example.sh git-staging.sh       # Linux/Mac/WSL
cp git-main.example.sh git-main.sh
chmod +x git-staging.sh git-main.sh            # 首次需賦予執行權限
```

打開 `git-staging.bat` / `.sh`，把開頭的 `MY_BRANCH=YOUR_BRANCH_HERE` 改成你自己的個人 branch（如 `john` / `peter`）。`git-main.*` 沒有 MY_BRANCH，純粹複製即可（要客製也行，已 gitignored）。

> **為什麼明碼指定而非偵測 HEAD？**
> 偵測 HEAD 容易被「不小心切到別的 branch」誤觸發 —— 例如你在 `experiment` 分支上跑 `git-staging.bat`，HEAD-detect 模式會把 experiment 推到 staging。明碼 `MY_BRANCH=john` + 驗證 `HEAD == MY_BRANCH` 才能擋下這種狀況。

*跑同步：*

```cmd
git-staging.bat          ::（Windows）
```

```bash
./git-staging.sh         # （Linux/Mac/WSL）
```

`git-staging.bat` / `.sh` 邏輯：
1. **驗證當前 branch == `MY_BRANCH`** —— 用 `git rev-parse --abbrev-ref HEAD` 抓 `CURRENT_BRANCH`，跟腳本開頭寫死的 `MY_BRANCH` 比對。**不相等時印錯誤訊息 + `exit /b 1` 立即結束 bat**（後面所有 fetch / merge / push 全部不會執行）
2. `git fetch origin`
3. `git merge origin/staging`（衝突自己解，解完 commit 後重跑）
4. `git push origin $MY_BRANCH --force-with-lease`（允許 amend 後）
5. `git push origin $MY_BRANCH:refs/heads/staging`（FF push，不需 force —— 因 step 3 已把遠端 staging merge 進來）

> **為什麼不檢查 working tree 乾淨？** merge / push 只動 committed 內容；uncommitted 改動留在工作區不會被推到 staging（push 只看 ref，working tree 無關），有真衝突時 `git merge` 自己會 refuse。允許「寫一半時把已 commit 的部分同步到 staging」是刻意的工作流選擇。

實際 step 1 的 bat 邏輯：

```bat
for /f %%i in ('git rev-parse --abbrev-ref HEAD') do set CURRENT_BRANCH=%%i

if not "%CURRENT_BRANCH%"=="%MY_BRANCH%" (
    echo ERROR: expected to be on %MY_BRANCH%, currently on %CURRENT_BRANCH%.
    echo Switch back with: git switch %MY_BRANCH%
    exit /b 1
)
```

舉例：`MY_BRANCH=john`、你不小心 `git switch experiment` 後跑 `git-staging.bat`：

```
ERROR: expected to be on john, currently on experiment.
Switch back with: git switch john
```

bat 隨即結束（errorlevel=1），**沒有任何 git 操作被執行**。修正方式照訊息提示：`git switch john` 後重跑即可。

*多人共開的安全鏈：*

```
Peter 在 peter 分支 commit X、Y → git-staging → 遠端 staging 含 X、Y

John 跑 git-staging.bat（MY_BRANCH=john）：
  step 2. fetch origin（拿到 staging 含 X、Y）
  step 3. merge origin/staging 進 john
          → john 變「A、B、C、merge(X、Y)」
  step 4. push john → origin/john ✓
  step 5. FF push john → refs/heads/staging
          → staging 含「過去 + X、Y + A、B、C + merge」✓
```

關鍵：step 3 已把 Peter 的工作 merge 進 John 的分支，所以 step 5 的 FF 一定成立、**絕不會把 X、Y 覆蓋掉**。**沒有 `--force` 模式**（刻意設計，多人開發下沒有 100% 安全的 force push）。

到這裡遠端 staging 已含你的改動。**sync 動作不會觸發部署**，要部署到 production 才跑 `git-main.bat`。

> **為什麼 sync 跟 deploy 分開？**
> - sync：頻繁動作（一兩天多次），把段落性工作整合進 staging 讓同事可以 pull
> - deploy：嚴謹動作（幾天一次），把累積的 staging 推到 production；前置檢查、old-main 遞增備份齊全
>
> **為什麼在自己分支解衝突？**
> - 解失敗可以 `git reset --hard origin/john` 重來，不污染 staging
> - 不切 branch、保持 working tree 不變動
> - 整個 deploy 流程也不依賴本地 staging 分支（用 `origin/staging` ref）

手動操作（不想用 git-staging.bat 時）：

```bash
git fetch origin
git merge origin/staging
# 解衝突 + commit
git push origin john --force-with-lease
git push origin john:refs/heads/staging
```

**情境 3：超大功能、想再分一層 sub-branch**

```bash
# 從自己的 john 開出 feature/
git switch john
git switch -c feature/payroll-export
# 開發
git push -u origin feature/payroll-export

# 完成後 merge 回自己的 john（不直接進 staging）
git switch john
git merge --no-ff feature/payroll-export
git push origin john
git branch -d feature/payroll-export
git push origin --delete feature/payroll-export
```

> 大多數情況直接在 `john` 上做就好，sub-branch 是想隔離高風險變更時才開。

#### 部署到 production

```cmd
git-main.bat        ::（Windows）把當下的 staging 推到 main，觸發 production 部署
clear.bat           ::（Windows）清 framework caches（route/config/view）
```

```bash
chmod +x git-main.sh && ./git-main.sh   # （Linux/Mac/WSL）
```

`git-main.bat` 邏輯（**所有 ref 都用遠端 ref，不依賴本地 staging 分支**）：
1. fetch origin
   - **前置檢查**：若 `origin/main` 已等於 `origin/staging` → 無新 commit，中止部署
2. 備份：`old-main` 遞增合併
   - 第一次（遠端尚無 `old-main`）：直接以 `origin/main` bootstrap
   - 後續：建 merge commit（parents = 既有 old-main + 即將被取代的 main，tree = main）、FF push 到 `old-main`
3. force-push `origin/staging` → `origin/main`（觸發 webhook 部署）

> 因為 deploy 直接用「fetch 後的遠端 staging」推到遠端 main，**本地 staging 分支從此可有可無**，不論你身在哪個 branch、本地 staging 是否最新都不影響部署正確性。

> **amend → 重新 deploy 的處理**：amend 會產生新 SHA（即使 `--amend --no-edit`，committer 時間戳變了 SHA 也變），所以 amend 後 `staging` 跟 `main` 的 SHA 不同，前置檢查不會擋下，old-main 遞增備份每次都建獨立 merge commit 不會衝突 —— 這是本機制設計時就支援的合理情境。

**Rollback：**

```bash
# 單步 rollback（回上一版）
git push origin old-main^2:refs/heads/main --force

# 多步 rollback（回到任意歷史 deploy）
git fetch origin
git log origin/old-main --merges --first-parent --oneline   # 列出歷次 deploy 備份節點
# 挑目標 merge commit 的 ^2 = 該次 deploy 前的 main
git push origin <target>^2:refs/heads/main --force
```

> **`old-main` 的設計**：每次 deploy 建一個 merge commit（first parent = 既有 old-main，second parent = 被取代的 main，tree = 被取代的 main），永遠累積、永不覆寫。`old-main` HEAD 是最新 merge commit，HEAD^2 指向上一版 main（單步 rollback 目標）；歷次 deploy 沿 `--first-parent` chain 可一路回溯，多步 rollback 直接挑歷史節點。

**Linux 端清快取**（SSH 上 production / staging server，或在 WSL / Mac 開發）：

```bash
chmod +x clear.sh    # 首次需賦予執行權限
./clear.sh           # 內容對等 clear.bat：optimize:clear + cache:clear
```

PHP 不在 PATH 時用環境變數覆寫（如 Plesk）：

```bash
PHP=/opt/plesk/php/8.5/bin/php ./clear.sh
```

**部署前確認**：
- staging 上沒有半成品 commit
- CI 綠燈
- 本機跑過、確認沒問題
- 對方的個人 branch 已經 merge 進 staging 的部分也是 OK 的（口頭確認或看 `git log staging`）
- **建議先部署到測試區驗證後再 deploy 到 production**

#### 部署到測試區

staging branch 對應測試環境，**手動**部署。具體部署機制（手動拉取的伺服器路徑、cache 清理、是否 webhook、Plesk 配置等）由衍生專案在自家 `docs/md/` 補充。

通常流程：把 staging 的最新內容部到測試區 → 在測試區跑過、確認 OK → 才跑 `git-main.bat` 升 production。

#### 兩位開發者協作要點

- **個人 branch 完全自由** — 在自己的 `john` / `peter` 上 force push、rebase、amend 都不會影響對方
- **整合到 staging 前先同步** — `git-staging.bat` 內建先 fetch + merge `origin/staging`，把對方推上 staging 的吃進來，再把自己的推上去；不需要本地 staging 分支
- **部署前口頭確認** — 跑 `git-main.bat` 前知會對方一聲，避免 staging 上有對方還在測試的東西被推上線

## Pull / Merge 流程

### 拉取遠端變更

預設用 `git pull`（= `pull --merge`）。Laravel 專案的 `composer.lock` 跟 migration 檔案順序常導致 rebase 出狀況，merge 比較直觀。

**全域偏好設定**（建議）：

```bash
git config --global pull.rebase false   # 預設用 merge
```

### 解衝突常見情境

1. **`composer.lock` 衝突**：取一邊（通常取 origin）→ 跑 `composer update --lock` 重新對齊。不要手動編輯 lock 檔。
2. **`composer.json` 衝突**：手動 merge 兩邊的 require / require-dev 段，再跑 `composer update --lock`。
3. **Migration 編號衝突 [協作]**（兩人同時加 migration）：把較晚的 migration 重命名（時間戳調後），跑 `migrate:fresh --seed` 確認沒問題。
4. **語言檔衝突 [協作]**：兩邊都加 → 兩邊都保留，按 key 排序。

> **[單人]** 後兩項極少遇到 —— 自己一個人不會跟自己搶 migration 編號或 lang key。但仍可能因「在多台電腦同時開發 + 各自 commit」誤撞，遇到時處理方式相同。

### Merge commit 該保留還是 rebase

- 共用分支（main）merge feature branch 進來：**保留 merge commit**，看得出脈絡
- 個人 feature branch 同步 main：可 rebase（保持分支線性），可 merge（保留時序）

> **[單人]** 如果 feature branch 短命（一天內 merge 回 main），用 `--no-ff` 也只是多一筆 merge commit、價值不高。直接 fast-forward merge 即可；要區分「這段是某 feature」靠 commit message 就夠。
> **[協作]** 偏好 `--no-ff`（即「保留 merge commit」），git 歷史能清楚看到 feature 的開始與合併點，做 review 或追問題時較直觀。

## Commit 訊息規範

### 不用 `feat:` / `fix:` 前綴

理由：
- 不接 semantic-release 自動版本號（內部系統不需要版本號）
- 業務面 changelog 走另一套機制（見 `00009_Changelog撰寫機制.md`）
- 前綴實際上常被誤用（一律寫 `feat:`，分類訊號失效）

### 寫法

動詞開頭，講做了什麼，細節塞括號或分號後：

```
舊：feat: 修正年假計算錯誤（特休年資未含到職當月）
新：修正年假計算錯誤（特休年資未含到職當月）

舊：feat:1.新增留職停薪跟離職規則2/員工緊急連絡人3.移除預設時間
新：新增留職停薪／離職規則、員工緊急聯絡人欄位；移除預設時間
```

### 顆粒度建議

| 情境 | 建議 |
|---|---|
| 單一邏輯改動（一個 bug fix、一個新功能） | 一個 commit |
| 大型功能含多個子功能 | 拆多 commit，每個都能單獨 revert |
| Refactor + 新功能混在一起 | **拆開**：先 refactor 一個 commit，再新功能一個 commit |
| 修 typo / rename | 單獨一個小 commit |

### 主題相近的小修改：優先 amend

新一輪改動若與**上一次 commit 主題相近、且變動檔案少**，優先 `git commit --amend` 合併到上一次提交，避免把連貫的工作切成一堆無意義的小 commit。

| 情境 | 建議 |
|---|---|
| 同一機制的微調 / 漏改 / typo | amend |
| 上一次 commit 漏掉的對應文件補充 | amend |
| 延續上一次 commit 範圍的後續修改（同一 PR scope） | amend |
| 已 push 的 commit | **不要** amend（重寫歷史風險，改開新 commit 修） |
| 跨主題的修改（內容已和上次 commit message 不符） | **不要** amend |
| 想保留決策時序脈絡的改動（如重要設計變動） | **不要** amend |

判斷不出時：開新 commit 比 amend 安全（多一筆訊息比丟訊息脈絡好回頭）。

### 訊息長度

- 第一行（subject）：50 字內描述「做了什麼」
- 必要時空一行寫 body：解釋「為什麼這樣做」（背景、權衡取捨）
- 別在 subject 重複檔名 / function 名（git diff 會顯示）

## Push 規則

### 已 push 的 commit 有小問題

**開新 commit 修**，不重寫歷史。多寫一筆 commit 比 force push 安全 100 倍。

### 還沒 push 的 commit 想改

直接 `--amend`，不需要 force：

```bash
git add <檔案>
git commit --amend --no-edit
git push  # 沒 --force，因為還沒 push 過
```

### 真的需要重寫已 push 的歷史

用 `--force-with-lease` 取代 `--force`：

```bash
git push --force-with-lease
```

差別：origin 有你不知道的新 commit 時，`--force-with-lease` 會拒絕並提醒先 pull，避免覆蓋同事工作。

> **[單人]** `--force-with-lease` 的「擋掉同事新 commit」價值不存在，但仍建議用，因為：(a) 在多台電腦間切換時，A 機 push 後 B 機可能不知道，這條保護一樣有效；(b) 養成習慣，未來加人時不需要重練。

**建議全域設定 alias 防手滑**：

```bash
git config --global alias.fpush 'push --force-with-lease'
```

之後要 force 都用 `git fpush`，連寫 `--force` 的機會都沒有。

### main 分支：GitHub Branch Protection 鎖死

repo Settings → Rules → Rulesets → New branch ruleset：

| 欄位 | 值 |
|---|---|
| Name | `Protect main` |
| Enforcement | Active |
| Target branches | Include `main` |
| Block force pushes | ✅ 勾選 |

設定後即使 repo 管理員自己也不能 force push main（這是好事，避免手滑）。

> 私有 repo + GitHub Free 也支援 Rulesets。

## CI（GitHub Actions）

### CI 對兩種情境的價值

- **[單人]**：每次 push 自動跑測試，抓出「明顯爛掉」的 commit；維持 main 綠燈作為「現在這份 code 至少能跑」的心理安全網。沒有 reviewer 時，CI 是你唯一的同儕。
- **[協作]**：上述 + 擋下同事 push 進 main 的爛 code（搭配 Branch Protection 的 required status check，CI 紅燈就無法 merge PR）。

兩種情境都建議從 Day 1 就接 CI ——「等專案大了再加」往往一拖就半年，而初期接的成本最低（測試少、設定簡單）。

### 觸發時機

- push 到 main → 跑一次
- 開 PR 進 main → 跑一次
- PR 上每次新 push → 重跑

### Workflow 檔案位置

`.github/workflows/ci.yml`

### 最小可行版本（範例）

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    name: PHP Tests
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.5'
          extensions: mbstring, intl, pdo_mysql, pdo_sqlite, zip, gd
          coverage: none
          tools: composer:v2

      - uses: actions/cache@v4
        with:
          path: vendor
          key: ${{ runner.os }}-php85-composer-${{ hashFiles('composer.lock') }}

      - run: cp .env.example .env
      - run: composer install --no-interaction --prefer-dist --no-progress
      - run: php artisan key:generate
      - run: php artisan test --no-ansi
```

PHP 版本、需要的 PHP 擴充、cache key 等實作細節依專案而定。

### Token 權限注意事項

修改 `.github/workflows/` 下的檔案時 push 會被擋下，除非用的 Personal Access Token 有 **`workflow`** scope。

修法：GitHub Settings → Developer settings → Personal access tokens → 編輯 token → 勾 `workflow` scope → Save。

### 免費方案額度

GitHub Free：私有 repo 每月 2000 分鐘 Linux runner。

實務上完全用不完：本級規模專案每月用量約 60-300 分鐘。

### CI 失敗的處理

CI 紅燈不要忽略：

1. 看 GitHub Actions 的 log 找錯（最右欄展開步驟即可）
2. 在本地重現問題後修
3. 修好後再 push（會自動觸發新一輪 CI）

CI 本身故障（如 GitHub 服務異常）：Actions tab → 失敗的 run → **Re-run failed jobs**。

## 常見工作流情境

### 情境 1：開發新功能

```bash
git checkout main
git pull
git checkout -b feature/new-payroll-rule

# ...寫 code、測試、commit ...

git push -u origin feature/new-payroll-rule
# 開 PR 或直接 merge 回 main（依當時策略）
```

### 情境 2：修正線上 bug

```bash
git checkout main
git pull
git checkout -b hotfix/login-error

# ...修正 + 加測試 ...

git push -u origin hotfix/login-error
# merge 進 main → CI 跑過 → 部署
```

### 情境 3：搞砸了想救回來

| 狀況 | 救法 |
|---|---|
| 剛 commit 但訊息打錯，還沒 push | `git commit --amend` 改訊息 |
| commit 了不該 commit 的檔案，還沒 push | `git reset --soft HEAD~1` 退回，重新 commit |
| 改壞了想退回上一個 commit 的狀態（捨棄目前所有改動） | `git reset --hard HEAD`（**所有未 commit 改動會消失**） |
| 找不到剛剛的 commit（reset / amend 後） | `git reflog` 找到 SHA → `git checkout <sha>` |

`git reflog` 會記錄你最近 90 天的所有 HEAD 移動，幾乎沒有「真的丟失」的 commit，遇到問題先別慌、先 reflog。

## 常用 git alias

放進 `~/.gitconfig` 的 `[alias]` 段，或執行 `git config --global alias.<name> '<command>'`：

```
[alias]
    co = checkout
    br = branch
    st = status
    sw = switch
    fpush = push --force-with-lease
    last = log -1 HEAD --stat
    unstage = reset HEAD --
    visual = log --oneline --graph --decorate --all
```

`git visual` 可以視覺化看分支關係，比 `git log` 直觀。
