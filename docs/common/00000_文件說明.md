# 文件說明

定義本專案（`ocadmin` 範本）與所有衍生具體系統（`projFoo` 等）的 `docs/` 目錄結構、檔案編號規則、git 納入策略。

本專案為 **LaravelOcadmin 基礎範例專案（`ocadmin`，開源版）**，是衍生具體系統的基準。本檔同時定義 ocadmin 自身與所有衍生專案的規範。

> **資料夾名 `projMain` vs 識別符 `ocadmin`**：本機資料夾名稱為 `D:\Codes\PHP\Laravel\LaravelOcadmin\projMain\`（早期叫 `branchMain`，已更名為 `projMain`）。文件層級的概念識別符用 `ocadmin` — 對齊 namespace `App\Portals\Ocadmin\` / config `portals.ocadmin` / env `OCADMIN_*` / portal name / role/permission prefix `admin`。引用本範本文件時路徑寫 `projMain\docs\...`（識別符與資料夾名兩者皆指同一範本層）。

## 一、docs 子目錄

```
docs/
├── common/              # ocadmin 設計文件（衍生專案對應 md/）
├── reference/           # 外部系統參考材料（如 OpenCart sql dump），僅供查閱比對
├── migrate/             # 舊系統 → 新系統 ETL 腳本（衍生視專案）
├── changelog/           # 季度更新摘要 YYYYQN.md（衍生視專案）
│                        # 機制詳 00009_Changelog撰寫機制.md
├── done/                # 已完成 todo 的歸檔處，保留工程過程紀錄（衍生視專案）
└── todo/                # 工作便條、設計討論稿（衍生視專案；部份入 git，詳 §四）
```

各子目錄目的、生命週期、蒸餾去向：

| 子目錄 | 必要性 | 目的 | 生命週期 | 蒸餾去向 |
|---|---|---|---|---|
| `common/`（ocadmin）／ `md/`（衍生） | ★ 必有 | 模組設計、業務規則、schema、決策（**source of truth**）| 永久；舊文件偶有修訂 | — |
| `reference/` | ✱ 視專案 | 外部系統參考材料（如 OpenCart sql dump），僅供查閱比對，**不被本系統載入或執行** | 永久 | — |
| `migrate/` | ✱ 衍生視專案 | 舊系統 → 新系統 ETL 腳本（一次性，上線 + 舊系統退役後完全不再需要）| 持續累積；上線後逐步退役 | — |
| `changelog/` | ✱ 衍生視專案 | 對外（管理層／跨部門）的業務導向季度摘要（機制詳 [`00009`](00009_Changelog撰寫機制.md)）| 每季新增一份，定稿後不大改 | — |
| `done/` | ✱ 衍生視專案 | 完成的大主題 todo，**有保留價值的工程過程紀錄**（phase 推進、設計討論、踩過的坑）| 永久歸檔 | — |
| `todo/` | ✱ 衍生視專案 | 工作便條：規劃稿、設計討論、進度筆記 | 各檔不同（見 §四）| 大主題 todo 完工後：規則蒸餾去 `md/` + 過程紀錄移到 `done/`（看哪個有保留價值），原檔刪除 |

`ocadmin` 為範本／文件型專案，無業務 code、無移植、無 changelog、無 todo（少量規劃直接寫進 `common/9xxx` 議題探討段）。通常只有 `common/` + `reference/`。

衍生專案依需求啟用其它子目錄；命名統一遵循上表（不要自創 `etl/` `archive/` 等同義名）。

### 各子目錄使用時機

**`common/`（ocadmin）／ `md/`（衍生）— 現況的設計規則**

模組業務規則、schema 設計取捨、跨模組整合方式、ACL 規範等系統當下的權威說明。讀者要知道系統現在怎麼運作，這裡是一站式參考。**不寫**純 implementation detail（讀 code 即知）、單次 bug fix、暫態的過渡描述。

開新檔的時機：新模組落地需要解釋業務規則、schema 設計做出非顯然的取捨、跨模組機制建立、現有規則發生變更。

**`reference/` — 外部系統參考材料**

外部系統的 sql dump / API 規格等，作為設計時對照查閱用，**不被本系統載入或執行**。例：OpenCart 4 sql dump 用來查 OpenCart 怎麼設計選單與設定（ocadmin 受其啟發）。**不放**本系統自己產出的東西、會被 Laravel migrate / seeder 引用的檔案（那屬 `database/`）。

**`migrate/` — 舊系統 → 新系統 ETL**

新系統取代舊系統的轉換期：每個 `migrate_*.sql` 對應一個邏輯模組，`migrate_all.sql` 用 `source` 串接保證執行順序。**一次性使用**：上線 + 舊系統退役後整個目錄可刪。**不放** Laravel migration（屬 `database/migrations/`）、上線後一次性的資料修補（記到 `todo/00000000_進度筆記.md` 的「🚀 上線後執行」段）。

**`changelog/` — 季度業務摘要**

每季 `YYYYQN.md`，給管理層／跨部門查閱的業務面摘要。技術細節看 git log，本目錄是業務導向的精選。季末（Apr/Jul/Oct/Jan 月初）整理上一季產出，機制詳 [`00009`](00009_Changelog撰寫機制.md)。季中草稿 `changelog_*_draft.md` 放 `todo/` 並 gitignore，定稿後改名搬入。

**`done/` — 完工 todo 的工程過程紀錄**

跨多 session 的大主題完工後，若過程的 design rationale 對未來有參考價值（phase 推進、設計取捨「為什麼 A 而非 B」、踩過的坑），整支 todo 移到 `done/` 永久歸檔。**不是**所有完工 todo 都進 `done/`：純規劃稿型（如「某模組落地」）蒸餾規則進 `md/` 後原檔直接刪即可。`md/` 寫**應然**（系統現在怎麼運作），`done/` 寫**實然**（當時為什麼這樣做）——兩者可能源自同一個 todo，但目的不同。

**`todo/` — 工作便條**

跨多 session 的大主題規劃稿（`yyyymmdd_<主題>.md`）、進度筆記（`00000000_進度筆記.md`）、changelog 季中草稿。短期、單 session 內就完成的小事不必開檔。git 策略（哪些入 git / 哪些 ignore）見 §四。

### 為什麼 ocadmin 用 `common/` 而衍生用 `md/`

`common/` 的語意是「跨衍生專案**共用**機制」，名稱描述定位；衍生專案的 `md/` 是「本專案具體實作的設計文件」，generic markdown design docs。角色相同，命名各自描述其在跨專案結構中的位置。

## 二、檔案編號規則

各 doc 子目錄內檔名遵循 5 位數編號：`{編號}_{標題}.md`，前 2 碼為分類，後 3 碼為序號。

### 第一位數字（命名空間）

| 第一位 | 用途 | 寫入 branch |
|---|---|---|
| `0` | 開發規範後設文件 | ocadmin（衍生專案不寫此段） |
| `1` | 基礎共用機制 | ocadmin |
| `2` | 衍生專案具體實作 | **所有衍生 branch 共用**（projFoo 等） |
| `9` | 議題探討與參考 | ocadmin |

衍生 branch 的歸屬靠 git repo 隔離（不同衍生 branch 各自寫的 23xxx 各自存在於各自 repo），不靠第一位數字區分。

### 第二位數字（業務段）

第二位代表業務領域，**跨第一位語意保持一致**：例如 ocadmin 的 `13xxx` 是銷售訂單，所有衍生專案的 `23xxx` 也是銷售訂單。

| 第二位 | 業務段 | 說明 |
|---|---|---|
| 0 | 開發規範（0x） / 系統全域架構（1x、2x） | 0x 段為 ocadmin 開發規範；1x/2x 段為系統全域架構（含參數設定、Settings、認證、選單、日誌等基礎機制） |
| 1 | 基礎主檔 | 組織、公司、部門、行政區、供應商、客戶、會員等跨模組共用主檔 |
| 2 | 商品型錄 | 商品、分類、選項、BOM、計量單位 |
| 3 | 銷售訂單 | 訂單、銷售明細、退貨、發票 |
| 4 | 採購生產（供應鏈） | 採購進貨、應付前流程、生產製造 |
| 5 | 財務會計 | 應付帳款、付款、費用支出、應收／應付分類帳 |
| 6 | 人資差勤 | 員工、出勤、排班、薪資、勞健保 |
| 7 | 報表統計 | 銷售、庫存、會員分析等 |
| 8 | CRM | 客戶服務案件、行銷活動 |
| 9 | 其它與議題探討（1x、2x） / 議題探討與參考（9x） | 雜項、UI、前端、未實作的提案、舊版保留參考 |

### 第二位字母擴充（a~z）

業務段 0~9 用滿後，可改用字母擴充第二位（共 36 個段位足夠任何 ERP 規模）：

| 第二位 | 預留語意 |
|---|---|
| `1a` / `2a` | 財務會計細分（如預算、成本中心，若 5x 不敷使用） |
| `1b` / `2b` | 生產製造細分（如製令工單、BOM 計算） |
| `1c~1z` / `2c~2z` | 未來擴充 |

實際啟用字母段時，再於本表登錄具體語意。

### 命名格式範例

```
{編號}_{標題}.md
```

- `00000_文件說明.md`（本檔）
- `10000_系統架構.md`
- `10007_權限機制.md`
- `10021_Settings參數設定.md`

### 序號配置建議

同一分類下，`x000` 通常為該分類的總覽／概述，`x001` 之後為細節主題；但並非硬性規定，實際依內容重要性與閱讀順序安排。

每段 1000 個序號（x000~x999）足夠用，可按業務子主題彙整。例：

- `13000~13099`：訂單核心
- `13100~13199`：訂單發票
- `13200+`：訂單其他子主題（保留）

### 10xxx 主題群內部排列（ocadmin 現況）

10xxx 為 ocadmin 最大段（含參數設定後共 23 檔），內部依主題群彙整、序號大致遞增：

| 序號範圍 | 主題群 |
|----------|--------|
| 10000 | 總覽 |
| 10001 | Portal |
| 10002–10003 | 國際化（多語、詞彙） |
| 10004–10010 | 認證、安全、帳號（Sanctum、使用者記錄、API 安全、權限、2FA、裝置、全域帳號） |
| 10011 | 選單 UI |
| 10012–10014 | 觀測與錯誤處理（日誌、例外、JSON 回應） |
| 10015 | 非同步與排程（Queue） |
| 10016–10018 | 資料架構（Model 分層、EAV/ZTM、多層選項連動） |
| 10019–10020 | 資源管理（圖片、靜態資源快取） |
| 10021–10022 | 參數設定（Settings 主檔、多層擴充架構） |
| 10023 | 英文名稱單複數規範 |
| 10024 | 日期查詢機制 |
| 10025–10026 | 帳號模擬、OAuth 帳號中心整合 |
| 10027 | DevLogin 開發登入繞過 |
| 10028 | 時區處理 |

### 衍生 branch 命名空間

衍生 branch 在 docs 目錄維護自己的 `20000_文件說明.md`，描述本 branch 在 2x 段使用情況（含必要時針對自身的子分段）。例：`projFoo/docs/md/20000_文件說明.md`。

衍生 branch 的「開發規範後設文件」放在 20xxx 段（系統全域架構），不另設 0x 段。

### 文件退役與編號永久保留

當某份文件對應的機制 / 模組不再使用、被抽離、被改寫，**編號永久退役，不補位、不重用**。已退役的編號保留 gap（例：10002, 10004, 10005，10003 已退役 → 不要把新文件命名為 10003）。

處置依文件未來性：

| 未來性 | 處置 |
|---|---|
| 永遠不會啟用 | 直接刪除（git log 是 history source of truth，可隨時撈回原文） |
| 未來可能啟用 / 有研究價值 | 移到 `research/`（衍生專案則對應其私有目錄），編號退役 |
| 暫時還有殘留依賴需過渡 | 原檔保留、文件開頭明標「未實作 / 待退役」；依賴清乾淨後再決定刪 / 移 |

**不採做法**：

- 把「未實作」內容留在 `common/` 加 caveat 即可 —— 違反「`common/` 只寫實作現況」原則（未實作該放 `research/`）；半年後讀者掃 doc 容易忽略開頭的 caveat 而誤以為是 reference
- 留空殼（編號 + 標題 + 「未實作」一行） —— 無資訊價值純佔位；git log 已能撈回原文，stub 不額外貢獻

**為什麼編號永久退役、不補位**（三項理由）：

1. **符合自家原則**：`common/` 只寫實作現況。退役 = 從 common 移走（或刪），是這原則的自然延伸。
2. **編號 = 永久身份**：類似 issue tracker ID / git commit SHA / database PK，刪除即退役但永不重用。Gap 不困擾任何系統（git / IDE / 跨專案引用都不依賴連號）；補位反而讓歷史引用撞 ID — 舊文章寫的 `ocadmin/10003` 將來指向意義完全不同的新內容，歷史失真。
3. **產業先例**：RFC（IETF）、ADR（Architecture Decision Record）都採「永久編號 + 狀態欄」（Active / Withdrawn / Superseded by X），不補位、不重用。本系統 doc 體制定位類同（業務 / 機制設計的永久檔案），沿用此慣例。

退役編號的索引（optional）：若想明示「10003 已退役，全文見 research/xxx」，可在本檔 §二「10xxx 主題群內部排列」表加「已退役」欄；但這只是 nice-to-have，不強迫。

## 四、git 納入策略

### 預設 track（整個子目錄入 git）

`common/`、`md/`、`reference/`、`migrate/`、`changelog/`、`done/` ——這些都是長期保留、變動慢的檔案。

### `todo/` 採「預設 track，僅 ignore scratch」

| 檔名 pattern | 範例 | git | 理由 |
|---|---|---|---|
| `yyyymmdd_<主題>.md` | `20260508_ApiCateringWebV3_規劃.md` | ✅ track | 大主題規劃稿，含設計取捨／phase 規劃／風險／決議；跨多 session 推進，期間想回頭看 commit 軌跡很有用。完工後刪除（規則蒸餾進 `md/`，過程紀錄看情況移到 `done/`），git history 仍保留 design rationale。 |
| `00000000_進度筆記.md` | （唯一這個檔案） | ❌ ignore | session 交接 scratch；高 churn、覆寫式維護，只反映 now 狀態。commit 史上一堆「進度筆記更新」是雜訊。瑣碎念頭、未獨立成案的想法直接記到此檔（如「⬜ 待排」「🚀 上線後執行」段），不另開 `todo.md`。 |
| `changelog_*_draft.md` | `changelog_2026Q2_draft.md` | ❌ ignore | 季中草稿；季末改名搬到 `changelog/` 才入 git（既定機制詳 00009）。 |

實作上規則寫在根 `.gitignore`：

```gitignore
docs/todo/00000000_*.md
docs/todo/changelog_*_draft.md
```

預設規則（不在 ignore 列上的就 track），不另設 `docs/todo/.gitignore`。

### 為什麼這樣分

主題 todo 入 git **多花一支「建立規劃稿」的 commit**，但中間勾選跟收工各自跟對應 feature/docs commit 一起進，**不增加額外 commit 負擔**。換來：

- 跨機器同步、備份
- 工作隔幾週才繼續時，`git log -- docs/todo/` 看得到推進軌跡
- 設計取捨理由有 git 軌跡可查，不依賴對話 transcript

scratch 類維持 ignore 是因為高 churn——每個 session 都會改幾次，commit 史塞滿無內容差異的「進度筆記更新」。
