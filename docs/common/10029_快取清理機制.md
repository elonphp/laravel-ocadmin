# 快取清理機制（`cache:prune-expired`）

> 對應命令：`App\Console\Commands\PruneExpiredCacheCommand`
> **預設不排程**——預設策略是每季全清，本命令為 opt-in，取捨見 §七
> 相關文件：[`10015_佇列Queue與排程.md`](10015_佇列Queue與排程.md)（排程如何被觸發）

---

## 一、為什麼需要這支命令

### 1-1. 框架沒有「只刪過期」的入口

Laravel 內建與快取有關的命令只有三支：

| 命令 | 行為 |
|---|---|
| `cache:clear` | **整個清光**，含仍然有效的項目 |
| `cache:forget` | 刪指定的一個 key |
| `cache:prune-stale-tags` | **Redis 專用**，且只處理 tag |

沒有「掃過期、只刪過期」這種東西。要清就是全清，而全清會連帶把有效快取一起丟掉，
在正常營運時間執行等於自找一波 cache stampede。

### 1-2. 快取的刪除是 lazy 的，孤兒項目永遠不會消失

`FileStore` 只有在「某個 key 剛好又被讀到、發現已過期」時，才刪**那一個**檔
（`getPayload()` 內部呼叫 `forget()`）；`DatabaseStore` 同理。

於是：

> **再也不會被讀到的 key，永遠不會被清掉。**

只要 key 裡含日期、id、參數雜湊這類會變動的成分——而那正是快取 key 最常見的長相——
每換一組參數就留下一個孤兒。它們過期了、沒有任何用處，但檔案還在磁碟上、列還在資料表裡，
只增不減。

這是個安靜的洩漏：不會壞、不會報錯，只是磁碟與資料表一直長大，直到有人去看才發現。

### 1-3. 這件事與任何功能無關

快取清理是**系統維運**，不屬於任何一個使用快取的功能。
不該由「某個報表」或「某個模組」順便處理，也不該綁在特定的 key 前綴上——
否則每多一個用快取的地方，就要記得多寫一支清理。

## 二、兩條刪除規則

```bash
php artisan cache:prune-expired                    # 預設：過期 + 逾齡 90 天
php artisan cache:prune-expired --dry-run          # 預覽，不刪
php artisan cache:prune-expired --days=30          # 改逾齡門檻
php artisan cache:prune-expired --days=0           # 只刪過期，關閉規則 2
php artisan cache:prune-expired --store=file       # 只處理指定 store（可重複指定）
```

| # | 規則 | 判準 |
|---|---|---|
| 1 | **已過期 → 刪** | 項目自己記錄的到期時間 |
| 2 | **未過期但超過 N 天沒被寫入 → 也刪** | 檔案 mtime（預設 90 天） |

### 2-1. 規則 2 的用意：連 `forever` 也不給無限期居留

`forever` 寫進去的項目到期時間是 `9999999999`，規則 1 永遠碰不到它。
少量還好，但沒有上限就意味著「寫一次就永遠佔著」——而快取本來就該是可拋棄的。

規則 2 給所有項目一個**絕對壽命上限**。對真正的快取而言，被刪掉只是下次 miss、
重建一次，沒有正確性影響。

### 2-2. ⚠️ 「超過 N 天」是「**最後一次寫入**超過 N 天」，不是「建立以來」

快取檔身上只有兩個時間訊號：檔頭的到期時間、檔案系統的 **mtime**。
**沒有建立時間，也沒有最後讀取時間**——`FileStore::get()` 只讀不寫，不會更新 mtime。
（atime 不能用：多數 Linux 檔案系統掛載時帶 `relatime` / `noatime`，不可靠。）

所以判準只能是 mtime，這帶來一個必須知道的行為：

> 一個 `forever` 項目，就算**每天都被讀**，只要沒被重寫過，滿 N 天就會被刪。

換句話說，**「被讀」不算活著，「被寫」才算**。

這其實是好的語意——「持續在更新的留著，寫一次就沒再動過的清掉」——
但它決定了規則 2 適用的對象，見 §四的使用紀律。

### 2-3. 資料庫 store 不支援規則 2

`cache` 資料表只有 `key` / `value` / `expiration` 三欄，**沒有任何寫入時間**。
`forever` 的列 `expiration = 9999999999`，完全無從判斷年齡。

要支援就得改表結構、並改掉框架 `DatabaseStore` 的寫入行為，代價遠高於效益。
故 database store **只套用規則 1**，命令輸出會明確標示「此 driver 無寫入時間，不適用」，
而不是安靜地略過——不然看輸出的人會以為規則 2 生效了。

而這個組合會是多數環境的現況：Laravel 11 把 `CACHE_STORE` 預設從 `file` 改成 `database`，
理由是官方層級的（免額外服務、多機部署共用、與 session / queue 一致），
不是任何專案自己的取捨。換句話說，**沒特別選過的環境，預設就落在「只有規則 1 生效」那一側。**

> 若某個環境很在意規則 2，把 `CACHE_STORE` 改成 `file` 即可讓它全面生效。
> 這是環境層級的取捨，不由本命令決定。

## 三、實作要點

### 3-1. 只讀檔頭 10 bytes，不讀內容

`FileStore` 的檔案格式是：

```php
str_pad((string) $expiration, 10, '0', STR_PAD_LEFT) . serialize($value)
```

**前 10 個位元組就是到期的 unix timestamp**，`9999999999` 代表永不過期。

判定過期只需要那 10 個位元組，而快取檔可能有數 MB。命令用 `fopen` + `fread(10)`，
不做 `file_get_contents`，也不 `unserialize`——後者不只慢，還會在內容含有物件時
觸發 autoload 甚至 `__wakeup`，對一支維運命令來說是完全不必要的風險。

### 3-2. 掃描範圍嚴格限定 cache store 的 path

只掃 `config('cache.stores.*.path')`。**不碰**：

| 目錄 | 是什麼 | 該用什麼清 |
|---|---|---|
| `storage/framework/views` | 編譯後的 Blade | `view:clear` |
| `bootstrap/cache` | config / route / package 快取 | `config:clear`、`route:clear` |

那些都不是 cache store 的項目，沒有到期時間可讀，混進來只會誤刪。

### 3-3. 鎖檔與快取檔同目錄，但這是安全的

`file` store 的 `lock_path` 預設就指向 `path` 同一個目錄，所以 `Cache::lock()` 產生的
鎖檔會跟快取檔混在一起。這不構成問題：

- 鎖檔**格式相同**（前 10 bytes 也是到期時間），規則 1 判得出來
- 刪掉**已過期**的鎖正是應該做的事（那是沒被正常釋放的殘留）
- 規則 2 碰不到有效的鎖——鎖的 TTL 都是秒到分鐘級，不可能存活 90 天

同理，database store 的 `cache_locks` 表也一併套用規則 1。

### 3-4. 損毀檔直接刪

檔頭讀不到 10 碼數字，代表寫入中斷或檔案損毀。這種檔沒有任何人能用
（框架讀它時 `unserialize` 也會失敗），留著只是佔位，直接刪並單獨計數。

### 3-5. 清完檔案要刪空目錄

file store 以 key 的雜湊分兩層目錄存放，清完檔案會留下大量空殼目錄。
命令用 `RecursiveIteratorIterator::CHILD_FIRST` 走訪——子目錄先被處理掉，
父目錄在同一輪就跟著判定為空，一次走訪即可清乾淨。

### 3-6. 輸出分開報「過期」與「逾齡」

不要只給一個總數。兩者的意義不同：

- **過期**數量高 = 正常回收，符合預期
- **逾齡**數量持續偏高 = 有人把不該長存的東西寫成了 `forever`，是個該追查的訊號

`--dry-run` 會在每行前面加 `[Dry Run]`，並且**不寫排程日誌**（預覽不是一次執行）。

## 四、配套的使用紀律：`forever` 該用在什麼地方

規則 2 的存在，反過來界定了 `forever` 的正當用法：

> **`forever` 只能用在「刪掉會自動重建、且重建無副作用」的資料。**

需要靠快取存活才能正確運作的東西——例如把快取當索引、當帳本、當「我寫過哪些 key」的
登記簿——**不能只活在快取裡**。快取隨時可能因為清理、部署、切換 driver、磁碟問題而消失；
一旦那份登記簿沒了，依賴它的邏輯就會安靜地失準。

這類資料應該有資料表或檔案作為持久化來源，快取只是它的加速層。

判斷方法很簡單：**問「這一筆被刪掉，系統會不會有人察覺？」**
答案若是「會，而且會出錯」，那它就不該只存在於快取。

## 五、排程

> ⚠️ **預設不掛這支命令。** 預設策略是每季全清，本命令是 opt-in——判斷依據見 §七。
> 以下是決定啟用時的建議寫法。

```php
// routes/console.php
Schedule::command('cache:prune-expired')
    ->dailyAt('00:30')
    ->withoutOverlapping();
```

排在離峰時段。掃描成本很低（每個檔只讀 10 bytes），但清理本身沒有時效壓力，
沒有理由跟營運時段搶 I/O。

`withoutOverlapping()` 防止前一次還沒跑完就又啟動——快取目錄很大時單次可能跑上一陣子。

命令執行結果會經 `LogDatabaseRepository::logSchedule()` 寫入排程日誌，與其他維護排程一致。

> 排程本身如何被觸發（cron / Plesk 計劃任務）見 [`10015_佇列Queue與排程.md`](10015_佇列Queue與排程.md)。

## 六、驗證

第一次部署建議先 dry-run，確認要刪的東西符合預期：

```bash
php artisan cache:prune-expired --dry-run
```

行為驗證可以自己造四種項目來對（過期 / 有效 / forever 剛寫 / forever 老舊），
把最後一個的 mtime 用 `touch($path, time() - 200 * 86400)` 調老，再跑一次命令，
確認只有「過期」與「forever 老舊」兩個被刪、有效的兩個留著。

## 七、預設策略：每季全清，本命令是 opt-in

前面六節說明的是「只刪過期」怎麼做、以及為什麼框架給不了。但**要不要做到那個精細度，是另一個問題**。

### 7-1. 預設採用全清

```php
// routes/console.php
Schedule::command('cache:clear database')->quarterlyOn(1, '03:00');
Schedule::command('cache:clear file')->quarterlyOn(1, '03:10');
```

`cache:clear` 一次只作用**一個** store（沒帶參數就是 `cache.default`），所以要分兩行。

理由很單純：快取本來就是可拋棄的暫存，任何項目被刪掉都只是下次 miss、重建一次。
既然如此，為了「不誤傷仍然有效的項目」而維護一套逐筆比對的機制，收益與複雜度不成比例。

全清還順手解掉兩件精細回收做不到的事：

| | 精細回收 | 全清 |
|---|---|---|
| database store 的 `forever` 列 | **清不掉**（無寫入時間，見 §2-3） | 清得掉 |
| file store 的鎖檔殘留 | 只清得掉已過期的 | 全部清掉 |

### 7-2. 全清的代價

三件事，都要知道：

1. **執行的那一刻全部 miss。** 所有依賴快取的路徑同時回源重算，是一次人為製造的 stampede。排在離峰、且頻率低到一季一次時可以接受；流量大的環境要自己評估那一分鐘。
2. **兩次之間沒有上限。** 精細回收讓資料表維持在穩態，全清則是讓它長滿一季再歸零。峰值 = 一季份的孤兒量。寫入量大的環境要估過。
3. **`flush()` 走的是 `DELETE` 不是 `TRUNCATE`。** 表養大之後那是一筆重交易，而且 InnoDB 不會把空間還給作業系統。真的長到會痛時，手動 `TRUNCATE` 比跑命令划算。

### 7-3. 什麼時候該改掛精細回收

出現以下任一情況，就把 §五 的排程掛回去，並把全清拿掉（**兩者不要同時掛，那是重複做同一件事**）：

- 有任何一條路徑「一次全 miss」的代價無法承受
- 快取表 / 目錄在一季內就長到會影響備份或磁碟

### 7-4. 鎖：一律釘在 database store

鎖（`Cache::lock()`、排程的 `withoutOverlapping()` / `onOneServer()`、unique job 等）**跟快取住在同一個 store，但不是快取**——它被誤刪的後果不是「重算一次」，而是同一段程式同時跑兩份。

兩種載體的行為差很多：

| | 載體 | 自我回收 | 被該 store 的 `flush()` 影響 |
|---|---|---|---|
| database | `cache_locks` 表 | ✅ `DatabaseLock::acquire()` 有 2% 彩票跑 `pruneExpiredLocks()` | ❌ `flush()` 只清 `cache` 表，清鎖是 `flushLocks()`（`--locks`） |
| file | `lock_path` 目錄（**預設等於 `path`**） | ❌ 無（`FileLock::acquire()` 只是普通的 `add()`） | ✅ 整批刪，**不判斷過期，活鎖一起帶走** |

所以全清策略要成立，就得確保鎖不會落在 file store 上：

```php
// routes/console.php
Schedule::useCache('database');              // 排程互斥鎖固定存 cache_locks

Cache::store('database')->lock('foo', 10);   // 應用層取鎖也明確指定，不要用 Cache::lock()
```

`Cache::lock()` 取的是**當前 default store 的鎖**，會跟著 `CACHE_STORE` 漂移；明確指定就不會。
這在任何 `CACHE_STORE` 設定下都成立——`cache_locks` 表由 migration 無條件建立，不因為快取沒用資料庫而缺席。

#### `Schedule::useCache()` 實際做了什麼

命名看不出它跟鎖有關。它唯一的作用是**指定排程互斥鎖存在哪個 cache store**，與快取讀寫無關：

```php
// Illuminate\Console\Scheduling\Schedule
public function useCache($store)
{
    if ($this->eventMutex instanceof CacheAware) {
        $this->eventMutex->useStore($store);          // withoutOverlapping() 用的
    }

    if ($this->schedulingMutex instanceof CacheAware) {
        $this->schedulingMutex->useStore($store);     // onOneServer() 用的
    }

    return $this;
}
```

從參數到資料表的完整路徑：

```
Schedule::useCache('database')
  → CacheEventMutex::useStore('database')        // 記下 store 名
  → 排程要跑時 CacheEventMutex::create()
      → shouldUseLocks($store)                   // $store instanceof LockProvider ?
      → DatabaseStore 有實作 → true
      → cache->store('database')->getStore()->lock($event->mutexName(), ...)
      → DatabaseStore::lock() 回傳 DatabaseLock
      → INSERT INTO cache_locks (key, owner, expiration)
```

不呼叫它時，store 名是 `null`，`cache->store(null)` 解析成 `cache.default`——這就是「漂移」：
同一份程式碼換個環境變數，鎖就換了個地方存。

> ⚠️ 參數是 `config('cache.stores')` 的**鍵名**，不是 driver 名。兩者常同名而看不出差別，
> 但若另外定義了 `'locks' => ['driver' => 'database', 'lock_table' => ...]`，這裡就要寫 `'locks'`。

作用範圍很窄，不要誤以為它改掉了預設 store：

| 呼叫 | 用哪個 store |
|---|---|
| `Cache::get()` / `put()` / `flexible()`、`cache:clear`（不帶參數）、RateLimiter | `cache.default`，不變 |
| `Cache::lock()` | `cache.default`，**不變** |
| 排程的 `withoutOverlapping()` / `onOneServer()` | 被釘住的那個 |

只有最後一列受影響。**被排程執行的那些命令，其內部的快取行為完全不受這行影響**——
這也正是為什麼應用層取鎖還得自己寫明 `Cache::store(...)->lock()`。

> ⚠️ **前提**：寫下這行等於宣告 `database` store 一定可用——資料庫連得上、`cache_locks` 表存在。
> 框架的 migration 無條件建立 `cache` 與 `cache_locks` 兩張表，與 `CACHE_STORE` 設什麼無關，
> 所以預設情況下成立。但若某專案因為「我們用 file 快取，用不到這兩張表」而刪掉那份 migration，
> 排程取鎖時就會炸——**要刪那份 migration，就得連這行一起重新評估**。

釘住之後，`cache:clear file` 就是單純刪快取檔，不存在「會不會刪到不該刪的」這個問題。

> 若某環境確實需要 file store 的鎖，框架的解法是把 `lock_path` 指到 `path` **以外**的目錄：
> `hasSeparateLockStore()` 成立後 `flush()` 便刪不到鎖，且 `cache:clear <store> --locks` 才可用
> （否則會丟 `RuntimeException`）。
