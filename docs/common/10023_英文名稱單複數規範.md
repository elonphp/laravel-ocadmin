## 零、元原則（遇到新情境時自己會推）

> **單數 = 描述「概念 / 類型 / 單一實例」**
> **複數 = 描述「集合 / 容器 / 多個實例」**

判斷一個名字該單數還是複數，問自己：**「這個名字描述的是什麼？」**
從「對象本質」回推，不要從「它跟誰擺一起」反推。

### 三個語境分類

不同語境下，名字描述的對象不同：

| 語境 | 描述對象本質 | 規則 | 出現位置 |
|---|---|---|---|
| **OO / 程式內** | 概念、類型、namespace、單一物件 | **單數** | Model / Controller / Service / Policy / Resource class / 單一變數 / Module folder / **View folder** / Permission name resource 段 |
| **HTTP / RESTful** | 資源集合的對外位址 | **複數** | URL path resource 段 / Route name resource 段 |
| **DB / 儲存層** | 存放多筆記錄的容器 | **複數** | Table 名 / Migration filename |

集合變數（如 `$users = User::get()`）走複數，是因為**它持有多個實例**——「對象本質」決定，不是「在哪個語境」決定。

### 邊界情況

- **View folder** 屬於「OO / 程式內」語境：folder 裡放的是 `index.blade.php` 等以 action 為名的檔案，folder 本身代表「某個概念的視圖空間」，不是「多個 view 實例的集合」。所以是**單數**，跟 Controller / Module folder 對齊；不是跟 URL 對齊。
- **Pivot table**（如 `role_user`）：是 DB table 但命名特殊（兩個單數字母序）。理由：pivot 描述「兩個概念的連結」，名字以**概念**為主體，不是描述「多個連結記錄的容器」；Laravel `belongsToMany` 也照此慣例自動 infer pivot name。算 DB 層的局部例外。
- **FK 欄位 `user_id`**：單數因為它指向**一筆記錄**的 id，不是多個 user 的容器。
- **不可數名詞**（`cache` / `data` / `info`）：照英文本身慣例，沒有單複數選擇問題（資料夾叫 `cache/` 不加 s）。
- **Boolean 變數 / 欄位**（`$is_active` / `$has_permission`）：描述狀態，沒有「數量」概念，不適用此規則。

下一節 §一 是快速查表；遇到表上沒列的新情境，回到本節元原則自己推。

## 二、URL prefix 與 Route name：複數

### 2.1 URL prefix

格式：`/{portal_url}/{module}/{resources}`

```
/admin/system/users           ✅  複數
/admin/catalog/products       ✅  複數
/admin/config/taxonomies      ✅  複數（不規則複數照英文規則）
/admin/system/user            ❌  單數
```

URL 直接呈現在瀏覽器網址列，是 HTTP 資源位址，遵循 RESTful 慣例使用複數名詞。

### 2.2 Route name

格式：`{lang}.{portal}.{module}.{resources}.{action}`

```php
// 路由定義
Route::prefix('settings')->name('settings.')->group(function () {
    Route::get('/', [SettingController::class, 'index'])->name('index');
    Route::get('/create', [SettingController::class, 'create'])->name('create');
});

// 產生的 route name（含外層前綴）
// → lang.ocadmin.system.settings.index
// → lang.ocadmin.system.settings.create
```

Route name 的 **resource 段**跟 URL prefix 保持一致（都複數），避免「URL 複數但 name 單數」的認知分裂。

**複數規則只套用在 resource 段**。`system`、`catalog` 是 module（功能命名空間），代表「哪個功能區」而非「多少個資源」，維持單數；`settings`、`products` 才是 resource，代表 RESTful 資源集合，使用複數。

### 2.3 Laravel `Route::resource` 的預設行為

Laravel 的 `Route::resource('users', UserController::class)` 會自動產生：

| Route name | Method | URL |
|-----------|--------|-----|
| `users.index` | GET | `/users` |
| `users.create` | GET | `/users/create` |
| `users.store` | POST | `/users` |
| `users.show` | GET | `/users/{user}` |
| `users.edit` | GET | `/users/{user}/edit` |
| `users.update` | PUT/PATCH | `/users/{user}` |
| `users.destroy` | DELETE | `/users/{user}` |

URL 和 route name 都是複數，本規範直接沿用此慣例。

## 三、Permission name resource 段：單數

格式：`{portal}.{module}.{resource}.{action}`

```
admin.system_acl.user.access          ✅  resource 段單數
admin.catalog.product.modify          ✅  resource 段單數
admin.catalog.products.modify         ❌  resource 段複數（錯）
```

Permission name 的 resource 段採單數，與 Eloquent Model 命名對齊。

詳細理由見 [10007_權限機制.md §13](10007_權限機制.md)。本節僅列關鍵點：

1. **與 Model 命名對齊**：`User` Model → `user` permission resource，跨層一致
2. **英文不規則複數問題**：`category → categories`、`taxonomy → taxonomies`，單數永遠不用想複數規則
3. **Wildcard 語意清晰**：`admin.catalog.product.*`（對 product 的所有動作），比 `products.*` 更直覺
4. **URL 與 permission 各走各的**：`/catalog/products`（URL）vs `admin.catalog.product.access`（permission），不互相牽動，維護者習慣分工後不混淆

## 四、Eloquent Model / DB Table / FK / Pivot

Laravel 預設慣例（本系統遵循）：

### 4.1 Model：單數

```php
class User extends Model { }         // ✅  app/Models/User.php
class Product extends Model { }      // ✅  app/Models/Product.php
class OrderProduct extends Model { } // ✅  關聯子表也單數
```

### 4.2 DB Table：複數

```
users           ← App\Models\User
products        ← App\Models\Product
order_products  ← App\Models\OrderProduct
acl_roles       ← App\Models\Acl\Role
```

Laravel 自動把 Model class 名轉為 snake_case 複數作為 table 名。若需自訂，覆寫 `protected $table = 'xxx';`。

### 4.3 Foreign key：`{單數}_id`

```php
$table->foreignId('user_id')->constrained();       // → users.id
$table->foreignId('product_id')->constrained();    // → products.id
$table->foreignId('organization_id')->constrained('org_organizations');  // 跨命名前綴需指明
```

### 4.4 Pivot Table（多對多中介表）：兩單數字母序組合

```
role_user        ← roles ↔ users
product_tag      ← products ↔ tags
permission_role  ← permissions ↔ roles（Spatie 的習慣命名）
```

字母序避免「該叫 user_role 還是 role_user」的爭論。Laravel `belongsToMany()` 預設依此推算 pivot 名稱。

### 4.5 Migration filename：複數（對應表名）

```
2014_10_12_000000_create_users_table.php             ✅
2026_01_15_100000_create_products_table.php          ✅
2026_02_01_000000_create_order_products_table.php    ✅
```

詳細編號規則見 [`00006_Migration模組編號規範.md`](00006_Migration模組編號規範.md)。

## 五、Controller / Resource class

### 5.1 Controller：單數

```php
class UserController extends OcadminController { }       // ✅
class ProductController extends OcadminController { }    // ✅
class OrderImageController extends OcadminController { } // ✅  業務 entity 的子資源也單數
```

Resource Controller 的方法名跟 Laravel 預設（`index` / `create` / `store` / `show` / `edit` / `update` / `destroy`）。

### 5.2 API Resource / Collection：對應 Model 命名

```php
class UserResource extends JsonResource { }              // ✅  單一資源（單數）
class UserCollection extends ResourceCollection { }      // ✅  集合（仍單數類名 + Collection 後綴）
```

`UserCollection` 雖然處理多筆，class 名仍是「Model 單數 + Collection」，不是 `UsersCollection`。

### 5.3 Policy class：單數

```php
class UserPolicy { }       // ✅
class ProductPolicy { }    // ✅
```

對應 Model 名。

### 5.4 Service / Action class：通常單數業務 entity

```php
class OrderService { }              // ✅  以 Order 為業務 entity
class PaymentProcessor { }          // ✅  以動作命名也可
class GenerateInvoiceAction { }     // ✅  Action class 用動詞+名詞
```

Service 抽出時機見 [`10016_架構分層職責.md`](10016_架構分層職責.md)。

## 六、Blade view / 資料夾

View 子目錄跟 **Controller / Module folder** 對齊用**單數**（不是跟 URL 複數），檔名用 action 動詞：

```
resources/views/ocadmin/
├── catalog/                     ← module 段
│   ├── product/                 ← 領域概念，單數
│   │   ├── index.blade.php       (路由 catalog.products.index → /admin/catalog/products)
│   │   ├── create.blade.php
│   │   ├── edit.blade.php
│   │   └── form.blade.php       ← create / edit 共用
│   ├── option/
│   └── option-value-group/
├── org/
│   ├── company/
│   ├── department/
│   └── employee/
└── system/
    ├── user/
    ├── role/
    └── permission/
```

**為何不跟 URL 走複數？** view folder 描述「某個領域概念的視圖集」，與 `Modules/Catalog/Product/ProductController.php`、`app/Models/Catalog/Product.php` 的命名階層對齊；URL 是 HTTP 對外的資源集合（複數），是另一個維度，不影響 view 內部組織。本系統「URL 複數 / 程式內單數」的分工同樣套用在 view folder。

View namespace（`View::addNamespace` 的第一個參數）採單數，對應 Portal 名：`ocadmin::`、`pos::`、`hrm::`。

## 七、變數命名

### 7.1 單一物件：單數

```php
$user = User::find(1);
$product = Product::with('images')->find($id);
$order = $request->user()->orders()->latest()->first();
```

### 7.2 集合 / array：複數

```php
$users = User::active()->get();        // Collection
$products = Product::paginate(20);     // Paginator（仍視為複數集合）
$ids = $request->input('ids', []);     // array
```

### 7.3 關聯方法命名

belongsToMany / hasMany 對應的關聯方法用複數（拿回的是集合）：

```php
public function roles(): BelongsToMany { ... }   // ✅  $user->roles → Collection
public function orders(): HasMany { ... }        // ✅  $user->orders → Collection
public function images(): HasMany { ... }
```

hasOne / belongsTo 用單數：

```php
public function user(): BelongsTo { ... }        // ✅  $order->user → User instance
public function profile(): HasOne { ... }
```

### 7.4 Boolean：描述性，無單複數

```php
$is_active = true;
$has_permission = $user->can('...');
$can_modify = $this->authorize('modify', $product);
```

不要硬塞單複數（如 `$active` 應改為 `$is_active`）。

## 八、為何 URL 複數 vs Permission 單數

兩套慣例服務不同目的：

| | URL（複數） | Permission name（單數） |
|---|---|---|
| **設計來源** | RESTful（資源集合導向） | Eloquent / OO（class 命名） |
| **意義** | 「這個路徑管理 user 這類資源**集合**」 | 「對 user 這個資源**類型**的權限」 |
| **業界共識** | Rails / Django / Laravel `Route::resource` 預設皆複數 | AWS IAM / GCP IAM 混用，無壓倒性偏好；Laravel 內部以 Model 單數命名為主 |
| **不規則複數風險** | URL 必須拼對英文複數（`taxonomies` 不是 `taxonomys`） | 永遠單數，完全規避 |

維護者習慣這個分工後（URL 複數 / 程式內單數），切換時不需要思考。詳見 [10007_權限機制.md §13](10007_權限機制.md)。

## 九、跨層階層對齊（縱向結構）

§二–§七 處理的是「同一個概念在各層該單數還是複數」（橫向拼寫）。本節處理另一軸：「同一個概念在各層的階層位置」（縱向結構）。

> **同一個 resource 在所有層的「身份座標」應該相同。**

每個 resource 在系統中有一個**身份座標** = `{module}/{resource}`（可巢狀成 `{module}/{sub_module}/{resource}`）。系統各層對這個 resource 的指代都用同一個座標——誰也不跳層、誰也不加層、誰也不換字。

座標不對齊 → 維護者腦中需建立多套對映表（看 URL 才知 route name → 看 route name 才知 view folder → 看 view folder 才知 module folder）。座標對齊後，知一處即知所有處。

### 9.1 五層座標對齊

| 層 | 路徑樣式 | `setting` 範例（座標 `system/setting`） |
|---|---|---|
| URL prefix | `/{portal_slug}/{module}/{resource}` | `/admin/system/settings` |
| Route name | `{lang}.{portal}.{module}.{resource}.{action}` | `lang.ocadmin.system.settings.index` |
| Permission | `{portal}.{module}.{resource}.{action}` | `admin.system.setting.access` |
| Module folder | `Core/Controllers/{Module}/{Resource}Controller.php`（Core 模板隨附）或 `Modules/{Module}/{Resource}/`（專案自有） | `Core/Controllers/System/SettingController.php` |
| View folder | `app/Portals/{Portal}/resources/views/{module}/{resource}/` | `views/system/setting/` |

**Model folder（`app/Models/{Module}/{Resource}.php`）** 不強制納入座標對齊：Model 是跨 Portal 共用、可能不屬於任一 Portal 的 module 切分（例 `app/Models/User.php` 放 root）。但若某 Model 屬於明確業務領域，子資料夾名建議與 Portal module 一致（例 `app/Models/Sale/Order.php` 對應 `Modules/.../Sale/Order/`）。

### 9.2 座標的 token 一致性

座標是「**概念 token 的序列**」，排除 case 與單複數差異後**主體拼字必須相同**。各層 case 與單複數轉換規則照 §一 快速參考表，但**主體 token 跨層不能改拼字**。

❌ 反例（token 拼字不一致）：view folder 叫 `common/imgmanager/` 但 route 叫 `common.image-manager.*`——主體一個是 concat `imgmanager`，另一個是兩字 hyphenated `image-manager`，token 序列不同。
✅ 修正：統一為 `image-manager` / `ImageManager/` / `image_manager`，五層 case 不同但 token 序列一致。

複合詞跨層 case 轉換對照表（範例）：

| 概念 | URL / Route | Permission | Folder | 變數 |
|---|---|---|---|---|
| authorization plan | `authorization-plans` | `authorization_plan` | `AuthorizationPlan/` | `$authorization_plan` / `$authorizationPlan` |
| image manager | `image-manager` | `image_manager` | `ImageManager/` | `$image_manager` |
| custom option name | `custom-option-names` | `custom_option_name` | `CustomOptionName/` | `$custom_option_name` |

### 9.3 對齊範例（合規）

#### 9.3.1 兩段座標（典型，單 resource module）

```
Resource: order（訂單管理）
座標:     sale / order

URL:            /admin/sale/orders
Route name:     lang.ocadmin.sale.orders.{action}
Permission:     admin.sale.order.{action}
Module folder:  app/Portals/Ocadmin/Modules/Sale/Order/OrderController.php
View folder:    views/sale/order/{action}.blade.php
Model:          app/Models/Sale/Order.php（可選，但建議對齊）
```

五處的 `sale/order` 完全一致，差異僅 case 與單複數（依 §一）。Module folder 採 per-resource sub-folder（`Sale/Order/`），是 resource 內 helper 檔多時（FormRequest / Policy / Service 等同層收納）的典型形式。

#### 9.3.2 兩段座標（多 resource module，Module folder flat）

同一 module 下有多個 resource 時，**Module folder 採 flat**（controller 直接放 module 根目錄，對應 Laravel 慣例），其他 4 層仍走 2 段座標 `{module}/{resource}`：

    ┌───────────────┬─────────────────────────────────────────────────────┬────────────────────────────────────────────────────┐
    │      層       │                  Member（主資源）                   │                 Level（會員等級）                  │
    ├───────────────┼─────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
    │ URL           │ /admin/member/members                               │ /admin/member/levels                               │
    ├───────────────┼─────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
    │ Route name    │ lang.ocadmin.member.members.*                       │ lang.ocadmin.member.levels.*                       │
    ├───────────────┼─────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
    │ Permission    │ admin.member.member.*（4 段不變）                   │ admin.member.level.*（4 段）                       │
    ├───────────────┼─────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
    │ Module folder │ Modules/Member/MemberController.php（flat）         │ Modules/Member/LevelController.php（flat）         │
    ├───────────────┼─────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
    │ View folder   │ views/ocadmin/member/member/index.blade.php（2 段） │ views/ocadmin/member/level/index.blade.php（2 段） │
    ├───────────────┼─────────────────────────────────────────────────────┼────────────────────────────────────────────────────┤
    │ Lang          │ lang/zh_Hant/admin/member/member.php                │ lang/zh_Hant/admin/member/level.php                │
    └───────────────┴─────────────────────────────────────────────────────┴────────────────────────────────────────────────────┘


§9.6 五題對齊解讀：Module folder 的 token 序列由「資料夾 + Controller filename」共同呈現 — `Modules/Member/MemberController.php` 即 `member/member`（folder 段 `Member` + filename 去 `Controller` 後綴 `Member`），與其他 4 層 `member/{resource}` 一致。

**何時 flat、何時 per-resource sub-folder**：

- **Flat（首選）**：典型 CRUD module、每 resource 僅有 Controller（少量 helper），module 名與某個 resource 同名時更明顯收益（避免 `Member/Member/` 冗餘）。Member / Crm / Www / Account 等「portal-root 性質、語意聚焦」module 走此模式。
- **Per-resource sub-folder**：某 resource 有大量輔助檔（多支 Service / Request / Policy / Action class）需獨立 namespace 收納時。如 Sale/Order/、Inventory/PurchasingOrder/、Accounting/ExpenseSlip/ 等業務複雜 resource。

兩種 layout 不影響其他 4 層座標，是 Module folder 內部組織偏好；同一專案內可混用，依各 resource 大小決定。

#### 9.3.3 三段座標（巢狀 module）

若 module folder 用了三層巢狀（`System/Acl/User/`），其他四層也需有同樣三層：

```
URL:            /admin/system/acl/users
Route name:     lang.ocadmin.system.acl.users.{action}
Permission:     admin.system_acl.user.{action}              ← module 段合併底線
Module folder:  Modules/System/Acl/User/UserController.php
View folder:    views/system/acl/user/{action}.blade.php
```

> Permission 那層**唯一例外**用底線合併 `system_acl`：[10007 §3.1](10007_權限機制.md) 規定 permission「原則上 4 段、module 多層用底線連接」（第 4 段鎖 action，前 3 段壓進 portal/module/resource）。其他四層不受 4 段限制，照階層用 `system/acl/{resource}` 平鋪即可。座標對齊**排除分隔符與單複數差異後 token 序列相同**，因此 `system.acl.user`（其他層）與 `system_acl.user`（permission）視為同一座標。

### 9.4 例外情境

#### 9.4.1 Portal-level singleton

不屬於任何 module 的 portal 內建功能，座標退化為 `{resource}` 單段：

| 例 | URL | Route | Module folder | View folder |
|---|---|---|---|---|
| Login | `/admin/login` | `lang.ocadmin.login` | `Core/Controllers/LoginController` | `views/auth/` |
| Dashboard | `/admin` | `lang.ocadmin.dashboard` | `Modules/Dashboard/` | `views/dashboard/` |

Login/Logout/Dashboard 通常用 middleware 而非 permission 控管，故 permission 段省略。view folder 用 `auth/` 是 Laravel 預設慣例的 portal-level 例外（不對映 module）。

#### 9.4.2 通用工具入口（`common/` 模組）

跨業務模組共用的工具（image-manager、file-browser、log-viewer 等）以 `common` 作為 module 段，其下放單例工具即可，不需要再開 resource 子層：

```
URL:            /admin/common/image-manager
Route name:     lang.ocadmin.common.image-manager.{action}
Module folder:  Core/Controllers/ImageManagerController（或 Modules/Common/ImageManager/）
View folder:    views/common/image-manager/
```

#### 9.4.3 Account 模組（使用者自身資料）

```
URL:            /admin/account/profile
Route name:     lang.ocadmin.account.profile
Module folder:  Core/Controllers/Account/ProfileController.php
View folder:    views/account/
```

`profile` 是 singleton（一個帳號只有一個 profile），URL/route 用單數合理（RESTful singleton resource 慣例）。

#### 9.4.4 跨 Portal 共用 Model

`app/Models/User.php` 等共用 Model 不屬於任何特定 Portal 的 module 階層，可放 `app/Models/` root。Model 子資料夾命名若與業務領域一致，可降低跨層認知成本，但不強制。

#### 9.4.5 業務名 vs 技術名（不可混用）

同一個概念在不同層用不同字 → 維護者需要記憶對映表。本規範**不允許混用**：

❌ Module folder `Modules/Party/Organization/` 配 Route `dealer.members.*`——`Party` 是技術 namespace（Person + Organization），`dealer` 是業務語意（經銷商），同一個 controller 上下層被兩個字代表。

✅ 擇一統一：
- 全技術命名：`Modules/Party/Member/` + route `party.members` + view `party/member/`
- 全業務命名：`Modules/Dealer/Member/` + route `dealer.members` + view `dealer/member/`

#### 9.4.6 Model 命名與外部 namespace 衝突

當 Model class 名稱會與 Laravel 內建 facade 或第三方套件全域 class 撞名時，**Model 層可保留較長的 disambiguating token**（如 `RequestLog`），其他層仍使用 short concept token（如 `log`）。此跨層分歧需在該 resource 的 module doc 內留命名說明，並在本節（§9.4.6）索引。

❌ Model `App\Models\System\Log` 撞 `Illuminate\Support\Facades\Log`——同檔同時 `use` 兩者需 alias 處理，且新進開發者易誤呼 facade 為 Model。

✅ Model `App\Models\System\RequestLog` 保留 disambiguating token；其他層（URL `/admin/system/logs`、Route `system.logs.*`、Permission `admin.system.log.*`、Controller `LogController`、View `views/system/log/`、Lang `admin/system/log.php`）統一用 `log`。命名理由詳見 [10012_日誌記錄 §命名說明](10012_日誌記錄.md)（搜尋「命名說明」段）。

> 跟 §9.4.5「業務名 vs 技術名不可混用」的差異：§9.4.5 禁止的是**無外部約束的人為混用**（如 Party vs dealer 是團隊自由選擇）；本節允許的是**外部 namespace 強制讓 Model 不能用 short token** 的情境——例外的觸發條件是不可控的外部撞名，不是命名偏好。

### 9.5 違規類型

四種典型違規：

#### 9.5.1 階層深度不對齊

各層對 resource 採用不同的層數。

❌ 反例：
- Module folder：`Modules/System/Acl/UserController.php`（system → acl → user，3 層）
- Route：`system.users.*`（system → users，2 層，跳過 acl）
- View：`views/acl/user/`（acl → user，2 層，跳過 system）

三層各跳一層，認知成本最高。

✅ 修正方案 A（保留 acl 層）：所有層都加上 `acl/`。URL 變 `/admin/system/acl/users`，view folder 改成 `views/system/acl/user/`。

✅ 修正方案 B（移除 acl 中介層）：Module folder 把 `Acl/` 下的檔案移到 `Modules/System/{User,Role,...}/`；view folder 從 `views/acl/` 搬到 `views/system/`。URL/Route/Permission 維持現況不動。

方案 A 多一層 acl，語意分群更清楚；方案 B 移除 acl，URL 更短。擇一即可。

#### 9.5.2 階層位置不對齊（多/缺 module 段）

某層有 module 段，另一層沒有。

❌ 反例：
- Route：`/admin/organizations`（root 之下，無 module）
- Permission：`admin.organization.organization.*`（多了一層 `organization` module）
- Module folder：`Modules/Party/Organization/`（Party 是 module）

座標一個是 `/organization`、一個是 `organization/organization`、一個是 `Party/Organization`。

✅ 修正：取一個 module 段名，五層全部對齊。例如全用 `org`：URL/Route `org.organizations.*`、Permission `admin.org.organization.*`、Module folder `Modules/Org/Organization/`、View `views/org/organization/`。

#### 9.5.3 主體 token 不同

見 [§9.2 反例](#92-座標的-token-一致性)。

#### 9.5.4 業務名 vs 技術名混用

見 [§9.4.5](#945-業務名-vs-技術名不可混用)。

### 9.6 檢驗清單

對每個 resource，回答以下五題，答案應**完全相同**（排除 case 與單複數）：

1. URL prefix 的 `{module}/{resource}` 序列是什麼？
2. Route name 的 `{module}.{resource}` 序列是什麼？
3. Permission name 的 `{module}.{resource}` 序列是什麼？
4. Module folder 的相對路徑（從 `Modules/` 起）是什麼？
5. View folder 的相對路徑（從 `views/` 起）是什麼？

五題答案完全一致 → 對齊。任一不同 → 違規，列為 refactor 候選項並對照 §9.5 修正。

## 十、遷移指引

當現有專案的命名與本規範不符（橫向 §二–§七 / 縱向 §九）時，依下列順序處理。

### 10.1 需要調整的項目

| 軸 | 調整項目 | 說明 |
|---|---|---|
| 橫向（§二–§七） | `routes/*.php` | `Route::prefix()` 與 `.name()` 改為複數 |
| 橫向 | Controller 內 `route('...')` 呼叫 | 更新 route name |
| 橫向 | View 內 `route('...')` 呼叫 | 更新 route name |
| 橫向 | `$xxx_url` 變數（Controller 產生的 URL）| 若 `route()` 產生，跟著更新；若 `routePrefix()` 動態推算則自動正確 |
| 縱向（§九） | Module folder rename / move | namespace 跟 use 跟著改，IDE refactor |
| 縱向 | View folder rename / move | `view('...')` path string 跟著改，可 grep 一次取代 |
| 縱向 | Permission seeder | 字串依新座標重打；注意角色現有 permission 連動 |
| 縱向 | Route prefix + name 階層 | Controller 用 `routePrefix()` 則不必動 `route()` 呼叫 |
| — | Middleware `can:` / `permission:` | 字串引用 permission name，跟著 seeder 改 |

### 10.2 `routePrefix()` 動態推算的好處

符合 [10007_權限機制.md §12](10007_權限機制.md) 的 `routePrefix()` 模式，Controller 從當前 route name 反推前綴：

```php
protected function routePrefix(): string
{
    return preg_replace('/\.[^.]+$/', '', request()->route()->getName());
}
```

這類 Controller 只要路由改完，不需要逐一修改 `route()` 呼叫，反推邏輯自動適應新名稱。**採用 `routePrefix()` 模式是降低遷移成本的關鍵**。

### 10.3 遷移順序

#### 10.3.1 程式碼層先動，URL 後動

```
1. 改 Module folder（namespace 跟 use 跟著改，IDE 自動 refactor）
↓ 2. 改 View folder（view path string 跟著改，可 grep 一次取代）
↓ 3. 改 Permission 字串 + seeder
↓ 4. 改 Route prefix + name（Controller 用 routePrefix() 則不必動 route() 呼叫）
↓ 5. 改 URL（可選；對外服務考慮 301 redirect 舊 URL）
```

URL 改動最後做，因為涉及 SEO、外部連結、行動裝置書籤；前面四步全在程式碼內部，影響範圍可控。

#### 10.3.2 專案優先順序

1. **新模組**：直接依規範命名，不產生技術債
2. **已存在但尚未部署到正式環境的專案**：一次性全量對齊
3. **正式運行中的專案**：評估影響範圍後分批調整（URL 改變需考慮 SEO、外部連結等）

## 十一、常見問題

**Q：URL 複數、permission name 單數，不會混淆嗎？**

不會。兩者出現的位置不同：URL 出現在網址列與路由定義，permission name 出現在 `can()`、`authorize()`、Seeder 等 PHP 程式碼中。維護者只要理解「URL 複數 / permission 單數」這個分工，對應記憶並不困難。

**Q：不規則複數怎麼辦（如 `taxonomy → taxonomies`）？**

URL 與 route name 使用英文正確複數形，就算是不規則複數也要寫對（`/system/taxonomies`、`system.taxonomies.index`、DB 表 `sys_taxonomies`）。permission name resource 段使用單數，剛好完全規避這個問題（`admin.system.taxonomy.access`）。

**Q：複合詞怎麼複數化（如 `leave-type`、`salary-item`）？**

對最後一個名詞加複數：`leave-types`、`salary-items`。Route name 同理：`leave-types.index`。DB Table 同理：`leave_types`、`salary_items`。

**Q：`access-token`、`user-device` 這類已是複合概念的詞呢？**

同樣對最後名詞加複數：`access-tokens`、`user-devices`、`personal_access_tokens`。ocadmin 現有路由與資料表已照此規則命名，可直接參考。

**Q：Pivot table 兩個單數誰前誰後？**

字母序。`role_user`（r 在 u 前面）、`product_tag`（p 在 t 前面）、`permission_role`（pe 在 ro 前面）。Laravel `belongsToMany` 預設按字母序推算 pivot 名稱，不依此會多打一個參數。

**Q：自訂表名前綴怎麼處理？例如本系統用 `acl_` / `org_` / `sys_` 等前綴？**

前綴不影響單複數判斷，主體仍複數：`acl_roles`、`acl_permissions`、`org_organizations`、`sys_settings`、`sys_menus`。Model 端覆寫 `$table` 屬性指明即可。

**Q：不可數名詞（如 `cache`、`data`、`info`）？**

照英文本身的慣例。`cache` 不可數，資料夾/檔名也用 `cache/` 不加 s（見 [`10019_圖片管理.md`](10019_圖片管理.md) 的縮圖快取路徑）。`data` 集合語意用 `data`、單筆用 `datum` 但實務上 `data` 已被吸收為集合與單數通用。`info` 視為不可數。

**Q：模組 / namespace 資料夾用單數還是複數？例如 `app/Models/Sale/Order.php` 還是 `app/Models/Sales/Order.php`？**

**單數**（`Sale/`）。模組資料夾是「網域概念 / 命名空間」，不是「資源集合」，與 class 命名規則一致。本系統現況：

- `app/Models/`：`Acl/`、`Catalog/`、`Org/`、`System/`（全部單數）
- `app/Portals/Ocadmin/Modules/`：`Account/`、`Catalog/`、`Dashboard/`、`Member/`、`Org/`、`System/`（全部單數）

所以：

```
app/Models/Sale/Order.php                              ✅  銷售網域，含 Order / OrderProduct / Payment 等
app/Models/Sales/Order.php                             ❌
app/Portals/Ocadmin/Modules/Sale/OrderController.php   ✅
app/Portals/Ocadmin/Modules/Sales/OrderController.php  ❌
```

對比 Laravel 內建：`App\Http\Controllers\Auth\`（auth 是概念，單數）、`App\Notifications\`、`App\Events\` 之類是 framework 機制資料夾，性質不同，不在此規範範圍內。

> URL 端對應的 **module 段**也是單數（§二.2「複數規則只套用在 resource 段」），所以對應路徑是 `/admin/sale/orders` —— **單數 module 段 + 複數 resource 段**，與資料夾 `Sale/` 同步單數。

#### Sale vs Sales 的語意張力（為何容易搖擺）

`Sale` 是本規範裡**最容易搖擺**的字，因為英文裡 `sales` 不只是 `sale` 的複數，**還是業務語境下的獨立名詞**：

| 寫法 | 英文語感 | 在程式裡指什麼 |
|---|---|---|
| `a sale` / `the sale` | 單一交易 / 一個促銷活動 | 一筆銷售紀錄、一個促銷 entity |
| `sales` | 業務語境的「銷售（業務）」——the Sales team、sales report、sales pipeline 等 | 業務領域 / 部門名稱 |

所以看到「Sales 模組」的直覺反應會是「對啊，就是 sales 業務嘛」——這個拉力是真的，不是錯覺。

**為何本規範仍選 `Sale/`：**

1. **「網域概念」比「業務領域標籤」更貼近 module folder 的角色**：folder 裡放的是 `Order` / `OrderProduct` / `Invoice` 等具體 Model，每個都是「銷售網域裡的 entity」；folder 名作為這些 entity 的 namespace 前綴（`Sale\Order`），單數讀起來更像「銷售（概念）下的 Order」，複數讀起來像「多筆 sale 下的 Order」反而怪。
2. **跨層一致勝過個別字的英文直覺**：若 `Sale` 破例用 `Sales`，那 `Inventory` 也可以爭論成 `Inventories`，`Catalog` 變 `Catalogs`，`Org` 變 `Orgs`，最終要不要複數變成逐字判斷。一律單數最省心。
3. **對 Magento 那派「Sales 模組」的態度**：Magento 採 `Sales` 確實是業界存在的選擇，但 Rails / Django / 多數 Laravel 應用採單數 module 命名。沒有壓倒性業界共識，內部一致性勝出。

**規避招式（若真覺得 `Sale` 太單薄）：** 換個更具體的 module 名繞開——例如直接叫 `Order/`（如果模組重心是訂單）、`Pos/`（如果是 POS 收銀流程）、`Checkout/` 等。**不要為了表達「業務領域」而把 module folder 改複數。**
