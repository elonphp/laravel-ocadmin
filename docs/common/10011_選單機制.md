## 一、概述

後台側欄選單需依使用者權限動態顯示：使用者只能看到自己有權限的選單項目。本文件記錄兩種選單方案的完整設計，兩套並存於 `MenuComposer` 中，透過設定切換。

- **方案 A — Code Driven 單檔**：選單以 PHP hardcoded array 定義在 `MenuComposer::buildMenusFromCode()` 內，無 DB 依賴。
- **方案 B — DB Driven**：選單存入獨立的 `sys_menus` / `sys_menu_translations` 表，與權限表分離，透過 `permission_name` 欄位關聯權限做可見性判斷。

**切換方式：** `config/vars.php` 的 `menu_driver` 設定，或 `.env` 設定 `MENU_DRIVER`：

| 值 | 說明 |
|---|---|
| `code` | 從 `MenuComposer::buildMenusFromCode()` hardcoded array 讀取（預設） |
| `database` | 從 `sys_menus` 表讀取（需先跑 `MenuSeeder`） |

**預設為 `code` 的理由**：ocadmin 是範例 / 範本專案，要 clone 即跑、零 DB 依賴。多數衍生專案的 sidebar 一旦定稿就不大改，runtime 編輯選單是少數場景（多租戶 / SaaS）才需要切到 `database`。`MenuSeeder` 仍保留並與單檔結構等價，需要時 `MENU_DRIVER=database` + `db:seed --class=MenuSeeder` 即可切換。

三方案的優劣比較見 [`docs/research/選單機制其它實作.md`](../research/選單機制其它實作.md)。

### 1.1 選單權限慣例：`*.menu` action

選單可見性用獨立的 `*.menu` 權限後綴，與資料存取（`.access` / `.access_all`）解耦：

| Action | 用途 | 由誰判定 |
|---|---|---|
| `{resource}.menu` | 選單是否顯示在 sidebar | MenuComposer |
| `{resource}.access` | 列表 + 單筆檢視（基礎資料權限） | Controller `authorize()` |
| `{resource}.access_all` | 看全部（不限 created_by） | Controller 內部 scope |
| `{resource}.modify` / `.delete` / ... | 各操作 | Controller `authorize()` |

**為何分開？** 三者語意不同，不該強制蘊含：

- 純 UI 可見性（`.menu`）vs 資料權限（`.access`）拆開 → 角色設計時各自勾選，意圖明確
- 不需在程式碼裡寫「access_all 蘊含 access」之類的隱式邏輯
- 權限管理 UI 上一個 checkbox 一件事
- **一個資源可掛在多個選單下**（見 [10007 §十二 單控制器多選單入口](10007_權限機制.md#十二單控制器多選單入口)）：`.access` / `.modify` / `.delete` 綁在**資源**（一個功能模組一組），`.menu` 綁在**選單放置點**。故同一個「商品設定作業」可同時出現在「基本資料 > 商品」與「銷售 > 商品」——**功能權限只需一份**（同一個 `catalog.product.access`），各放置點的顯隱則由各自的 `.menu` 表達（可共用一個，也可拆成 `master.product.menu` / `sale.product.menu` 獨立開關）。反之，若把選單可見綁死進 `.access`，下列兩種情形就表達不出來：
  - **多放置點獨立顯隱**：同一資源在 A 選單顯示、在 B 選單隱藏（給不同角色不同視角）。
  - **可達但不顯示**：某頁從別頁按鈕或子流程進入，能 `.access` 但不該佔一條側欄。

**規則：**

1. 選單檔／選單表的 `permission` 一律填 `*.menu`
2. Controller `authorize()` 一律用 `*.access` / `*.modify` / `*.delete` / ...，**不**用 `*.menu`
3. Role 設定 UI 可加前端規則：勾 `*.access_all` 自動連帶勾 `*.access`（後者為基礎必選）
4. 父層分組節點（無 `href`、無 `route`）不需 `permission`；子項全被過濾時自動隱藏

### 1.2 選單樹層級獨立於五層座標對齊

[10023 §九](10023_英文名稱單複數規範.md) 規範的「五層座標對齊」涵蓋 URL prefix / Route name / Permission / Module folder / View folder 五層 — **不包含選單樹**。選單樹是 UX 層，分組基於使用者心智模型；五層是 resource 座標層，反映實際 URL / 程式碼結構。**兩者正交，各自選最合適的結構**。

**實例**：`Taxonomy` / `Term` 兩個 resource 五層全對齊 `system / taxonomy`、`system / term`（兩段座標），**Controller 不開中介資料夾**（直接放 `Core/Controllers/System/TaxonomyController.php`、`TermController.php`）。但側欄選單把這兩條收進 `Vocabulary (詞彙管理)` 中介層 — System 母選單下視覺較整齊：

```
System
├── 訪問控制（5 條 ACL link）        ← Controller 也有 Acl 中介層（system_acl）
├── 詞彙管理（2 條 Taxonomy/Term）   ← Controller 沒中介層（座標兩段平鋪）
├── 參數設定
├── 資料表結構
├── 選單設定
├── 遷移功能
└── 日誌管理
```

**判斷選單何時開中介層**：純 UX 考量（同類 link ≥ 2、避免母選單下平鋪過多項影響掃描）。**選單開中介層不會也不該帶動 Controller / view / URL / permission 同步開中介層** — 那受五層座標對齊規範約束，跟選單分組無關。反過來說，Controller 有中介層（如 ACL `Core/Controllers/System/Acl/`）對應選單通常也有同名中介群（「訪問控制」），這是巧合而非強制——Controller 開中介是因「議題 4 五層對齊 ✓ + 多 sibling ✓ 雙條件」滿足，選單開中介是因 UX 需要。

業界對照（選單樹與底層 URL 結構獨立）：
- GitHub Settings — sidebar ~15 分群，URL 全是 `/settings/{section}` 沒中間群段
- VS Code 左側活動欄 — Explorer / Search / Source Control 是 UI 群組，不對應內部 API namespace
- Magento Admin — Marketing / Content / Reports 大分群，Controller 散在各 module 裡

## 二、方案 A — Code Driven 單檔（預設）

選單樹以 PHP 陣列 hardcoded 在 `MenuComposer::buildMenusFromCode()` 內，無 DB 依賴，clone 範例後即可起跑。範本層為 `MENU_DRIVER=code` 的預設行為。

### 2.1 實作位置

`app/Portals/Ocadmin/Core/ViewComposers/MenuComposer.php`：

- `buildMenus()` 依 `config('vars.menu_driver')` 切換來源
- `buildMenusFromCode()` 整棵選單樹（L1 → L2 → L3）以 `$menus[]` 陣列定義
- `filterByPermission()` 遞迴過濾無權限項；分組節點（無 `href`）子項全空時自隱

### 2.2 選單項目結構

每個節點為 array，欄位：

| 欄位 | 必填 | 說明 |
|------|------|------|
| `id` | 僅 L1 | HTML id，用於 sidebar 展開/收合狀態 |
| `icon` | 僅 L1 | FontAwesome class |
| `name` | 是 | 顯示名稱（內部以 `__()` 解 lang key） |
| `permission` | 否 | 對應的選單權限名稱，慣例填 `{resource}.menu`；無此欄位則不做權限檢查 |
| `href` | 是 | 連結，空字串表示純分組節點（父層） |
| `children` | 是 | 子項目陣列 |

### 2.3 範例片段（節錄自 `MenuComposer::buildMenusFromCode()`）

```php
$t = fn (string $key) => __("admin/common/menu.{$key}");

// 商品型錄
$menus[] = [
    'id'       => 'menu-catalog',
    'icon'     => 'fa-solid fa-tag',
    'name'     => $t('text_catalog'),
    'href'     => '',
    'children' => [
        [
            'name'       => $t('text_catalog_product'),
            'icon'       => '',
            'href'       => route('lang.ocadmin.catalog.products.index'),
            'permission' => permName('catalog.product.menu'),
            'children'   => [],
        ],
        // ... 其他子項
    ],
];
```

### 2.4 過濾邏輯

`filterByPermission()` 規則：

1. 項目有 `permission` 欄位 → 用 `Gate::forUser($user)->check()` 檢查；無權限則移除
2. 項目無 `permission` 欄位 → 不檢查，直接保留
3. 子項目全部被移除且父層 `href` 為空 → 父層也移除（避免空的分組節點）
4. `super_admin` 的 `Gate::check()` 永遠回傳 `true`（見 [10007 §10.5](10007_權限機制.md#十使用者權限快取)），選單全部可見；其他角色依角色指派的權限決定

**為何用 `Gate::forUser($user)->check()` 而非 `$user->can()`？** Spatie Permission 的 `can()` 不經過 Laravel `Gate::before`，會導致 `super_admin` / `developer` 的放行邏輯失效。

**父層可見性規則：** 父層選單（如「系統管理」、「商品型錄」）不設 `permission`，可見性由子項向上推導決定：

- 至少一個子項有權限 → 父層**顯示**
- 所有子項都無權限 → 子項全被過濾 → 父層自動**隱藏**

因此不需要為父層選單額外定義整段群組的 `*.menu`，子項各自的 `{resource}.menu` 已足夠控制整個選單群組的可見性。

### 2.5 新增模組 Checklist

- [ ] 在 `buildMenusFromCode()` 對應位置插入新的 `$menus[] = [...]` 區塊
- [ ] 子項目 `permission` 慣例填 `{resource}.menu`
- [ ] 對應的 `*.menu` 權限已在 `AclPermissionSeeder` 中定義
- [ ] 翻譯字串加在 `lang/{locale}/admin/common/menu.php`
- [ ] 若同時想支援 DB Driven，同步在 `MenuSeeder` 補上對應的 `createMenu(...)` 呼叫

### 2.6 變體：模組各自一個 Menu class（未實作）

當模組多到單檔過長時，可考慮拆成「每個模組一個 `{Module}Menu` class」，MenuComposer 改持有 `$menuClasses` 註冊表逐一收集。**ocadmin 範本層未實作此變體**——目前選單規模仍在單檔可掃描範圍內，引入多檔的成本大於收益。

設計細節與三方案對照：[`docs/research/選單機制其它實作.md`](../research/選單機制其它實作.md)。

## 三、方案 B — DB Driven（進階：需 runtime 編輯選單時）

> 本方案需 `MENU_DRIVER=database` + 跑 `MenuSeeder` 後才會生效。適合需後台 UI 編輯選單、多租戶 / SaaS、多 Portal 同表分割等場景。範本層保留完整實作（`MenuController` / `MenuTreeController` / `MenuSeeder`），切過去即可用。

選單存入獨立的 `sys_menus` / `sys_menu_translations` 表，不與 `acl_permissions` 混用。透過 `permission_name` 欄位關聯權限做可見性判斷。

### 3.1 設計原則

選單與權限各司其職：

| | `sys_menus` 表 | `acl_permissions` 表 |
|---|---|---|
| **職責** | 定義 sidebar 的結構、順序、連結 | 定義功能權限（access / modify / delete） |
| **欄位** | portal、icon、route_name、href、sort_order | name、guard_name |
| **關聯方式** | `menus.permission_name` → `acl_permissions.name` | — |

**不混用的好處：**

- `acl_permissions` 不會多出 `icon`、`href`、`sort_order` 等選單專用欄位
- Spatie 的 `hasPermissionTo()` / `can()` 不會撈到選單節點
- 選單可以有不需權限檢查的純分組節點，不必塞進權限表

### 3.2 資料表結構

```
menus                                  menu_translations
├── id                                 ├── id
├── portal ──→ 'ocadmin','www','pos'   ├── menu_id (FK → menus)
├── parent_id (FK → menus, nullable)   ├── locale
├── permission_name (nullable) ──→     ├── display_name
│   acl_permissions.name               └── unique(menu_id, locale)
├── route_name (nullable)
├── href (nullable)
├── icon (nullable)
├── sort_order (default: 0)
├── is_active (default: true)
└── timestamps
```

**欄位說明：**

| 欄位 | 說明 |
|------|------|
| `portal` | 所屬應用入口：`ocadmin`（後台）、`www`（官網）、`pos`（POS）等，對應 `config/portals.php` |
| `parent_id` | 自我關聯，`null` 表示 L1 根節點 |
| `permission_name` | 關聯到 `acl_permissions.name`，慣例填 `{resource}.menu`；`null` 表示不檢查權限（純分組節點，可見性由子項推導） |
| `route_name` | 本系統的 named route，MenuComposer 用 `route()` 動態產生 URL（含語系前綴） |
| `href` | 外部連結或靜態 URL，直接輸出到前端 |
| `icon` | FontAwesome class，僅 L1 根節點使用 |
| `sort_order` | 同層排序，數字越小越前面 |
| `is_active` | 停用選單項目而不刪除 |

**`route_name` 與 `href` 的優先順序：**

| route_name | href | 結果 |
|---|---|---|
| 有值 | — | `route($route_name)` 產生 URL（本系統路由） |
| null | 有值 | 直接輸出 `href`（外部連結） |
| null | null | 純分組節點（可展開收合的父層） |

### 3.3 樹狀結構範例

以 Ocadmin 後台為例：

```
[portal=ocadmin]

catalog                              (L1, parent_id=null, icon=fa-solid fa-tags)
├── catalog.product                  (L2, permission=admin.catalog.product.menu, route=lang.ocadmin.catalog.product.index)
├── catalog.option                   (L2, permission=admin.catalog.option.menu, route=lang.ocadmin.catalog.option.index)
└── catalog.category                 (L2, permission=admin.catalog.category.menu, route=lang.ocadmin.catalog.category.index)

sale                                 (L1, parent_id=null, icon=fa-solid fa-cart-shopping)
├── sale.order                       (L2, permission=admin.sale.order.menu, route=lang.ocadmin.sale.order.index)
└── sale.return                      (L2, permission=admin.sale.return.menu, route=lang.ocadmin.sale.return.index)

system                               (L1, parent_id=null, icon=fa-solid fa-gear)
├── system.setting                   (L2, permission=admin.system.setting.menu, route=lang.ocadmin.system.settings.index)
└── system.taxonomy                  (L2, permission=admin.system.taxonomy.menu, route=lang.ocadmin.system.taxonomies.index)
```

> 選單節點只管「呈現與連結」，權限檢查透過 `permission_name` 指向 `acl_permissions` 表。同一個權限可被多個選單節點引用（如 §14 單控制器多選單入口的情境）。

### 3.5 Menu Model

```php
// app/Models/Menu.php

namespace App\Models;

use App\Traits\HasTranslation;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\BelongsTo;
use Illuminate\Database\Eloquent\Relations\HasMany;

class Menu extends Model
{
    use HasTranslation;

    protected $fillable = [
        'portal', 'parent_id', 'permission_name',
        'route_name', 'href', 'icon', 'sort_order', 'is_active',
    ];

    protected string $translationModel = MenuTranslation::class;
    protected array $translatedAttributes = ['display_name'];

    protected $with = ['translation'];

    public function parent(): BelongsTo
    {
        return $this->belongsTo(Menu::class, 'parent_id');
    }

    public function children(): HasMany
    {
        return $this->hasMany(Menu::class, 'parent_id')
            ->where('is_active', true)
            ->orderBy('sort_order');
    }

    /**
     * 產生 URL：route_name 優先，其次 href，都沒有回傳空字串
     */
    public function resolveUrl(): string
    {
        if ($this->route_name) {
            return route($this->route_name);
        }

        return $this->href ?? '';
    }

    /**
     * 轉為前端 sidebar 所需的 array 格式
     */
    public function toMenuItem(): array
    {
        return [
            'id'         => 'menu-' . $this->id,
            'icon'       => $this->icon ?? '',
            'name'       => $this->display_name,
            'permission' => $this->permission_name,
            'href'       => $this->resolveUrl(),
            'children'   => $this->children->map(fn ($child) => $child->toMenuItem())->toArray(),
        ];
    }
}
```

### 3.6 MenuComposer（DB 版）

```php
// app/Portals/Ocadmin/Core/ViewComposers/MenuComposer.php

use App\Models\Menu;

class MenuComposer
{
    public function compose(View $view): void
    {
        $view->with('sys_menus', $this->buildMenus());
    }

    protected function buildMenus(): array
    {
        $user = auth()->user();

        // 撈該 portal 的 L1 根節點（含遞迴子項）
        $menus = Menu::with('children.children')  // eager load 2~3 層
            ->where('portal', 'ocadmin')
            ->whereNull('parent_id')
            ->where('is_active', true)
            ->orderBy('sort_order')
            ->get();

        return $menus
            ->map(fn ($menu) => $menu->toMenuItem())
            ->map(fn ($item) => $this->filterByPermission($item, $user))
            ->filter()
            ->values()
            ->toArray();
    }

    /**
     * 遞迴過濾：移除無權限的項目，子項全空的父層也移除
     */
    protected function filterByPermission(array $item, $user): ?array
    {
        if (!empty($item['permission']) && !$user->can($item['permission'])) {
            return null;
        }

        if (!empty($item['children'])) {
            $item['children'] = collect($item['children'])
                ->map(fn ($child) => $this->filterByPermission($child, $user))
                ->filter()
                ->values()
                ->toArray();

            if (empty($item['children']) && empty($item['href'])) {
                return null;
            }
        }

        return $item;
    }
}
```

**父層可見性規則：** 父層選單（如「商品型錄」）的 `permission_name` 設為 `null`，不做權限檢查，可見性由子項向上推導：

```
商品型錄  (permission_name = null, 純分組節點)
├── 商品      (permission_name = admin.catalog.product.menu)
├── 選項      (permission_name = admin.catalog.option.menu)
└── 規格      (permission_name = admin.catalog.specification.menu)
```

- 使用者有任一子項 `*.menu` 權限 → 「商品型錄」**顯示**
- 使用者三個都沒有 → 子項全被過濾 → 「商品型錄」自動**隱藏**

因此不需為父層選單額外定義群組權限（如 `admin.catalog.*.menu` 整段），子項各自的 `*.menu` 已足夠控制整個選單群組的可見性。`super_admin` 的 `can()` 永遠回傳 `true`（見 [10007 §10.5](10007_權限機制.md#十使用者權限快取)），選單全部可見；其他角色依角色指派的權限決定。

### 3.7 Seeder 範例

```php
// database/seeders/MenuSeeder.php

use App\Models\Menu;

class MenuSeeder extends Seeder
{
    public function run(): void
    {
        $portal = 'ocadmin';

        // L1: 商品型錄
        $catalog = Menu::updateOrCreate(
            ['portal' => $portal, 'route_name' => null, 'permission_name' => null, 'parent_id' => null, 'icon' => 'fa-solid fa-tags'],
            ['sort_order' => 10, 'is_active' => true]
        );
        $catalog->translateOrNew('en')->display_name = 'Catalog';
        $catalog->translateOrNew('zh_Hant')->display_name = '商品型錄';
        $catalog->save();

        // L2: 商品
        $product = Menu::updateOrCreate(
            ['portal' => $portal, 'parent_id' => $catalog->id, 'permission_name' => permName('catalog.product.menu')],
            ['route_name' => 'lang.ocadmin.catalog.product.index', 'sort_order' => 1]
        );
        $product->translateOrNew('en')->display_name = 'Products';
        $product->translateOrNew('zh_Hant')->display_name = '商品';
        $product->save();

        // L2: 選項
        $option = Menu::updateOrCreate(
            ['portal' => $portal, 'parent_id' => $catalog->id, 'permission_name' => permName('catalog.option.menu')],
            ['route_name' => 'lang.ocadmin.catalog.option.index', 'sort_order' => 2]
        );
        $option->translateOrNew('en')->display_name = 'Options';
        $option->translateOrNew('zh_Hant')->display_name = '選項';
        $option->save();

        // ... 其餘模組依此類推
    }
}
```

### 3.8 新增模組 Checklist

- [ ] 在 `MenuSeeder` 中新增該模組的 L1 + L2 選單項目
- [ ] 填入 `permission_name`（慣例填 `{resource}.menu`）
- [ ] 填入 `route_name`（本系統路由）或 `href`（外部連結）
- [ ] 確認對應的 `*.menu` 權限已在 `AclPermissionSeeder` 中定義
- [ ] 執行 `php artisan db:seed --class=MenuSeeder`

### 3.9 多 Portal 支援

同一張 `sys_menus` 表透過 `portal` 欄位區分不同應用的選單：

| portal | 應用 | 說明 |
|--------|------|------|
| `ocadmin` | 後台管理 | 完整的 sidebar 選單樹 |
| `www` | 官網 ApiWww | 前台導覽列 |
| `pos` | POS 系統 ApiPos | POS 功能選單 |

每個 Portal 的 MenuComposer 只撈自己的 `portal`：

```php
// Ocadmin
Menu::where('portal', 'ocadmin')->whereNull('parent_id')...

// POS
Menu::where('portal', 'pos')->whereNull('parent_id')...
```

不同 Portal 的選單完全獨立，不會互相干擾。同一個權限（如 `admin.catalog.product.access`）可被多個 Portal 的選單節點引用。
