## 設計原則

1. **簡單優先，按需抽層**：預設只有 Controller + Model 兩層，其他層要有明確觸發條件才開。
2. **YAGNI**：不為了「未來可能需要」而提前抽象。事實證明重構成本比過度設計成本低得多。
3. **抽層的觸發條件是「實質需求」**：多 Model 編排 / 業務分歧 / 跨 Portal 共用，三選一才抽。不要為了「分層乾淨」而抽。
4. **業務分歧與資料編排分兩軸看**：
    - **業務分歧軸**（不同 Portal 有不同業務流程，catering 派送 vs retail 門市）→ 用 **Service** 隔離，按 Portal + 模組 + entity 為原則
    - **資料編排軸**（同 entity 的多表 CRUD，建單同時 sync products / options / payments）→ 用 **Repository** 集中，跨 Portal 共用
    兩軸獨立判斷、各自 evolve，不要混為一談。
5. **不採用 query-wrapper Repository**：典型 Repository pattern（`$repo->find($id)` 包 `Order::find($id)`）在 Eloquent 框架下永遠是多餘層，反對。但「entity 多表 CRUD 編排」性質的 Repository 是有價值的、採用——細節見〈[Repository 層](#repository-層entity-多表-crud-編排)〉、〈[為什麼不採用 query-wrapper Repository](#為什麼不採用-query-wrapper-repository)〉。
6. **「要不要抽層」與「放哪一層」是兩個問題**：前者看觸發條件（多 Model 編排 / 多 Controller 共用 / 跨 HTTP context 重用），後者**只看作用範圍**（被幾個 Module、幾個 Portal 用到）。把兩者混成一個問題問，是分層失控的主因——見〈[判準：作用範圍決定層級](#判準作用範圍決定層級)〉。

## 分層總覽

### 判準：作用範圍決定層級

Service 放哪裡，**只由一個問題決定：這段業務編排被誰用到**。

| 作用範圍 | 位置 |
|---|---|
| 跨 Portal 共用 | `app\Services\` |
| 單一 Portal 內、跨 Module 共用 | `app\Portals\{Portal}\Services\` |
| 單一 Module 內 | `app\Portals\{Portal}\Modules\{Domain}\{Resource}\` |

心智模型：**一個 Portal 就是縮小版的 `app/`，外加一個 `Modules/`**。這條規則不限於 `Services`——`Events` / `Listeners` / `Jobs` / `Console` / `Mail` 等 layer 同理，與 `app/` 同名同義，只是作用範圍縮到那個 Portal（見 [10001 §6.0.1](10001_Portal概述.md#601-portal-級-layer-資料夾)）。

> **判準不是「對內 vs 對外」。**
>
> `app\Services\` 的常見成員確實是包裝 Integration 的對外業務介面（發票、通知、金流的統一介面），但那是**結果**、不是**定義**——對外串接天生就跨 Portal 共用，所以自然浮到最上層。反過來說，一段純內部的跨 Model 編排，只要真的被兩個以上 Portal 用到，一樣屬於 `app\Services\`。
>
> 更要緊的是反向那句：**「跨 Model 的業務流程」本身不構成放進 `app\Services\` 的理由**。它只回答「需要一個 Service」，不回答「放哪一層」；層級一律回到上表的作用範圍判定。混用這兩個問題，`app\Services\` 就會變成雜物間。

### 三個核心角色

Service 依作用範圍分三個角色，規則相同、只差範圍：

- **Module Service**（`app\Portals\{Portal}\Modules\{Domain}\{Resource}\{Entity}Service.php`）：單一 Module 內的業務編排。**預設起點**——絕大多數 Service 都在這裡出生。
- **Portal Service**（`app\Portals\{Portal}\Services\{Entity}Service.php`）：同一 Portal 內、被**兩個以上 Module**（或 `Core/` 與 Module 同時）用到的業務編排。知道自己屬於哪個 Portal，不知道被哪個 Module 呼叫。
- **全域 Service**（`app\Services\{Entity}Service.php`）：被**兩個以上 Portal** 用到的業務編排，不知道 Portal。

第四個角色是 **Repository**（`app\Repositories\{Entity}Repository.php`）：跨 Portal 共用的 entity 多表 CRUD 編排——**選用層、預設不開**，見〈[Repository 層](#repository-層entity-多表-crud-編排)〉。

其他層（Controller、Model、Integrations、Helpers、Supports）都環繞這幾個角色服務。完整對照：

| 層 | 位置 | 用途 | 預設是否開啟 |
|----|------|------|--------------|
| Controller | `app\Portals\{Portal}\Modules\{Domain}\{Resource}\` | HTTP 入口、Request / Response、Portal 邊界 | 永遠 |
| Model | `app\Models\` | Active Record、關聯、Scope、defaults | 永遠 |
| Module Service | `app\Portals\{Portal}\Modules\{Domain}\{Resource}\{Entity}Service.php` | 單一 Module 內的業務編排 | 按需 |
| Portal Service | `app\Portals\{Portal}\Services\`（默認 flat） | 同一 Portal 內、跨 Module 共用的業務編排 | 按需 |
| 全域 Service | `app\Services\`（默認 flat） | 跨 Portal 共用的業務編排（含包裝 Integration 的對外介面）| 按需 |
| Repository | `app\Repositories\`（flat） | entity 多表 CRUD 編排，跨 Portal 共用，不知道 Portal | **選用**（罕用）|
| Integrations | `app\Integrations\` | 外部服務（SMS、Email、金流、物流 API） | 按需 |
| Helpers | `app\Helpers\` | 橫切技術工具，無 domain knowledge（DateHelper、StringHelper）| 既有 |
| Supports | `app\Supports\{Domain}\` | domain 純運算，認 entity / business rule、**不碰 DB 與外部**（TaxCalculator）| 按需 |

### 依賴方向（重要）

```
Controller → Service → Repository → Model
              ↓             ↓
        Integration    Supports / Helpers
```

- **Service 可以呼叫 Repository / Integration / Supports / Helpers / Model**
- **Service 三層之間只能由內往外呼叫**：Module Service → Portal Service → 全域 Service。反向（全域 Service 去呼叫某個 Portal 的 Service）代表東西放錯層，該把它往上搬，而不是建立反向依賴
- **Repository 可以呼叫其他 Repository / Supports / Helpers / Model**，**不能呼叫 Service**
- **Repository 不知道自己被哪個 Portal 呼叫**——這是它能跨 Portal 共用的前提
- Controller 簡單動作可以略過 Service，直接打 Repository 或 Model

## 預設流程：Controller 直接操作 Model

簡單的 CRUD 不需要 Service，Controller 直接使用 Eloquent：

```php
// 列表
$orders = Order::query()
    ->filterByPhone($filter_data['filter_phone'] ?? null)
    ->paginate();

// 建立
$order = new Order();
$order->fill($request->validated());
$order->save();

// 更新
$order->fill($request->validated());
$order->save();
```

當發生以下情況之一，再往上抽層：

- 需要一段業務編排（多 Model 編排、多 Controller 共用、跨 HTTP context 重用）→ 抽 Service。**層級另外判**，依作用範圍決定（見〈[判準：作用範圍決定層級](#判準作用範圍決定層級)〉），預設從 Module Service 起
- 需要呼叫外部 API（簡訊、金流、Email）→ 抽 `app\Integrations\{Vendor}\{Vendor}Client`
- 單一 Controller 方法超過 ~150 行編排邏輯 → 抽 Service

## Model 職責

### Model 應該做的事

| 職責 | 做法 |
|------|------|
| 欄位定義與型別 | `$attributes`（預設值）、`$casts`、`$fillable` / `$guarded` |
| 關聯 | `hasMany()`、`belongsTo()`、`belongsToMany()` 等 |
| 查詢 Scope | `scopeFilterByXxx()`，處理複雜/跨欄位/跨關聯查詢 |
| 表單預設值 | `defaults()` 靜態方法，供 Controller `create()` 使用 |
| Accessor / Mutator | 欄位顯示/儲存轉換（用 `Attribute::make()`） |

### Model 不應該做的事

| 不該做 | 該放哪裡 |
|--------|----------|
| 跨 Model 的業務流程（建單同時扣庫存、寫 log） | Service 層——**層級依作用範圍決定**，預設 Module Service（見〈[判準：作用範圍決定層級](#判準作用範圍決定層級)〉）|
| HTTP / Request 處理 | Controller |
| 呼叫外部服務（送簡訊、刷卡） | `app\Integrations\` |
| Portal 專屬條件（如 `brand_id` 隔離） | Controller 或 Middleware |

## 複雜查詢：Model Scope

### 先說：OrmHelper 是什麼

`OrmHelper`（`app\Helpers\OrmHelper.php`）是本系統獨創的 ORM 查詢輔助工具，把 `?filter_name=A&equal_status=B&page=2&sort=id&order=desc` 這類 URL query string 自動套到 Eloquent Builder：

| 參數 prefix | 行為 |
|---|---|
| `filter_xxx` | 模糊比對 `xxx LIKE '%...%'`，支援萬用字元 `*0912`、精確 `=0912345678` |
| `equal_xxx` | 精確比對 `xxx = ...` |
| `sort` / `order` / `page` / `per_page` | 自動處理排序與分頁 |

詳細用法（白名單機制、進階匹配規則）見 [00003_Ocadmin程式規範.md](00003_Ocadmin程式規範.md#filterdata-白名單機制)。

### 何時 OrmHelper 不夠用 → 需要 Scope

`OrmHelper` 處理「**參數名直接對應到單一資料表欄位**」的查詢（`filter_name → name LIKE`、`equal_status → status =`）。當查詢參數**無法直接對應到單一欄位**時，需要 Model Scope：

| 情境 | 說明 |
|------|------|
| 多欄位 OR 搜尋 | 輸入「電話」需同時搜尋 `mobile` 和 `telephone` |
| 跨關聯查詢 | 依訂單商品名稱搜尋訂單 |
| 特殊值轉換 | `withoutV` 要轉成 `status_code <> 'void'` |
| 彈性格式解析 | 日期輸入支援多種格式（`20260301`、`2026-03-01`、`20260301-20260331`） |

這些邏輯屬於**領域知識**，不應分散在各 Portal Controller，應集中於 Model Scope。

### Scope vs OrmHelper：具體對照

```
filter_phone → mobile LIKE '%...%' OR telephone LIKE '%...%'   ← 一對多欄位，需 Scope
filter_name  → name LIKE '%...%'                               ← OrmHelper 直接處理
equal_status → status = '...'                                  ← OrmHelper 直接處理
filter_product_name → whereHas('orderProducts', ...)           ← 跨關聯，需 Scope
filter_delivery_date → BETWEEN / >= / <=（彈性格式）           ← 格式解析，需 Scope
```

判斷標準：**參數名稱無法直接對應到單一資料表欄位** → 使用 Model Scope；對得上的就走 OrmHelper。

### 命名規則

| 規則 | 範例 |
|------|------|
| 前綴一律用 `scope` | `scopeFilterByPhone` |
| 語意對應使用者輸入的概念 | `filterByPhone`（而非 `filterByMobileOrTelephone`） |
| 空值時直接 return | `if (empty($value)) return;` |

### Scope 範例

**多欄位 OR 搜尋**（改用 `OrmHelper::filterOrEqualColumn()` 支援萬用字元 `*0912`、`=0912345678`）：

多欄位 OR 的模式：第一個欄位直接呼叫，後續欄位各自包一層 `orWhere(function)` 再呼叫（因為 `filterOrEqualColumn` 內部使用 `->where()`，不能直接串 OR）：

```php
public function scopeFilterByPhone(Builder $query, ?string $phone): void
{
    if (empty($phone)) return;
    $phone = preg_replace('/[\s\-]/', '', $phone);
    $query->where(function ($q) use ($phone) {
        OrmHelper::filterOrEqualColumn($q, 'filter_mobile', $phone);
        $q->orWhere(function ($sub) use ($phone) {
            OrmHelper::filterOrEqualColumn($sub, 'filter_telephone', $phone);
        });
    });
}

public function scopeFilterByKeyname(Builder $query, ?string $keyname): void
{
    if (empty($keyname)) return;
    $query->where(function ($q) use ($keyname) {
        OrmHelper::filterOrEqualColumn($q, 'filter_personal_name', $keyname);
        $q->orWhere(function ($sub) use ($keyname) {
            OrmHelper::filterOrEqualColumn($sub, 'filter_shipping_personal_name', $keyname);
        });
        $q->orWhere(function ($sub) use ($keyname) {
            OrmHelper::filterOrEqualColumn($sub, 'filter_shipping_company', $keyname);
        });
        $q->orWhere(function ($sub) use ($keyname) {
            OrmHelper::filterOrEqualColumn($sub, 'filter_payment_company', $keyname);
        });
    });
}
```

**跨關聯查詢**：

```php
public function scopeFilterByProductName(Builder $query, ?string $name): void
{
    if (empty($name)) return;
    $query->whereHas('orderProducts', function ($q) use ($name) {
        OrmHelper::filterOrEqualColumn($q, 'filter_name', $name);
    });
}
```

**彈性日期格式**：

```php
// 支援多種輸入格式：20260301、2026-03-01、20260301-20260331、20260301-
public function scopeFilterByDeliveryDate(Builder $query, ?string $dateStr): void
{
    if (empty($dateStr)) return;
    $sql = DateHelper::parseDateToSqlWhere('delivery_date', $dateStr);
    if ($sql) $query->whereRaw("({$sql})");
}
```

**特殊值轉換**：

```php
public function scopeFilterByStatusCode(Builder $query, ?string $statusCode): void
{
    if (empty($statusCode)) return;
    if ($statusCode === 'withoutV') {
        $query->where('status_code', '<>', 'void');
    } else {
        OrmHelper::filterOrEqualColumn($query, 'filter_status_code', $statusCode);
    }
}
```

### 安全性：白名單的必要性

`OrmHelper::applyFilters()` 的實作是「欄位存在於資料表就套用」，若不加白名單，使用者可自行在 URL 加入 `?equal_customer_id=5&filter_is_closed=0`，這在**前台對外 Portal 是明確的安全漏洞**。

解決方式為 `filterData()` 白名單（完整說明見 [00003_Ocadmin程式規範.md](00003_Ocadmin程式規範.md#filterdata-白名單機制)）：

```php
$filter_data = $this->filterData($request, [
    'filter_code',
    'filter_phone',          // 進 Scope，不進 OrmHelper
    'filter_delivery_date',  // 進 Scope，不進 OrmHelper
    'equal_status_code',
]);
```

**注意：傳空陣列 `[]` 不等於全開放**，反而是最嚴格——只剩共用參數（`sort, order, page` 等），所有 `filter_*` / `equal_*` 都不會進來。後台內部頁面如需全開放，請用 `$request->query()` 並加注解說明原因。**前台對外 Portal 一律必須使用白名單。**

**Scope 處理的參數，在 `OrmHelper::prepare()` 之前必須從 `$filter_data` 移除**，避免 OrmHelper 重複套用：

```php
$query->filterByPhone($filter_data['filter_phone'] ?? null);
unset($filter_data['filter_phone']);
```

### Controller 整合方式

完整 Controller 整合範例（filterData 白名單 → Scope 串接 → OrmHelper 收尾 → 分頁）見 [`00003_Ocadmin程式規範.md`](00003_Ocadmin程式規範.md#filterdata-白名單機制)，本文件不重複。

### 多 Portal、多品牌環境

Scope 定義在 Model，是整個系統共用的領域知識。**各 Portal 自行組合需要的 Scope**，不需要 Repository 中介：

```php
// Ocadmin Portal（後台）：完整搜尋欄位
$query = Order::query()
    ->filterByPhone($filter_data['filter_phone'] ?? null)
    ->filterByKeyname($filter_data['filter_keyname'] ?? null)
    ->filterByDeliveryDate($filter_data['filter_delivery_date'] ?? null)
    ->filterByProductName($filter_data['filter_product_name'] ?? null);

// POS Portal：只需少數查詢條件
$query = Order::query()
    ->filterByDeliveryDate($filter_data['filter_delivery_date'] ?? null);
```

**品牌隔離不放進 Scope**，因為它是 Portal 的隱性條件，而非使用者輸入的搜尋條件：

```php
// Portal Controller 自行加
$query = Order::query()
    ->where('brand_id', $this->currentBrand()->id)
    ->filterByDeliveryDate($filter_data['filter_delivery_date'] ?? null);
```

## Model 預設值（defaults）

預設值依複雜度分層放置，**不集中在單一 `prepareData()` 方法**（`prepareData` 與 `OrmHelper::prepare()` 撞詞，語意不清）：

| 預設值類型 | 放置位置 | 說明 |
|-----------|---------|------|
| 簡單欄位預設（空字串、0、enum 初始值） | `Model::$attributes` | Laravel 原生，自動套用於新實例 |
| 表單初始值（含關聯選項、顯示預設） | `Model::defaults()` 靜態方法 | 命名語意明確，與查詢邏輯無關 |
| 需要 DB 查詢的預設（如預設門市） | `app\Repositories\{Entity}Repository::newModel()` | 需 DB 依賴時放 Repository（持久化編排的家），不污染 Model |

```php
class Order extends Model
{
    // 簡單欄位預設（Laravel 原生）
    protected $attributes = [
        'status_code' => 'pending',
        'quantity'    => 1,
        'is_visible'  => true,
    ];

    // 表單初始值（靜態方法，供 Controller create() 使用）
    public static function defaults(): array
    {
        return [
            'status_code'    => 'pending',
            'delivery_type'  => 'pickup',
            'payment_method' => 'cash',
        ];
    }
}
```

```php
// Controller create()
public function create(): View
{
    $data['order'] = Order::defaults();
    return view('ocadmin::sale.order.form', $data);
}

// Controller edit()（從 DB 取得，不需 defaults）
public function edit(Order $order): View
{
    $data['order'] = $order;
    return view('ocadmin::sale.order.form', $data);
}
```

## Service 層（業務編排）

### Service 的三個位置

Service 有三個放置位置，**由作用範圍決定**（判準見〈[判準：作用範圍決定層級](#判準作用範圍決定層級)〉）：

- **Module Service**（`app\Portals\{Portal}\Modules\{Domain}\{Resource}\`）：**單一 Module 內的業務編排**。知道自己屬於哪個 Portal、哪個 Module，處理該 Module 特有的業務 rule（派送費計算、找零、假單流程）。**這是預設起點，本章主要規則討論的就是它**。
- **Portal Service**（`app\Portals\{Portal}\Services\`）：同一 Portal 內、**被兩個以上 Module 共用**的領域規則。它存在的理由是**消除 Module 之間的橫向相依**——沒有這一層，B module 就得 `use` A module 的 Service，把兩個本該能各自增刪、各自移植的 feature 綁死。
  - `Core/` 與某個 Module 同時用到的東西也算這一層。讓 `Core/` 去 import 某個 Module 的 Service 更糟——那等於基底層倒過來依賴業務層。
- **全域 Service**（`app\Services\`）：被**兩個以上 Portal** 共用、**不知道 Portal**。典型例子：`InvoiceService` 包裝多家發票廠商（內部呼叫 `app\Integrations\Ecpay\EcpayClient` 或 `app\Integrations\Ezpay\EzpayClient`）、`NotificationService` 包裝多種通知管道（SMS / Email / Push）。呼叫端拿到「開發票」「發通知」這種業務動作、不知道用哪家廠商。

**Service 是業務介面、Integration 是廠商實作**。換廠商只動 Integration、Service 介面不變。

三層的規則完全相同（按需開、按 entity 命名、默認 flat、可注入 Repository / Integration / Supports / Helpers），差別只在作用範圍，因此本章後續的粒度規則、命名、樣態、禁忌**對三者一體適用**。

### 升層是單向的

**先放最裡層，被更大的範圍用到才往上搬**：

```
Module Service ──────────→ Portal Service ──────────→ 全域 Service
            被第二個 Module 用到          被第二個 Portal 用到
```

- **不要預先卡位**：「這個以後大概會共用」不是升層理由。`app\Services\` 之所以會變成雜物間，幾乎都是從這句話開始的
- **升層是重構、不是新增**：搬上去之後原位置不留 wrapper，呼叫端一起改
- **沒有降層的義務**：已經升上去的東西，後來即使只剩一個呼叫端也不必特地搬回來
- 判定「被幾個 Module / Portal 用到」看的是**實際 import**，不是設想中的未來

> 想檢查既有的 `app\Services\` 有沒有失控，方法很直接：逐支數它被幾個 Portal import。**只被一個 Portal 用到的，就是該往下搬的對象**——這個判準可以機械化執行，不需要爭論。

### 目錄結構：默認 flat

`app\Services\` 與 `app\Portals\{Portal}\Services\` 都**默認 flat**，同一 domain 累積到 **≥ 2 支**才開子目錄。門檻對齊 [10001 §6.2.1 默認 flat 原則](10001_Portal概述.md#621-默認-flat-原則)：

```
app\Services\
├── InvoiceService.php          ← 單支，flat
├── NotificationService.php
└── Sale\                       ← 同 domain ≥ 2 支才開子目錄
    ├── OrderSyncService.php
    └── QuotationService.php
```

- 子目錄名用**業務 domain**，跟 `Modules/` 的 `{Domain}` 共用同一套詞彙；不要出現 `Common` / `Misc` / `Other` 這種不表達任何東西的分類
- 開子目錄是**純目錄整理**，不改變作用範圍判定——`app\Services\Sale\OrderSyncService` 一樣必須是跨 Portal 共用的

### 角色

Service 是「**某個作用範圍內、某個 entity 的業務動作編排層**」。多表 CRUD 的 transaction 細節不歸它管——有開 Repository 就交給 Repository，沒開就自己包 `DB::transaction()`。

### 粒度規則（原則）

一個 Portal 內、同一業務 entity **原則上對應一個 Service**：

- 主 Controller 與**同 entity 的 sub-resource Controller** 共用同一個 Service
- 例：`Sale\Order\OrderController`、`Sale\Order\OrderPaymentController`、`Sale\Order\OrderShippingController` 都注入 `Sale\Order\OrderService`
- Service 路徑跟主 entity 對齊：`app\Portals\{Portal}\Modules\{Domain}\{Resource}\{Entity}Service.php`

「原則」表示有例外，見 §「原則的例外」。

### 「同 entity」的判斷指引

新人會問「OrderPaymentController 算同 entity 嗎？」——靠下列 marker 判斷：

| Marker | 符合 → 同 entity |
|---|---|
| URL sub-resource 結構 | `/orders/{order}/payments` → payment 是 order 的 child |
| DB belongsTo 關聯 | `OrderPayment` schema `belongsTo Order` → payment 是 order 的 child |
| 業務 invariant 連動 | 改 payment 會影響 order 狀態（fully_paid → status='paid'）|

**符合任一條件即視為同 entity、共用 Service**。

不算同 entity 的情境：

- 在不同模組（如 `Sale\Order\OrderController` vs `Report\Order\OrderExportController`）
- sub-resource 有獨立生命週期（如 `Catalog\Product\ProductImageController`，當 Image 演化成跨 entity 共用資源）

核心 marker：**業務動作的 boundary 一致** → 同 entity；**業務動作的 boundary 不同** → 各自 Service。

### 原則的例外

「原則上一個 entity 一個 Service」有以下例外（PR comment 註記理由即可）：

1. **純 read-only / view-only Controller**：例如 `OrderCalendarController` 只展示日曆視圖，不需要 OrderService 那一套編輯邏輯，直接打 Model + Scope
2. **Service 膨脹拆分**：原本 OrderService 同時處理 CRUD + 付款 + 退款 + 出貨，後來付款邏輯成長到 200 行 → 拆 `OrderPaymentService`（仍放 `Sale\Order\` 目錄下、跟 OrderService 並列）。**拆出來的 Service 仍歸 OrderPayment 相關 Controller 用、不擴張其他 Controller 用**
3. **Sub-resource 演化成獨立 entity**：原本 ProductImage 跟 Product 緊密綁定 → 後來 Image 變成可被多種 entity（Product / Article / Banner）共用，這時 ImageService 升級成跨 entity 工具

### 觸發條件：何時建 Service

不是每個 Controller 都要有對應 Service。**有以下任一情況才建檔**：

1. **多 Model 編排**：建單同時 sync products / options / payments（即使單 Portal、也建）
2. **Portal 業務分歧**：catering 派送費計算 vs retail 找零，business rule 不同
3. **同 entity 多 Controller 共用**：OrderController + OrderPaymentController + OrderShippingController 共用同一段業務編排
4. **跨 HTTP context 重用**：排程任務、Queue Job 要呼叫同一業務動作
5. **Controller 單一方法超過 ~100 行的編排邏輯**

**單一 Controller 的單表簡單 CRUD 不需 Service**——Controller 直接打 Model。**單 Portal 也適用此原則**——並非「跨 Portal 才開 Service」，單 Portal 同樣可以開 Service，只要符合上述觸發條件。

> 這五條回答的是「**要不要建 Service**」，不是「**建在哪一層**」。後者一律回到作用範圍判定（見〈[判準：作用範圍決定層級](#判準作用範圍決定層級)〉），預設從 Module Service 起。把「跨 Portal」拿來當建不建的門檻，是舊版規範最容易被誤讀的地方。

### 位置與命名

```
app\Portals\PosCateringV3\
├── Services\                       # Portal 內跨 Module 共用（默認 flat）
│   └── PricingService.php          #   ← Sale / Catalog / Report 三個 Module 都用到
└── Modules\Sale\Order\
    ├── OrderController.php         # 主 Controller
    ├── OrderPaymentController.php  # sub-resource Controller，注入 OrderService
    ├── OrderShippingController.php # sub-resource Controller，注入 OrderService
    └── OrderService.php            # 單一 Module 的業務編排；可注入 PricingService
```

三層的檔名規則一致（`{Entity}Service.php`）。分辨一支 Service 屬於哪一層，看它的**目錄位置**，不靠命名加前後綴。

### Service 流程典型樣態

```php
namespace App\Portals\PosCateringV3\Modules\Sale\Order;

use App\Models\Order;
use App\Models\User;
use App\Repositories\OrderRepository;
use App\Integrations\Sms\SmsClient;

class OrderService
{
    public function __construct(
        private OrderRepository $orderRepo,
        private SmsClient $sms,
    ) {}

    public function checkout(array $data, User $user): Order
    {
        // 1. Portal 業務 rule（catering 特有）
        $this->validateDeliveryAddress($data['shipping']);
        $data['delivery_fee'] = $this->calcDeliveryFee($data['shipping'], $data['items']);

        // 2. 多表 CRUD 編排 → 交給 Repository（跨 Portal 共用）
        $order = $this->orderRepo->saveWithRelations(new Order(), $data, $user);

        // 3. Portal 業務後續（catering 特有）
        $this->dispatchToDeliveryQueue($order);
        $this->sms->send($order->customer->mobile, "訂單 {$order->code} 已確認");

        return $order;
    }

    // addPayment、processRefund、syncShipping 等同 entity 動作都放這
}
```

### Service 不該做的事

- **不要包 Eloquent**：不要寫 `findById($id)` / `findAll()` 這種 pass-through，直接用 `Order::find($id)`
- **不要做 HTTP**：`$request`、`redirect()`、`response()` 留在 Controller
- **不要直接呼叫外部 API**：簡訊、金流、Email 屬於 Integrations。Service 注入 Integration Client
- **該 entity 有開 Repository 時，不要自己重寫多表 CRUD 的 transaction 細節**：交給它。Service 編排「業務流程」、Repository 編排「資料寫入」。沒開 Repository（多數情況）則由 Service 自己包 `DB::transaction()`，不必為此硬開一層

## Repository 層（entity 多表 CRUD 編排）

> **選用層、預設不開。** 實務上真正需要它的只有一種情形：**同一 entity 跨多張表、而且多個 Portal 共用同一套寫入邏輯**。只有一個 Portal 在用，就讓 Service 自己包 `DB::transaction()`，不必多這一層——多出來的一層要付出「呼叫端多跳一次、改一件事要開兩個檔」的成本，卻沒有換到共用。
>
> 下面的觸發條件請當**排除性**條件讀：**三條都不符合就不要建**。系統裡長期只有零星幾支 Repository 是正常狀態，不是缺失。

### 角色

Repository 是「**entity 多表 CRUD 編排層**」——管 entity 跨多張表的 transaction、不知道自己被哪個 Portal 呼叫、不做 Portal-specific 業務 rule。

跟典型 Repository pattern（`$repo->find()` 包 `Model::find()`）不一樣——我們**只用 Repository 處理多表編排**，**不做 query wrapping**。

### 觸發條件：何時建 Repository

**有以下任一情況才建檔**：

1. **entity 跨多張表、有 transaction 需求**：例如 Order 同時 sync products / options / payments / shipping
2. **多 Portal 共用同一 entity 的 CRUD**：catering 跟 retail 都建 order，多表 CRUD 邏輯一致
3. **defaults 需要 DB 查詢**：例如「預設門市」要查當前使用者所屬 → `newModel()` 放這

**單表 CRUD 不需 Repository**——Service 或 Controller 直接 `$model->fill()->save()`。

### 位置與命名

- 位置：`app\Repositories\{Entity}Repository.php`（flat 結構，不分 Portal、不分 Module）
- 命名：按 entity 命名
  - ✓ `OrderRepository`、`ProductRepository`、`PurchaseRepository`

```
app\Repositories\
├── OrderRepository.php
├── ProductRepository.php
├── PurchaseRepository.php       # 採購進貨（跨品牌共用）
└── ...
```

### 典型樣態

```php
namespace App\Repositories;

use App\Models\Order;
use App\Models\User;
use Illuminate\Support\Facades\DB;

class OrderRepository
{
    public function saveWithRelations(Order $order, array $data, User $user): Order
    {
        return DB::transaction(function () use ($order, $data, $user) {
            $order->fill($data);

            // 新增/編輯不對稱
            if ($order->exists) {
                $order->updated_by = $user->id;
            } else {
                $order->code       = $this->generateCode();
                $order->created_by = $user->id;
            }
            $order->save();

            // 多表 sync
            $this->syncProducts($order, $data['products'] ?? []);
            $this->syncShippingInfo($order, $data['shipping'] ?? null);
            $this->syncPayments($order, $data['payments'] ?? []);

            return $order;
        });
    }

    public function newModel(User $user): Order
    {
        $order = new Order();
        $order->shop_id = $user->default_shop_id;  // defaults 需要 DB 查詢
        return $order;
    }

    protected function syncProducts(Order $order, array $items): void { /* ... */ }
    protected function syncShippingInfo(Order $order, ?array $shipping): void { /* ... */ }
    protected function syncPayments(Order $order, array $payments): void { /* ... */ }
    protected function generateCode(): string { /* ... */ }
}
```

### Repository 不該做的事

- **不要做 Portal-specific 業務 rule**：catering 派送費、retail 找零 → 那是 Service 的事
- **不要呼叫外部 API**：傳訊、金流 → Integrations
- **不要做 query wrapping**：不要寫 `findById($id)` / `findActive()` 這種純 pass-through
- **不要 HTTP 相關**：`$request`、`response()` → Controller

### Repository ↔ Service 依賴方向

| 規則 | 為什麼 |
|---|---|
| Service 可以呼叫 Repository | Service 編排業務流程、Repository 是它的 CRUD 工具 |
| **Repository 不能呼叫 Service** | Repository 應該不知道 Portal、保持 Portal 無關 |
| Repository 可以呼叫其他 Repository | 跨 entity 的多表 transaction（如 Order 內也要寫 Inventory）|
| Service 可以直接打 Model（不經 Repository）| 簡單單表動作不需要 Repository |

### 多品牌 / 跨 Portal 共用範例

兩品牌共用採購、財務、料件，但各自前台、訂單、行銷的專案分層：

```
app\Portals\
├── PosCateringBrand1\Modules\Sale\Order\OrderService.php   # 品牌1 訂單編排
├── PosCateringBrand2\Modules\Sale\Order\OrderService.php   # 品牌2 訂單編排
├── OcadminBrand1\Modules\Purchase\PurchaseController.php   # 品牌1 採購管理
└── OcadminBrand2\Modules\Purchase\PurchaseController.php   # 品牌2 採購管理

app\Repositories\
├── OrderRepository.php       # 兩品牌訂單的多表 CRUD
├── PurchaseRepository.php    # 採購進貨共用
├── MaterialRepository.php    # 料件共用
└── AccountingRepository.php  # 財務會計共用
```

業務分歧落在 Module Service、資料編排落在 Repository——**兩軸獨立**、各自 evolve。

## Supports：純運算 utility

### 角色

無 Portal 業務語意、無 DB 寫入、純粹「給定輸入、產出輸出」的轉換層。**認 entity / business rule、但不操作 DB**。

例如：
- `OrderLabelFormatter`：給 `OrderProduct`，產出列印標籤的 array
- `TaxCalculator`：給商品價格與稅率，產出含稅價
- `ShippingFeeCalculator`：給地址與商品，產出配送費
- `BarcodeBuilder`：給 SKU，產出 barcode 字串

> **按需層**：沒有符合條件的成員就不要預建空資料夾。

### 邊界：Supports vs Service

判準一句話：**要不要碰 DB 或外部服務**。

| 這個 class 需要… | 落點 |
|---|---|
| 只吃參數、算完就回傳 | `app\Supports\{Domain}\` |
| 讀 / 寫 DB（查設定值、撈關聯資料） | Service |
| 呼叫外部 API、發通知、寫 log | Service（對外那段再往下交給 Integration）|

**「本質上是 domain 規則」不足以把它留在 `Supports`。** 例：一支「算出貨期限」的類別，性質上跟 `TaxCalculator` 同型，但它要讀系統設定裡的營業時間、還要看訂單目前狀態 → **不是純運算，落 Service**。

遇到這種情形，優先**切兩半**：Service 負責把 DB 資料撈齊，`Supports` 收「營業時間 + 訂單成立時刻」算出期限。**能切就切，切不動就整支放 Service**——不要為了讓它待在 `Supports` 而把 DB 查詢偷渡進去，那會讓這一層的「無 side effect」保證失效，之後沒有人敢直接信任 `Supports` 底下的東西。

### 為什麼不叫 Service

`Service` reserve 給「**Portal 內業務動作編排**」。看到 `XxxService` 讀者就知道：這是某 Portal 的、有業務流程、可能涉及 transaction 與 Integration。

純運算 utility 跟 Portal 無關、不做 transaction、無 side effect——叫 `Formatter` / `Builder` / `Calculator` 後綴更精確。位置統一放 `app\Supports\`。

### Supports vs Helpers 怎麼分

兩者本質不同：

| | `app\Helpers\` | `app\Supports\` |
|---|---|---|
| 內容性質 | 橫切技術工具，**無 domain knowledge** | domain 純運算，**認 entity / business rule** |
| 引用的東西 | 只認 raw data type（string、date、array） | 認 Model、enum、domain 概念 |
| 跟業務的關係 | 跟系統業務無關，換到別專案也能用 | 跟系統業務緊密綁定 |
| 典型成員 | DateHelper、StringHelper、UrlHelper | OrderLabelFormatter、TaxCalculator |
| 內部分類 | flat 或按 raw type 分 | 按業務 domain 分子目錄 |

**判斷規則**：問「這個東西有沒有引用 Model 或 domain enum？」

- 沒引用 → `app\Helpers\`（橫切技術工具）
- 有引用 → `app\Supports\{Domain}\`（domain 純運算）

### 位置與命名

```
app\Supports\
├── Sale\
│   ├── OrderLabelFormatter.php
│   ├── ShippingFeeCalculator.php
│   └── TaxCalculator.php
├── Catalog\
│   └── BarcodeBuilder.php
└── Hr\
    └── LeaveBalanceCalculator.php
```

- 內部按業務 domain 分子目錄（跟 modules 一致）
- 檔名用 `XxxFormatter` / `XxxBuilder` / `XxxCalculator` 後綴表達職責

### Supports 不該做的事

- **不要操作 DB**：要操作 DB 走 Repository
- **不要有 side effect**：不發 SMS、不寫 log、不改 Model 狀態
- **不要 HTTP 相關**：純運算不該知道 Request

## Integrations 層：外部服務

### 什麼東西放這裡

- 簡訊（Every8d、Mitake）
- Email（Mailgun、SendGrid）
- 金流（ECPay、NewebPay）
- 物流 API（黑貓、宅配通）
- 其他第三方 API

### 位置與命名

```
app\Integrations\
    Sms\
        SmsClient.php       // 介面或抽象類
        Every8dClient.php
        MitakeClient.php
    Ecpay\
        EcpayClient.php
    Mail\
        MailClient.php
```

使用 `Client` 或 `Gateway` 後綴，避免與 `Service` 混淆。

### 為什麼跟 Service 分開

- **Integrations 是「對外溝通」**，Service 是「內部業務」。
- 兩者壽命不同：外部 API 簽約/改版週期長，業務邏輯日日改。放一起會互相污染。
- Service 需要送簡訊時，注入 `SmsClient`，Service 本身不知道用哪家廠商。

```php
class OrderService
{
    public function __construct(private SmsClient $sms) {}

    public function confirm(Order $order): void
    {
        $order->status_code = 'confirmed';
        $order->save();
        $this->sms->send($order->customer->mobile, "訂單 {$order->code} 已確認");
    }
}
```

## 為什麼不採用 query-wrapper Repository

### 拒絕的是哪一種 Repository

我們**不採用「典型 Repository pattern」**——即「在 Eloquent 外再包一層 `$repo->find($id)` / `$repo->findActive()` 之類的 query wrapper」。

但**「entity 多表 CRUD 編排」性質的 Repository 是有價值的、有採用**（見 §「Repository 層」）。兩者差異：

| 類型 | 角色 | 我們的立場 |
|---|---|---|
| Query-wrapper Repository | 包 Eloquent 的查詢 API | ✗ 拒絕 |
| Entity-orchestration Repository | 編排多表 CRUD transaction | ✓ 採用 |

### Query-wrapper Repository 為什麼不採用

Repository Pattern 來自 Java / .NET 生態，目的是在 ORM 外再包一層，讓業務層不依賴 ORM。但 **Laravel Eloquent 本身就同時是 Active Record + Query Builder**：

- 寫入：`$order->save()`、`$order->delete()`
- 查詢：`Order::where(...)->get()`
- 領域查詢邏輯：Model Scope（`Order::filterByPhone(...)`）
- 交易：`DB::transaction(fn() => ...)`

Query-wrapper Repository 在 Laravel 裡只是「把 `Order::find($id)` 包裝成 `$repo->find($id)`」，除了增加一層間接性，沒有帶來任何能力。

### 常見的三層誤區

```
❌ Controller → Service → Query-wrapper Repository → Eloquent
```

這個疊法的問題：

- Service 方法多半只是轉發給 Repository
- Repository 方法多半只是轉發給 Eloquent
- 新增一個查詢要改三處
- 同一個 Controller 有時走 Service、有時直接走 Repository，沒有一致規則

### 我們採用的分層

```
✓ Controller → Model（簡單 CRUD）
✓ Controller → Service → Model（業務編排 + 多表寫入，Service 自己包 DB::transaction()）
✓ Controller → Service → Repository → Model（多表寫入邏輯需要跨 Portal 共用時）
✓ Service → Integration Client（呼叫外部 API）
✓ Service → Supports / Helpers（純運算 helper）
```

**查詢走 Model Scope**（領域查詢知識在 Model）。**寫入 / 業務 → Service**（層級依作用範圍，見〈[判準：作用範圍決定層級](#判準作用範圍決定層級)〉）。多表寫入預設就在 Service 裡包 transaction；只有當那套寫入邏輯要**跨 Portal 共用**時才下沉到 Repository。Repository 不做 query wrapping、只做 entity 持久化編排。

### 舊系統 `OrderRepository::resetQueryData()` 的問題

舊系統用 query-wrapper Repository 做複雜查詢前處理：

```php
public function resetQueryData($data)
{
    if (!empty($data['filter_phone'])) {
        $data['andOrWhere'][] = [
            'filter_mobile' => $data['filter_phone'],
            'filter_telephone' => $data['filter_phone'],
        ];
        unset($data['filter_phone']);
    }
    return $data;
}
```

| 缺點 | 說明 |
|------|------|
| 型別不安全 | `$data` 是無型別的可變 array，輸入輸出契約不明確 |
| 隱性結構 | `andOrWhere`、`whereRawSqls` 等內部結構對呼叫端不透明 |
| 難以測試 | 需要帶入整個 `$data` array 才能測試單一規則 |
| 多 Portal 不友善 | 邏輯藏在 Repository，各 Portal 需繞過或重寫 |

新系統用 Model Scope 取代這類**查詢邏輯**：

| 優點 | 說明 |
|------|------|
| 方法簽名明確 | `filterByPhone(?string $phone)` 一眼知道輸入型別 |
| 可獨立測試 | 每個 Scope 可單獨測試 |
| 多 Portal 共用 | Scope 在 Model，任何 Portal 直接呼叫 |
| 可組合 | 各 Portal 自由選擇需要哪些 Scope |

**新系統的 Repository（如 `OrderRepository::saveWithRelations()`）做的是「entity 多表 CRUD 編排」、不是查詢前處理**——徹底跟舊系統的 query-wrapper Repository 切割。

## 分層決策速查表

| 情境 | 做法 |
|------|------|
| 單 Portal、單表簡單列表查詢 | Controller + Model Scope |
| 多 Portal 共用列表查詢 | Controller + Model Scope（各 Portal 自己組合需要的 Scope）|
| 單 Portal、單表簡單建單 / 編輯 | Controller + Eloquent（`$order->fill()->save()`），不需 Service / Repository |
| 多 Portal 共用建單 / 編輯（業務一致）| 全域 Service；同 entity 多表且真的共用寫入邏輯，才另外開 Repository |
| 多 Portal 業務分歧的建單 / 編輯 | Controller + Module Service（共用的那段抽全域 Service）|
| 同 entity 多個 Controller（OrderController / OrderPaymentController）| 共用同一個 Service（同 Portal + 模組 + entity）|
| 跨 Model 的 transaction（建單同時扣庫存）| Service 自己包 `DB::transaction()`；同 entity 多表且跨 Portal 共用才考慮 Repository |
| 單一操作涉及多表、Controller 變肥（即使單 Portal）| 開 Service 把編排抽出來，符合「按需建檔」原則 |
| 業務編排只有一個 Module 用到 | `app\Portals\{Portal}\Modules\{Domain}\{Resource}\{Entity}Service.php` |
| 業務編排被同一 Portal 的兩個以上 Module（或 `Core/` 與 Module）用到 | `app\Portals\{Portal}\Services\`（Portal Service）|
| 業務編排被兩個以上 Portal 用到 | `app\Services\`（全域 Service）|
| 不確定以後會不會被共用 | 先放最裡層，真的被用到再往上搬（升層是單向的，不預先卡位）|
| 純運算 utility（label 格式、稅率算法），**不碰 DB / 外部** | `app\Supports\{Domain}\` 用 Formatter / Builder / Calculator 後綴 |
| 本質是 domain 規則、但算之前要先查 DB | Service；能切就把純算的那半留在 `app\Supports\{Domain}\` |
| 橫切技術工具（日期、字串、URL）| `app\Helpers\`（既有位置） |
| 送簡訊 / Email / 刷卡 | `app\Integrations\{Vendor}\{Vendor}Client` |
| Service 需要通知使用者 | Service 注入 Integration Client |
| 表單預設值（純欄位） | `Model::$attributes` 或 `Model::defaults()` |
| 表單預設值（需 DB 查詢） | Service（該 entity 已開 Repository 時放 `{Entity}Repository::newModel()`）|
| 品牌隔離、Portal 權限條件 | Controller 或 Middleware 加 where，不進 Scope |
| 跨品牌共用採購、財務、料件 | Repository（flat in `app\Repositories\`），各品牌 Portal 共用 |
